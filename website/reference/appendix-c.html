APPENDIX C

常见故障排查

排查的起点是保留原始提示并确认现场，而非立即寻找一条“修复命令”。请记录当前目录、Git 版本、分支或分离状态，以及工作区是否有未提交成果。本附录按现象提供查询方向；涉及丢弃内容、改写历史或更新远端时，仍应返回正文阅读适用条件。

暂存以后，普通diff没有输出

这一现象首先涉及比较边界。文件可能已经进入候选，也可能确实没有新增变化；先确认命令两侧，再判断是否需要重新编辑或提交。

现象与解释

工作文件经过暂存以后，git diff 为空，而 status 仍提示有待提交变化。普通 diff 主要比较工作区与索引；如果两者在所选范围内一致，就没有未暂存差异。这不意味着下一次提交没有内容。

查询与处置

使用 git diff --cached 检查索引相对当前提交的候选差异；使用 git diff HEAD 查看工作区相对当前提交的总体变化。后者可能把已暂存与未暂存变化合并呈现，不能代替候选检查。若仓库尚无初始提交，还应注意部分以 HEAD 为前提的查询不适用。详见第 3 章。

提交成功以后，工作区仍有修改

提交成功说明所选候选形成了记录，不说明每一份工作编辑都被纳入。本节通过提交前后的选择关系分析剩余变化，避免为追求干净状态而丢弃必要内容。

现象与解释

提交记录了索引所描述的候选状态，不自动纳入全部工作文件。暂存后继续编辑、存在未选择文件，或工具生成新文件，都可能使提交后仍有变化。

查询与处置

先读状态两列，再分别检查候选与工作区差异。需要保留的剩余变化可以另作有意义的提交；仅希望保留为草稿时，也不必强行提交。决定丢弃之前，明确来源和路径并保全需要的内容。不能把“让状态干净”作为覆盖文件的充分理由。

切换分支被拒绝

切换拒绝通常是在保护可能被目标检出覆盖的现场。诊断应先确认受影响路径与编辑，再选择保留方式，不能把暂存视为任何切换问题的通用修复。

现象与解释

Git 提示本地修改或未跟踪文件将被覆盖。保护针对的是目标更新与当前现场之间的关系，单纯执行 git add 通常不能消除风险：暂存并没有把草稿变成分支上的持久提交，也没有让目标更新与其自动兼容。

查询与处置

检查受影响路径，再按任务选择提交、保存现场、另建工作树或明确放弃相关编辑。使用 stash 时说明是否包含未跟踪文件，恢复后也要检查内容与索引。切换成功后仍需确认草稿在哪里；不要把成功切换理解为原分支自动保存了草稿。详见第 5 章与第 14 章。

进入分离HEAD状态

分离HEAD允许直接观察某个提交，状态本身不等于仓库损坏。需要区分仅阅读旧版本，还是已经产生应长期保留的新工作，再决定是否建立入口。

现象与解释

HEAD 直接定位一个提交，而非经普通本地分支解析。这是查看旧版和执行某些工具操作时的合法状态，不代表仓库损坏。

查询与处置

若仅查看，可以在处理好工作区以后返回原分支；若在此创建了需要保留的新提交，应先为当前结果建立分支等清晰入口，再离开。离开后能否找回取决于实际对象、reflog 和其他入口，不能依赖长期无条件恢复。详见第 5 章与第 8 章。

推送因非快进更新而被拒绝

此类拒绝说明所请求更新不符合相应入口关系要求，不会自动删除本地提交。先取得另一端的进展并检查双方范围，再决定如何整合。

现象与解释

服务器拒绝让目标引用按普通规则前进，常见原因是目标当前提交不是拟推送提交的祖先。这可能来自双方分叉，也可能涉及本地改写，不必然仅“远端更新较晚”。

查询与处置

先核对远端地址和目标分支，再获取可见历史，比较双方独有提交。依据团队约定选择整合或重新准备更新。强制推送与租约保护都不能代替共享历史的协作判断。若错误实际来自权限、规则或网络，应在对应层排查。详见第 7 章。

合并、变基或拣选因冲突暂停

三种操作都可能需要人工决定内容，但暂停现场与继续命令不同。先辨认正在进行哪项操作，再读取来源与候选，避免在未结束的现场再次发起同类任务。

现象与解释

冲突可能来自同一文本区域的不同修改，也可能来自删除与修改、同名新增、重命名或二进制内容等情形。并非每项冲突都出现文本标记，也并非每条路径都具备全部三个索引阶段。

查询与处置

先用状态确认正在进行的操作，再查看未合并条目和相关来源。按最终需求编辑并暂存，随后选择该操作对应的继续方式；目标不成立时，可在理解现场后中止。变基中的双方角色应根据当前重放步骤判断，不能只用含混的“自己”和“对方”作选择。详见第 6 章、第 10 章和第 11 章。

提交中残留冲突标记

文本中的标记可以作为问题线索，却不是判断未合并状态的唯一依据。需要分别检查索引阶段、文件内容和业务结果，判断问题是在解决过程中还是已经进入提交。

现象与解释

可能是解决时遗漏了标记，或暂存了仍含标记的内容。正常提交一般不会接受仍有未合并索引条目的状态，但把带标记的文本明确暂存以后，Git 不会自动理解这些字符一定属于错误。

查询与处置

核对补丁与项目语义，形成修复，并完善相应检查。单纯搜索标记可能误判教学示例或文档引用，因此检测规则也应说明范围和例外。已共享错误优先考虑追加修正，不因发现标记就直接改写公共历史。详见第 15 章。

子模块目录为空或版本不一致

父项目固定一个子提交，不保证当前目录已经取得相应对象与文件。诊断先确认父提交记录的目标，再核对初始化、来源可访问性与子仓库现场。

现象与解释

父项目记录的是依赖位置和提交关系，普通克隆未必已经取得并检出全部子模块。子模块中的新提交、未提交修改与父项目记录更新，也属于不同状态。

查询与处置

先读取状态与配置，确认地址可访问，再按需要初始化和更新。若子模块内有草稿，应先保全，不能为追求一致而直接覆盖。依赖升级需要确保目标提交已经在可访问来源保存，并在父项目提交新的记录。详见第 14 章。

提交姓名或邮箱不符合预期

身份字段由创建提交时的配置和环境决定，平台显示又有自己的关联条件。先检查实际提交正文与生效来源，再判断是否仅需修正以后提交的配置。

现象与解释

有效值可能来自不同配置层或命令环境，作者与提交者字段也不一定相同。平台展示关联与对象中已有元数据，不能混为一谈。

查询与处置

查询配置值及来源，并检查实际提交的作者和提交者。先修正后续提交所用配置；历史是否需要修改，取决于影响范围和协作约定。近期未共享提交与大范围公共历史应采用不同方案。平台邮箱关联不等于重写已有提交字段，历史过滤工具也不应成为处理单个身份问题的默认选择。详见第 2 章与第 11 章。

仓库占用较大或状态查询缓慢

空间占用与操作耗时可能来自不同环节。先记录对象统计、文件规模与测量条件，再选择工具，避免未经定位就堆叠配置或反复维护仓库。

现象与解释

对象历史、未跟踪文件数量、工作区扫描、外部大文件、网络与文件系统，都可能形成瓶颈。对象库较大与 status 缓慢未必具有同一根因。

查询与处置

先记录可重复测量，再分别分析传输、对象与扫描成本。count-objects 提供对象统计，不直接列出所有历史大文件。缓存和文件监视优化需结合版本及平台评估；LFS、历史清理与浅克隆也各有前提。故障现场应先保全，不要为了提速先删除历史。详见第 9 章与第 14 章。

自动合并成功，项目却不能正常工作

文本整合算法无法自动证明接口、单位和业务规则一致。出现这种现象时，应把历史整合成功与语义验收分开，围绕实际失败路径继续调查。

现象与解释

没有文本冲突不代表接口、数据格式或业务约束一致。双方在不同文件中的合理修改，也可能在组合后产生矛盾。

查询与处置

检查合并范围、关键补丁和运行验证，必要时比较两个父提交及整合结果。补充能够暴露问题的测试或资料检查，再修复最终成果。不要因为合并命令退出成功就把故障归因于“Git 已经检查过”。详见第 6 章与第 13 章。

需要恢复的内容不在新克隆中

普通克隆只能取得相应Git范围，草稿、外部对象和平台资料可能有其他保存位置。先确认所需内容是否曾经进入可取得的历史，再选择恢复来源。

现象与解释

新克隆未必包含未推送提交、其他仓库的 reflog、未提交草稿、平台资料或外部对象。浅克隆和部分克隆还会进一步改变本地可用范围。

查询与处置

明确缺失内容原来保存在哪里，检查其他副本、已有标识、备份与外部存储。恢复报告应列出已验证和未覆盖范围。没有进入 Git 的编辑可能需要依赖编辑器或系统备份；不能承诺任何误删都能由 Git 找回。详见第 8 章与第 15 章。
