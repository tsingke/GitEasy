APPENDIX B

配置、别名与检查模板

模板是理解和调整配置的起点，不是应当整份覆盖到个人环境中的标准答案。本附录优先使用仓库局部配置，区分只读别名、行为选择和检查程序。团队规则应由协作约定支持；个人工具偏好不应无意改变共享项目的工作方式。

最小配置与生效来源

配置模板应从项目所需的最少信息开始。先判断某个值是否必须、应作用于哪个仓库，再查询实际生效来源，能够减少多台机器、多个账户之间的隐含差异。

学习仓库使用独立身份

在新建练习仓库中配置姓名和邮箱，有助于避免影响其他工作。下列占位身份使用无效示例域名，不代表真实平台账号。命令应在已经初始化的练习仓库根目录执行。

查询并设置仓库局部身份
git config --local user.name "Git Learner"
git config --local user.email "learner@example.invalid"
git config --show-origin --get user.name
git config --show-origin --get user.email

配置查询的作用是确认 Git 实际读取到什么。配置值还可能来自系统、用户、条件包含和命令上下文；环境也可能提供作者或提交者信息。因此，排查具体提交时还应读取对象元数据，不能仅凭当前配置反推过去提交使用的值。

文本形式便于审阅，但路径不宜硬编码

下面给出一个有意保持简短的配置片段。可通过 git config 逐项设置，或在理解实际配置位置后编辑。不要假设所有仓库都把管理目录保存为工作区中的普通 .git 目录。

局部配置片段示例
[user]
    name = Git Learner
    email = learner@example.invalid
[alias]
    st = status --short --branch
    graph = log --oneline --graph --decorate --all
    last = log -1 --stat

该片段没有预设 pull 的整合方式，也没有统一启用性能优化或换行转换。省略这些选择，是为了让使用者先理解需求再配置，而非因为这些功能不重要。第 7 章、第 11 章与第 14 章分别提供判断背景。

只读别名与行为性别名

别名既可以缩短查询，也可能封装会改变现场的操作。采用模板时先区分这两类能力，再检查参数、路径和失败条件，避免简写名称掩盖实际作用范围。

别名缩短输入，不改变知识前提

st、graph 和 last 只组织查询输出，适合作为个人便捷入口。使用时仍应知道各选项显示什么，例如 --all 扩展观察入口，不代表能够显示本地尚未取得的服务器历史。

适合查询的别名片段
[alias]
    branches = branch -vv
    staged = diff --cached
    recent = for-each-ref --count=10 --sort=-committerdate --format='%(refname:short)' refs/heads

不宜把高影响动作命名成含混的快捷词。例如 discard 未说明覆盖范围，uncommit 未说明保留索引与草稿的方式。若团队确需行为性别名，应明确展开命令、前置条件和恢复方法，不能让缩写遮蔽影响。

不要让别名承担项目规则

个人别名不会自动随仓库传播。若项目依赖一套检查或构建步骤，应提供版本化脚本与文档，而非要求所有成员猜测作者的个人快捷配置。脚本也应记录输入对象、失败含义和工具前提。

客户端钩子的安装与范围

钩子把检查接入本地操作，但源码存在、已经安装和实际强制执行是不同事实。下面分别说明安装方式、检查输入和可能被绕过的边界。

选择可版本化的钩子目录

常见钩子可以放在默认管理目录，也可以通过 core.hooksPath 指定。团队若选择仓库内目录，需要明确安装动作：文件纳入版本控制，不代表新克隆已自动启用该配置。以下命令仅展示显式安装方式。

为当前仓库指定钩子目录
mkdir -p .githooks
git config --local core.hooksPath .githooks
git config --show-origin --get core.hooksPath

安装前应审阅钩子内容及其来源。钩子是可以执行程序的机制，不是纯文本说明。客户端钩子还可能被绕过，不能作为服务器接收规则的唯一依据。跨平台项目应检查解释器、执行权限和工具路径。

pre-commit检查候选内容

本书第 15 章的课程检查器明确区分工作区与索引模式。下面的钩子假设项目已经把该检查器保存为 tools/check_course.py，并具有对应五份资料。检查前先定位仓库根目录，避免相对路径依赖当前子目录。

pre-commit：调用已暂存内容检查
#!/bin/sh
set -eu
root=$(git rev-parse --show-toplevel)
cd "$root"
python3 tools/check_course.py --repo . --index
git diff --cached --check

两个检查分别承担资料规则与部分空白问题检查，任一失败都会中止。它们不验证全部业务要求，也不保证未跟踪文件符合规则。若检查器不在项目中，应先完成分发和路径调整，不能只复制钩子就期待工作。

commit-msg检查示例与规范的区别

提交说明可以采用项目约定，但简化检查必须明确自己的范围。下面的示例只接受一组类型、可选作用域、可选破坏性标记和非空摘要；它不是完整的 Conventional Commits 解析器，不检查正文、尾部或全部语义约束(Conventional Commits 2020)。

commit-msg：受限的首行教学检查
#!/usr/bin/env python3
from pathlib import Path
import re
import sys

message = Path(sys.argv[1]).read_text(encoding='utf-8')
lines = message.splitlines()
first = lines[0] if lines else ''
pattern = r'(feat|fix|docs|refactor|test|chore)(\([^()\r\n]+\))?!?: \S[^\r\n]*'
if re.fullmatch(pattern, first) is None:
    print('Expected: type(scope): nonempty summary', file=sys.stderr)
    sys.exit(1)

使用者应按项目需要决定是否允许其他类型、合并提交说明、撤销说明或工具自动生成的内容。规则过窄会造成不必要的阻断，规则过宽则可能只提供形式上的一致。检查说明必须与实际实现一致。

pre-push应调用真实项目检查入口

推送前可以运行项目的固定检查命令，但不应无条件假设所有项目都有 make test。检查脚本若只读取当前工作区，也不能证明所有即将推送的提交均已通过。高要求项目可能需要在独立检出环境中验证指定版本。

pre-push：调用项目自行提供的检查
#!/bin/sh
set -eu
root=$(git rev-parse --show-toplevel)
cd "$root"
# The project must provide and document this entry point.
python3 tools/project_check.py

上述 project_check.py 是需要项目自行实现的接口占位，不是本教材已经提供的通用检查器。选择部署前应确认文件存在、范围明确且失败能给出可理解提示。需要依据本次推送引用判断时，还应处理 pre-push 提供的参数与标准输入，不能把当前工作区等同于全部推送对象。

模板采用前的验证

一份模板只有在自己的环境和项目条件下得到验证，才适合作为长期约定。验证同时覆盖正常输入、预期拒绝和对既有现场的影响，而不只观察一次成功输出。

正例、反例与边界例

至少准备一个应通过的输入、一个应拒绝的输入，以及一个容易混淆的边界。候选检查的边界例可以是“工作区已修正但索引未更新”；说明检查的边界例可以是“有类型但摘要为空”；推送检查的边界例则应包含工作区与目标提交不一致的情况。

验证结果应记录工具版本和实际退出状态。不能仅因脚本打印了“通过”就认定成功，也不能把日志中出现预期拒绝当作整条实验失败。自动运行与人工阅读分别检查机制和可理解性。

逐项启用与回退

新规则可先在任务分支试用，再向成员解释安装与修复方式。若规则导致误判，应定位检查逻辑和输入范围，而非长期要求成员绕过。回退配置也应明确恢复到哪个值，避免覆盖其他工具原有设置。

团队协作中的最终接收约束，应由适当的服务端机制与持续集成共同支撑。客户端钩子提供及时反馈，文档提供规则解释，评审判断内容合理性，三者各有职责。掌握这些边界，比收集大量未经验证的模板更有价值。
