CHAPTER 12 · 进阶篇

版本标记、签名与发布

张庆科 编著约 33 分钟13 道分层习题

提交标识能够精确定位历史，却不方便人们谈论“本学期第一版”。标签给重要位置一个约定名称，签名为特定对象提供可验证的密钥证明，发布工程则把源码位置、验证过程和分发资料连接起来。本章依次说明这三层关系。

学习目标：能区分轻量标签与附注标签对象；能显式交换并核对标签目标；能说明版本号的兼容性含义；能区分签名有效、身份可信和内容正确；能为资料或软件项目建立可追溯发布与勘误流程。

命名里程碑 →\rightarrow 标签对象 →\rightarrow 标签交换 →\rightarrow 版本约定 →\rightarrow 签名与信任 →\rightarrow 发布证据 →\rightarrow 发布后修订。

标签与发布位置

发布需要一个能够明确说明交付内容的位置。图 12.1 把版本标签、发布材料与验证记录放在同一条交付链上。标签用于定位Git对象，平台发布说明与构建产物提供其他信息；签名可以支持完整性核验，其结论不包含软件行为已经正确。

分支适合表达持续演进的线，提交时分支引用通常前进。标签适合给约定位置命名，普通 commit 不会让它跟随当前分支前进。因此发布后继续修订 main，不会自动把 v1.0.0 改成新内容（图 12.2 ）。

但标签引用不是物理上不可修改。具备权限的人可以强制改写或删除，本地与服务端还可能具有不同规则。稳定性来自项目约定、服务端保护和核验机制，不能只凭名称以 v 开头就相信它永远指向同一对象。

轻量标签与附注标签

轻量标签是一项直接指向对象的引用，不创建专门的标签对象。附注标签则创建 tag 对象，记录目标、目标类型、标签者、时间和说明，可附签名，再由引用指向这个对象。常用目标是提交，但 Git 对象模型并不把全部标签限制为只能指向提交。图12.3以发布提交为例，展示中间是否存在 tag 对象。引用的存储可以由不同后端实现，不应把“标签是一项引用”误写成“标签永远对应一个可手工编辑的文件”。

正式发布通常采用附注标签，便于保留发布理由并支持验证。轻量标签仍适合本地临时观察。选择依据应是需要哪些记录和机制，而非认定某一种形式天然代表高质量。

完整实验：发布位置与主线演进

标签的价值在于为一项交付保留明确位置，而开发分支仍可以继续推进。下面先标记版本，再增加后续提交，通过两个入口的目标对照说明发布与开发为何可以同时进行。

同一提交的两种标签

在新目录执行以下步骤，不使用任何线上仓库。轻量与附注标签使用不同名字，避免对同名重复创建而产生错误。

建立发布实验并创建两种标签
mkdir lab12-release
cd lab12-release
git init -b main
git config user.name "Git Learner"
git config user.email "learner@example.invalid"
printf '# Course\n\nInitial reading material.\n' > README.md
git add README.md
git commit -m "docs: establish release material"
git tag checkpoint-1
git tag -a course-v1.0.0 -m "First stable course material"
git cat-file -t checkpoint-1
git cat-file -t course-v1.0.0
git cat-file -p course-v1.0.0
git rev-parse 'course-v1.0.0^{commit}'

前两项类型查询分别输出 commit 和 tag。附注标签本身的标识与发布提交标识不同；需要比较源码位置时，使用明确的类型剥离语法取得提交。若把 tag 对象标识当作 commit 使用而不理解自动剥离，排查签名或对象差异时容易混淆。

推进主线并确认发布位置保持原值
RELEASE12=$(git rev-parse 'course-v1.0.0^{commit}')
printf '\nCorrect the reading order.\n' >> README.md
git add README.md
git commit -m "docs: clarify reading order"
git show course-v1.0.0:README.md
git diff course-v1.0.0 HEAD -- README.md
git describe --tags --long
git rev-parse 'course-v1.0.0^{commit}'

发布文件不包含新增说明，当前 main 则包含它。describe 的输出把可达标签、距离信息和提交缩写组合起来。它是从所选历史与选项得到的描述，不是向平台查询“最新正式版本”；带合并的提交图中也不能简单把距离解释成日期顺序上的第几个提交。

交换标签要明确方向和范围

普通分支推送不会一概把全部标签带上；具体还受命令参数与配置影响。发布流程建议显式指定目标标签。--tags 会扩大到全部标签，可能把个人检查点也共享出去，不应不加选择地作为每次发布的固定动作。

fetch 的默认自动跟随主要取得指向所抓取历史的相关标签，不能概括为“拉取远端全部标签并覆盖本地同名标签”。需要明确全部标签时使用对应参数，并注意冲突名称和更新规则。对正式发布，核验明确标签的目标比猜测默认行为更可靠。

通过本地裸仓库交换指定发布标签
cd ..
git init --bare --initial-branch=main release-center.git
cd lab12-release
git remote add origin ../release-center.git
git push origin main
git push origin refs/tags/course-v1.0.0
git ls-remote --tags origin
git clone ../release-center.git ../release-reader
git -C ../release-reader rev-parse 'course-v1.0.0^{commit}'

ls-remote 中附注标签可能有名称行与剥离目标行，后者带特殊后缀。两行分别显示标签对象及其剥离目标，应按对象类型解释，避免误计为两个发布版本。新克隆取得的发布提交应与 RELEASE12 相同。

删除标签同样分本地与远端：tag -d 删除本地名称，push --delete origin TAG 删除指定远端名称。二者不会自动清除其他克隆已取得的副本。本节不删除正式实验标签，避免影响后面的恢复与核验。

版本号、兼容性约定与验证

语义化版本把版本写为主版本、次版本、修订版本三段。它适用于已经声明公共 API 的项目：不兼容变化提升主版本，向后兼容的功能增加提升次版本，向后兼容的错误修复提升修订版本。提升较高位时，后面的位按规范重置（图 12.4 ）。

这里的前提是“公共 API”和“兼容性”已经有定义。一个命令行工具可能把命令参数、输出格式和配置文件视为契约；一个教学资料库则可能约定章节路径、实验输入和评分标准。没有先定义契约，只看修改行数，无法合理判断版本级别。

例如将程序参数 --output 改为 --destination 并移除旧参数，可能只改很少代码，却影响所有旧脚本。修复几十行内部性能问题，在行为保持兼容时未必需要提升主版本。版本大小由对使用者的影响决定，不由代码增删量决定。

预发布、构建信息与开发阶段

预发布可以使用类似 1.2.0-rc.1 的名称，表示尚未作为该正式版本稳定发布。构建信息可附加在加号之后，不用于决定语义化版本的优先级。Git 标签中的 v 前缀是常见命名约定，不属于版本号本身的三段数字。

初始开发阶段的 0.x 也有相应规范，不能假定它具有与稳定 API 完全相同的兼容性承诺。教材不要求每个文档项目都照搬软件版本语义，但要求项目把自己的约定写明。对使用者而言，版本号表达维护者的承诺和判断，不是升级必然安全的技术证明。重要升级仍应阅读变更记录、运行测试并检查迁移要求。

签名：从对象完整性到密钥信任

签名验证需要与身份判断、软件验证分别进行。图 12.5 把内容完整性、密钥身份和软件行为列为三条独立证据线。签名验证成功后，仍应核对密钥与预期主体的对应关系，并执行适用的构建与测试；图中的摘要仅为示意。

对象标识把对象内容与一个摘要关联起来，但 user.name 和 user.email 都可以由提交者自行填写。签名进一步使用私钥对规定内容生成证明，验证者用相应公钥检查签名是否匹配（图 12.6 ）。

签名至少涉及三个问题：密码学验证是否通过；这个公钥是否确实属于预期主体且仍可使用；被签内容和构建结果是否符合需求。前两项通过也不能推出第三项。签名正确的程序仍可能有缺陷，泄露的私钥也可能生成数学上有效的签名。

Git 支持不同签名格式与外部工具。OpenPGP 常通过 GPG 使用，SSH 签名使用相应 OpenSSH 工具，其他格式也有各自前提。团队应选择一种明确配置与信任分发方式，不应把复制一个 global 开关当成完成密钥管理。

GPG 的配置与验证思路

已有 OpenPGP 密钥时，先确认密钥用途、完整指纹、有效期和可用私钥，再配置仓库的 signingkey。commit -S 对提交签名，tag -s 创建签名标签；verify-commit 与 verify-tag 分别验证相应对象。具体安装和交互生成选项随工具环境而异，应阅读本机文档。

公钥指纹适合通过可信渠道核对。仅从待验证提交的同一不可信来源取得公钥，再据此声称已确认身份，会形成循环论证。撤销、到期和平台显示规则也需要结合组织策略解释。

完整实验：使用一次性 SSH 密钥观察签名

以下扩展实验需要支持 SSH 签名的 Git 与 OpenSSH，常见基线为 Git 2.34 及以后版本，仍须确认本机工具支持。只在新实验目录创建一次性密钥，不读取或覆盖现有登录密钥。为便于自动演示使用空口令；这份教学私钥不用于登录或真实发布。

创建隔离的教学密钥与签名仓库
cd ..
mkdir lab12-signing
cd lab12-signing
mkdir keys
ssh-keygen -q -t ed25519 -N '' -C 'gitbook-demo' -f keys/demo
printf 'learner@example.invalid %s\n' "$(cat keys/demo.pub)" > keys/allowed_signers
mkdir project
cd project
git init -b main
git config user.name "Git Learner"
git config user.email "learner@example.invalid"
git config gpg.format ssh
git config user.signingkey "$(pwd)/../keys/demo"
git config gpg.ssh.allowedSignersFile "$(pwd)/../keys/allowed_signers"
printf '# Signed course\n' > README.md
git add README.md
git commit -S -m "docs: establish signed practice"
git tag -s signed-v1 -m "Signed practice release"

公钥名单把教学主体与教学公钥关联起来。真实环境中的名单必须由可信管理流程维护；本实验由自己建立名单，只用于观察机制，不能证明现实世界身份已经由第三方确认。

验证提交与标签并查看签名记录
git verify-commit HEAD
git verify-tag signed-v1
git log -1 --show-signature
git cat-file -p HEAD

输出应显示 SSH 签名验证结果，提交对象中可以看到签名相关字段。提交签名和标签签名是分别创建的：签名标签不意味着其指向的每一个历史提交都逐项签名，签名提交也不意味着某个平台发布制品已被相同密钥签名。

故意撤去本地允许列表再验证
cp ../keys/allowed_signers ../keys/allowed_signers.saved
: > ../keys/allowed_signers
git verify-commit HEAD

最后一条预期失败。对象内容和签名没有改变，改变的是本地验证所依据的公钥主体名单。它帮助区分“对象中的签名数据”和“验证者的信任配置”，不能把一次失败一概解释为对象已被篡改。

恢复名单并重新验证
mv ../keys/allowed_signers.saved ../keys/allowed_signers
git verify-commit HEAD
git verify-tag signed-v1
git status --short

所有配置只作用于教学仓库。私钥位于仓库外的 keys 目录，不应 add、提交或上传。实验结束时可按课程规定清理整个独立实验目录；不要把这个一次性身份迁移到真实账户。

从标签走向可追溯发布

Git 标签定位对象，托管平台 Release 组织说明与附件，构建系统产生分发制品。三者可以关联，但没有任何一项天然包含其他全部信息。仅创建标签不能证明测试通过，仅上传压缩包也不能证明它来自声称的源码（图 12.7 ）。

图12.8给出一条发布证据链：明确源码位置，记录环境与验证，产生制品，再提供使用说明。关键是能够从制品反查来源，从来源复现规定过程。

发布前核对哪些内容

先确定需求范围和待发布提交，再运行与该提交相匹配的检查。工作区中的临时修复没有进入提交时，不能用“本地测试通过”为旧提交背书。重要构建应从明确提交的干净环境进行，记录工具版本与依赖条件。

变更记录应按使用者关心的新增、修复、兼容影响与迁移事项组织。直接复制所有 commit 标题通常信息过碎，也可能遗漏使用者需要的说明。没有功能变化时，不应为了发布而夸大版本内容。

再核对许可证、依赖分发要求、文档路径与归档内容。涉及 LFS、子模块或外部下载时，要说明制品是否包含实际内容。普通 git archive 导出的源码树不等于完整开发环境。

资料项目的一次发布

GitEasy 的教学路线可以从指定课程提交建立附注标签，生成普通资料归档，保存检查日志与归档摘要，再在自己的课程副本创建平台 Release。标题与标签、目标提交必须一致；若平台允许自动创建缺失标签，应特别检查它选择的目标。

本书不预设作者线上仓库已经存在 v1.0.0 或任何 Release。第17章给出校园项目本地 campus-v0.1.1 发布与恢复路线，线上对象由实际操作后记录。示例版本与真实发行状态必须分开。

发布后勘误与维护线

发布后发现错误，通常追加修复并创建新版本，保留原标签的历史对应关系。移动已经分发的旧标签，会使两位使用者持有同名不同内容，削弱追溯性。必要的特殊撤回应公布原因、受影响范围与替代版本。

维护分支用于组织旧版本后续修复，标签用于标记该线上的具体发行点。若修复也适用于主线，应按依赖情况同步，并分别验证；不能假定拣选成功就代表两个版本行为一致。

对制品，重新制作也需要版本和过程记录。相同源码在不同依赖或时间条件下可能得到不同字节；若项目声称可复现构建，应明确可复现的范围，并用独立重建比较来证明，而不只比较文件名。

发布案例：从一个标签到一份可重建资料包

发布入口仅交付起点，使用者还需要源码、依赖、构建说明和检查结果。案例把这些材料联系到确切版本，避免交付只能在作者机器上运行。

发布对象与发布活动

标签给出一个稳定访问入口，发布活动则还包括资料选择、检查、说明、分发和交接。课程项目可以给某次授课材料创建附注标签，同时导出不含仓库管理数据的压缩包。包的使用者无需理解全部历史，也应能够判断版本、适用环境和已知限制。

若生成过程依赖外部工具、字体或数据，仅保存标签不足以重建完全相同的产物。应记录构建工具版本、输入来源和生成命令。精确到字节的可复现构建还可能要求固定时间戳、压缩参数等条件，不能由“来自同一提交”自动推出。

实验拓展：验证标签、归档与后续主线

以下独立实验创建一项课程发布，并在发布后继续修改主线。目标是证明发布入口保持原位置，而主线可以继续演进。

创建附注标签与资料归档
mkdir package12
cd package12
git init -b main
git config user.name "Git Learner"
git config user.email "learner@example.invalid"
mkdir docs
printf '# Course package\n' > README.md
printf 'Environment: Git and Python 3.\n' > docs/environment.txt
git add README.md docs/environment.txt
git commit -m "docs: prepare the first course package"
git tag -a course-v1.0.0 -m "Course materials for the first delivery"
RELEASE12=$(git rev-parse 'course-v1.0.0^{commit}')
git archive --format=zip --prefix=course-v1.0.0/ \
  --output=../course-v1.0.0.zip course-v1.0.0
printf 'Environment: Git, Python 3, and an editor.\n' > docs/environment.txt
git add docs/environment.txt
git commit -m "docs: clarify the editor requirement"
比较发布入口与当前主线
test "$(git rev-parse 'course-v1.0.0^{commit}')" = "$RELEASE12"
test "$(git rev-parse HEAD)" != "$RELEASE12"
test "$(git cat-file -t course-v1.0.0)" = tag
git show course-v1.0.0:docs/environment.txt
git show HEAD:docs/environment.txt
python3 - <<'PY'
import zipfile
with zipfile.ZipFile('../course-v1.0.0.zip') as package:
    names = package.namelist()
    assert 'course-v1.0.0/README.md' in names
    assert not any('/.git/' in name for name in names)
    text = package.read('course-v1.0.0/docs/environment.txt').decode()
    assert text == 'Environment: Git and Python 3.\n'
PY

归档包含标签所指定版本的跟踪内容，不包含后续编辑器说明，也不是可直接用于查询全部历史的仓库备份。若项目使用外部大文件或子模块，还要单独检查相应内容如何进入分发包。不能只看到压缩文件生成成功，就宣称发布材料完整。

标签用于标明交付位置，开发分支用于继续工作（图 12.9 ）。发布以后应同时核对标签目标和产物来源，避免把不断前进的分支名当作固定版本。

签名验证中的信任链

签名把对象与密钥联系起来，密钥与现实身份的关系还需独立依据。下面按验证链逐层检查，避免把有效签名、可信身份与正确内容混为一个结论。

对象校验、签名校验与身份判断

对象校验确认所取得的内容与标识关系，签名校验确认特定数据与密钥签名关系，身份判断则依赖密钥的可信绑定和管理流程。三者逐层增加信息，但没有一层可以自动证明程序没有缺陷。

验证者需要知道信任哪把密钥、信任范围是什么、密钥是否仍有效，以及验证发生时使用了什么规则。把公钥文件与签名一起从同一未知来源取得，只能建立有限的一致性，不能独立证明真实发布者身份。

长期验证既需要原始发布对象，也需要能够解释当时信任判断的材料（图 12.10 ）。密钥轮换后，应按项目政策保留相应记录，避免仅保存一张绿色验证截图。

密钥轮换与长期验证

密钥可能到期、被替换或因风险而撤销。项目应记录有效期与变更通知渠道，并在必要时提供新的可信声明。长期归档还应保留验证所需的信息和工具说明，使后来的读者理解当时的验证结论。

教学用一次性密钥仅用于观察机制，不应直接作为公开项目的长期签名身份。实验结束后删除教学私钥，与生产密钥的备份、保管和轮换，属于不同管理情境。

迁移练习：发布后发现遗漏

课程包发布后发现缺少一份必读说明。应直接移动原标签，还是发布修订版本？参考分析是：若原标签已经公开并被使用，应优先保留其原有含义，形成修订说明和新的版本入口。这样读者可以区分自己取得的是哪一份材料，也便于复核已发生的教学过程。

若误标对象涉及敏感内容，还需另行处置传播风险，不能只用版本号递增掩盖问题。发布管理既要准确标识版本，也要说明发生了什么变化和使用者应采取什么行动。

本章小结

标签命名对象位置，签名提供相应密钥的验证机制，发布工程建立使用者可以核验的交付关系。稳定名称需要规则支持，可信身份需要公钥管理支持，正确成果需要内容验证支持。

发布验收要求他人能够取得指定版本、理解变化、检查来源并按说明使用；创建名称属于其中一个步骤。把这些证据连接起来，版本管理才延伸到了真正的交付。

本章习题与解析

先独立作答，再展开解析核对思路。答案与教材同源，知识点随题列出。

基础12.1比较两种标签的对象路径，解释为何附注标签标识与发布提交标识可能不同。＋

考查知识点 · 轻量标签 / 附注对象 / 目标剥离

轻量标签通常直接指向目标，附注标签先指向标签对象，再由该对象指向目标并保存说明等信息。因此标签对象标识可与发布提交标识不同；使用cat-file类型和解引用分别核对。

读取附注标签对象可看到它自身的目标与说明，再解析到被标记提交。轻量标签直接保存目标引用，两者对象路径不同。长期报告应说明所记录的是标签对象标识还是最终发布提交标识。

应用12.2完成发布实验，推进 main 后证明标签目标保持原值，说明这一结果依赖什么约定。＋

考查知识点 · 标签稳定 / 分支推进 / 发布约定

标记后推进main，分别解析main和标签目标，检查标签仍指原发布位置。结果依赖没有被显式移动或删除重建的约定；标签不是技术上绝对不可修改的对象入口。

先记录标签解析值，再推进主线并复查，确认开发活动没有自然移动标签。技术上仍可能显式改写标签，因此稳定性还依赖权限、规则和协作约定；发布流程应防止同名内容被无说明替换。

基础12.3解释普通 push、--tags 与显式标签推送的范围；为什么不能说默认 fetch 一定取得远端全部标签？＋

考查知识点 · 标签传输 / 显式范围 / 自动跟随

普通push按配置选择分支等引用，不保证推送所有标签；--tags扩大到标签范围，显式标签推送只表达指定入口。fetch的自动跟随、显式选项和映射影响标签取得，不应概括为一定拥有远端全部标签。

可在独立远端建立多个标签，比较普通推送与显式推送的目标清单。抓取自动跟随与所选历史有关，无法据此保证取得全部标签；需要特定发布名称时应明确查询与传输范围。

应用12.4为课程资料定义兼容性契约，再给新增实验、修正文案和改变评分输入分别选择版本级别并解释。＋

考查知识点 · 兼容性契约 / 版本级别 / 用户影响

先定义课程接口，例如目录布局、输入格式和评分命令。兼容新增实验可对应次版本，文案纠错可对应修订版本，破坏原评分输入可能对应主版本；具体级别取决于实际兼容性契约，而非文件修改数量。

版本级别应围绕使用者依赖的输入、输出和行为决定。修正文案可能不改变契约，改变评分输入则可能破坏既有使用方式。答案需先定义本项目承诺，不能脱离约定机械套用三个数字。

基础12.5说明版本号能表达什么承诺，为什么不能单独作为升级安全证明。＋

考查知识点 · 版本声明 / 验证 / 升级风险

版本号表达维护者对兼容性的约定与沟通，不是自动证明。升级还要查变更说明、依赖、迁移条件和实际测试；即使标为修订版本，也可能存在未发现的缺陷或环境差异。

发布说明应把兼容性承诺与实际测试联系起来，列出变化、依赖和已知限制。版本号提供检索与沟通线索，升级决策仍需结合功能、环境和使用方验证，尤其关注数据格式或调用契约的变化。

应用12.6在具备环境时完成一次性 SSH 签名实验，记录名单为空与恢复后的不同结果。环境不足时明确标注未执行。＋

考查知识点 · SSH签名 / 允许签名者 / 环境前提

使用一次性演示密钥建立并验证签名；清空信任名单再验证，记录与恢复名单后的区别。完成后保留非敏感结果并清理临时密钥；环境不足时写未执行及原因，不复制别人的成功输出作为自己的结果。

实验应记录密钥来源、允许签名者文件与查询结果，并区分加密学验证和身份映射条件。一次性教学密钥不用于真实凭据，环境不足时登记未执行范围，不能根据配置文本就填写验签通过。

基础12.7区分签名有效、公钥属于预期身份和内容正确，分别需要什么证据？＋

考查知识点 · 签名有效 / 密钥归属 / 内容正确

签名有效需要密码学验证；公钥属于预期身份需要可信分发或管理记录；内容正确需要需求与测试。三类证据各自成立，不能由其中一项直接推出另外两项。

有效签名说明被签内容与相应密钥之间的校验关系；密钥属于谁需要独立信任依据，软件是否满足需求需要测试和审读。三项结论可组成发布证据，但任何一项都不能包办其余判断。

基础12.8说明提交签名、标签签名和制品签名是否互相自动包含。＋

考查知识点 · 提交签名 / 标签签名 / 制品签名

提交、标签和制品签名覆盖的对象不同。签名提交不自动签署附注标签或编译附件；制品还可能依赖构建环境与外部输入。发布清单应逐项标明对象、标识、签名和验证方法。

每种签名都有明确的被签对象。附注标签可能指向已签提交，制品也可能由某提交构建，但这些连接不会自动产生另一份签名。交付清单应列出各对象和相应验证方法。

应用12.9为 GitEasy 的个人课程副本写发布说明，必须标明实际已执行步骤与尚未执行的线上步骤。＋

考查知识点 · 发布说明 / 实测范围 / 资源取得

发布说明包含确切提交、标签、可见变化、适用环境与运行方式，列出实际完成的构建和测试。尚未创建Release、上传附件或执行线上评审时明确说明，不能把操作计划写成已经发生的事实。

应给出确切提交或标签、主要变化、运行前提和资源入口，再说明实际检查的系统与目标。若只完成本地归档，不写成已发布线上Release；若附件未含LFS实际内容，也应列入取得说明。

应用12.10设计发布后发现错误的勘误流程，说明如何避免同名不同内容。＋

考查知识点 · 勘误 / 不可变发布 / 后续修复

先确认影响和已分发范围，保留原版本，再建立新修订与勘误说明并关联原问题。遵循不可混淆的命名策略，避免悄悄用同一标签或附件名替换内容，使使用者无法识别实际取得的版本。

对已被使用的版本保留可追溯记录，发布修复版本并说明影响和升级方法。若原内容存在严重问题，应按规则撤回或标注，但仍需避免悄悄让相同标签表示另一份源码，造成校验和与历史报告无法对应。

应用12.11比较git archive、bundle与GitHub Release附件的保存范围。若项目含导出属性、子模块或LFS指针，怎样证明一个源码压缩包能够被使用，并指出哪些资料需要另行提供。＋

考查知识点 · 源码归档 / 导出属性 / 发布附件

archive围绕指定树生成文件归档，导出属性可能影响实际输出；bundle围绕所选Git历史保存对象和引用；Release还组织发布说明与附件。子模块目标和LFS实际内容通常需要额外取得条件，不能由压缩包扩展名推断齐备。

验收应在新目录解压或克隆，逐项检查依赖和关键文件，再运行使用或构建步骤。清单明确每类资料的来源、版本和校验方法；平台讨论、未提交草稿及运行数据另行安排保存，避免把源码包写成整个系统备份。

应用12.12为一次课程项目发布设计最小可追溯清单，至少包含版本、提交、源码、构建方法、测试结果、校验值与签名验证范围。解释校验值一致、签名有效和制品能正确运行各需要怎样的检查。＋

考查知识点 · 校验清单 / 构建来源 / 签名验证

清单固定发布名称与确切提交，说明源码入口、依赖、构建目标及实际测试环境，为交付文件记录校验值。使用签名时明确被签对象、验证命令和可信身份来源，避免将一份签名泛指所有附件。

校验值一致支持文件未在比较过程中改变，签名验证支持被签内容与密钥关系，制品正确运行还依赖目标环境和业务验收。发布人员应分别记录这三层结果，并列出没有构建、没有运行或尚无独立身份确认的部分。

综合12.13校园卡v1.0.0发布后发现限额错误，已有学生下载源码和二进制，同时维护分支仍需接收修复。请设计从确认受影响版本到新版本发布的流程：保留原版本可追溯性，组织修复与回归测试、维护移植、签名及校验，并说明为何不应悄悄重写同名标签。＋

考查知识点 · 公开版本 / 勘误 / 修复发布

先固定原标签、提交和已分发制品，确认缺陷影响及必要告知范围；在适当分支提交修复与回归测试，再将需要的独立变化移植到维护线并重新验证。根据兼容性契约确定新版本名称，发布说明给出影响、修正和使用者行动。

新标签、源码和制品分别记录来源与校验，按项目约定进行签名并说明验证范围。原版本可标注问题或按规则撤回，但不让同一名称无说明地指向另一份内容，否则既有校验、报告和协作者判断都会失去稳定依据。验收从新目录取得新版本并完成核心功能检查。

发布说明先列出受影响标签、问题触发条件及可用规避办法，保留原源码和二进制的对应关系。修复应包含能够复现限额错误的回归测试，按维护范围移植并分别验证。在各目标分支形成确定提交后，按版本政策建立新标签，验证签名所用密钥身份，再从标签重新构建和生成校验材料。新说明明确修复范围与已知限制。同名标签若被悄悄移动，先前下载者和后来取得者便可能对应不同内容，追溯依据随之失去一致性。
