CHAPTER 03 · 基础篇

工作区、索引与提交

张庆科 编著约 47 分钟11 道分层习题

上章中，文件经过 add 后才成为待提交内容。由此会产生两个问题：既然 Git 知道文件已经修改，为什么还需要暂存？同一个文件为什么可能同时显示“已暂存”和“未暂存”？本章通过逐行可检查的实验回答这两个问题。

学习目标：能够分别检查工作区、索引和 HEAD 中的文件内容；预测 add 与 commit 的结果；区分三种 diff 的比较对象；读懂 status 的两列状态；把混在同一文件中的两项修改组织为两次提交；在保留工作内容的前提下撤销暂存。

建立三份状态 →\rightarrow 故意让它们不同 →\rightarrow 用 diff 检查 →\rightarrow 阅读状态两列 →\rightarrow 选择部分修改 →\rightarrow 恢复与忽略规则 →\rightarrow 独立解释命令效果。

为什么需要一份候选内容

设想修改一份课程说明：教师邮箱已经确认，需要立即修正；考核办法仍在讨论，应继续保留为草稿。如果提交直接采用所有最新编辑，两项变化就难以独立说明。索引允许先选定可以共享的内容，工作区则继续保留尚未完成的编辑。

同一路径因此可以对应三份不同状态，观察时应分别确认其来源：

  1. 工作区中的内容：当前文件系统里已经保存的内容，编辑器和普通文件命令直接操作它。

  2. 索引中的候选内容：Git为下一次提交记录的路径、模式和内容对象标识等信息，日常操作中常称为暂存区。

  3. HEAD所代表提交中的内容：当前历史位置保存的文件快照；本章实验中HEAD正常指向main的最新提交。

一次提交需要先明确内容范围。图 3.1 将HEAD快照、索引候选和工作文件并列展示，卡片中的不同值用于强调三者可以各不相同。图中的箭头表示命令更新的目标；读取或更新一份状态，并不意味着文件作为实物从一个区域搬到另一个区域。

图 3.2 给出观察顺序：先读取已有提交，再检查提交候选，最后查看当前编辑；比较它们，才能判断哪些变化已经暂存、哪些仍留在工作区。它表示核对步骤，并不表示三份内容必须依次复制，或每次都要发生变化。

三份状态也不等于磁盘上的三个普通文件夹。索引通常是二进制管理文件，其条目引用对象数据库中的内容；提交通过树对象组织路径和内容。第9、10章再讨论物理结构，本章先区分三份可观察的状态。图 3.3 将这一模型与日常操作联系起来。

其中commit是概念简图：实际提交会创建新提交对象并更新当前分支，HEAD随之解析到新提交，旧提交保持原有内容。学习时应把“产生新记录”与“改写旧记录”区分开来；后续分支和对象章节将继续说明这一关系。

主实验：让三份内容依次分开

如果工作文件、索引和最近提交恰好相同，它们容易被误认为同一份内容。下面故意在不同时间停止编辑、暂存和提交，使三者分别保留不同文本，再用查询命令证明这种差别，而非仅凭区域名称猜测。

建立相同的起点

以下实验从全新目录开始，不依赖上一章的克隆或忽略规则。请依次执行，暂时不要加入其他文件。

建立只有一行内容的基线
mkdir git-lab-03
cd git-lab-03
git init -b main
git config --local user.name "Git Learner"
git config --local user.email "learner@example.invalid"
printf 'line 1\n' > notes.txt
git add notes.txt
git commit -m "docs: record the first line"

现在工作区、索引和 HEAD 中的 notes.txt 都应只有一行。先用三种查询方式验证，而非仅凭 status 推测：

分别读取三份内容
cat notes.txt
git show :notes.txt
git show HEAD:notes.txt

cat 读取工作区文件；git show :notes.txt 读取正常索引条目所引用的内容；git show HEAD:notes.txt 读取当前提交中的内容。三条命令应分别显示 line 1。冒号用于Git的内容选择语法，应与磁盘文件名区分。

只修改工作区

增加第二行，尚不暂存
printf 'line 2\n' >> notes.txt
git status --short
git diff
git diff --cached

此时工作区有两行，索引和 HEAD 仍有一行。普通 diff 应显示新增的第二行；cached diff 没有输出，因为索引与 HEAD 还相同。没有输出只表示指定比较没有差异，不表示文件从未修改。

暂存后再次编辑

先执行 add，让索引更新为两行；再追加第三行，但不要再次 add：

故意制造三份不同的内容
git add notes.txt
printf 'line 3\n' >> notes.txt
cat notes.txt
git show :notes.txt
git show HEAD:notes.txt
git status --short

此时三个查询结果依次应有三行、两行和一行。status 短格式中 notes.txt 前通常为 MM：第一列表示索引相对 HEAD 有修改，第二列表示工作区相对索引也有修改。

这一步揭示了 add 的作用时点：它记录执行当时为指定路径选定的内容，不建立“今后这个文件每次编辑都自动暂存”的关系。第三行出现在 add 之后，因此尚未进入索引。表3.1给出本节所用的比较项目。使用时应同时核对前述适用条件。

表 3.1 同一文件在主实验各阶段的内容行数
时刻工作区索引HEAD
基线提交后111

执行 add 后221

提交并验证预测

只提交索引中已经选定的两行
git diff --cached
git commit -m "docs: record the second line"
git show HEAD:notes.txt
cat notes.txt
git status --short

新提交中的文件应只有 line 1 和 line 2；工作区仍有 line 3。提交成功不要求工作区变干净，也不表示把目录里最新的所有编辑都收走。本例第三行没有丢失，它仅继续等待你作出选择。

如果你此前意外再次执行了 add，那么第三行也会进入提交。再次暂存更新了候选，实验前提随之改变，结果应据此重新判断。请通过 show 和 diff 检查事实，必要时在新目录重做实验，不要为“对齐答案”盲目执行 hard reset。

三种 diff 分别比较什么

差异结果只有在比较两侧明确时才有意义。同一个文件同时存在几种内容，因而不同diff可能都正确却显示不同变化。本节从比较边界出发读取新增与删除，随后把结果用于提交前检查（图 3.4 ）。

先确定两端，再看输出

普通仓库里最常用的三个比较如下。此处的说明针对已经跟踪的普通文件，未跟踪文件默认不会因此显示为完整补丁。表3.2给出本节所用的比较项目。使用时应同时核对前述适用条件。

表 3.2 三种 diff 的比较对象
命令比较方向回答的问题
git diff索引到工作区哪些已保存编辑还没暂存？
git diff --cachedHEAD 到索引下一次准备提交什么变化？

在“三行、两行、一行”的阶段，普通 diff 只显示第三行；cached diff 只显示第二行；diff HEAD 显示第二、三行。三条命令都正确，仅问题不同。在提交两行之后，cached diff 应重新为空，普通 diff 仍显示第三行。图 3.6 将每条命令的旧侧、新侧与本例结果分别列出。直线箭头只标明比较方向，查询不会改变任一状态。

差异中的增删只在选定两端之间成立（图 3.5 ）。先读比较范围，再解释补丁，能够说明为何同一路径在两条diff命令下出现不同结果。

读懂一段补丁

下面是结构示意，实际对象缩写可能不同：

终端输出
diff --git a/notes.txt b/notes.txt
--- a/notes.txt
+++ b/notes.txt
@@ -1,2 +1,3 @@
 line 1
 line 2
+line 3

第一行指出比较的路径。--- 与 +++ 分别标记旧侧和新侧，不表示执行了文件删除与新增。以 @@ 包围的片段头给出旧侧与新侧的位置及行数；本例从各自第 1 行开始，旧侧 2 行，新侧 3 行。

正文开头的空格表示上下文行，减号表示旧侧移除的行，加号表示新侧增加的行。修改一行常显示为一条删除加一条新增。a/ 与 b/ 是常见输出前缀，不要求项目中真的存在 a 和 b 两个目录。

先用文件内容核对补丁，再逐步熟悉行号。如果补丁突然显示整个文件每一行都变化，应检查行尾、编码或格式化，不能立刻推断内容全部被重写。

读懂 status 的两列状态

git status 的长格式适合初学者，因为它分组说明当前情况。git status --short 便于快速查看，普通非冲突文件主要使用两列状态，记为 XY（图 3.7 ）。

  • X 比较索引与 HEAD，表示已暂存的变化。

  • Y 比较工作区与索引，表示尚未暂存的变化。

空格也是有意义的字符。为避免印刷中看不清空格，下表用下划线显示空白位置；实际输出中没有下划线。表3.3给出本节所用的比较项目。使用时应同时核对前述适用条件。

读取短格式状态时，先确定每列的比较起点，再解释字母（图 3.8 ）。两列可以同时出现修改，因为同一路径在索引和工作文件中可以保存不同内容。

合并冲突时还有其他代码，不能继续把所有状态都按上述简单比较理解；第 6 章再解释未合并索引条目。同样，重命名通常由内容相似性推断，不是提交对象永久存着一条“重命名操作”记录。为了练习两列含义，你可以在主实验当前状态下依次运行三种 diff，再对照 status。状态字母是比较结论的摘要，diff 才进一步展示比较内容。

部分暂存：一次只提交一个意图

一次编辑可以同时完成多项任务，但它们不一定适合进入同一次提交。部分暂存让候选范围按意图组织；选择以后仍需核对上下文和依赖，确保每次形成的版本能够独立解释，并满足相应检查。

同一个文件中的两项修改可以分属不同的提交意图。图 3.9 中，标题修改已进入索引，邮箱修改仍留在工作文件，因而提交候选与当前磁盘文件并不相同。部分暂存完成后，应检查并验证索引所构成的候选，避免只测试工作目录而遗漏候选中的依赖。

建立两个互不相邻的修改

先把主实验剩余的第三行提交，恢复明确起点，然后创建一个具有足够间隔的文本：

准备部分暂存实验的基线文件
git add notes.txt
git commit -m "docs: record the third line"
printf 'title: Git course\n\nsection one\n\nalpha\nbeta\ngamma\ndelta\nepsilon\nzeta\n\ncontact: old@example.invalid\n' > course.txt
git add course.txt
git commit -m "docs: add course outline"

用编辑器修改 course.txt：把第一行的 Git course 改为 Git practice，把末行邮箱中的 old 改为 new。保留中间内容。这样得到两项可以独立理解的修改：标题变化和联系方式变化。

逐块选择候选修改
git diff -- course.txt
git add -p -- course.txt

-p 进入交互式补丁选择。Git 逐块询问是否暂存当前块；y 表示选择，n 表示暂不选择，q 表示退出并保留已作出的选择。若两项修改仍显示在同一块中，可以尝试 s 拆分；并不是任意一块都能拆分，提示符会列出当前可用动作。本例选择标题修改，暂不选择邮箱修改。不要仅凭按过 y 就认定选择正确，应检查两份差异：

确认候选内容与剩余内容
git diff --cached -- course.txt
git diff -- course.txt

cached diff 应只包含标题变化，普通 diff 应只包含邮箱变化。确认之后提交标题，再将剩余编辑单独暂存并提交。最终有两次提交，每次表达一个意图。

部分暂存允许索引保存一份与当前完整工作文件不同的候选内容。这正是索引存在的教学价值。但也引出一个工程问题：你在工作区运行的测试，未必验证了索引中那一份组合。涉及程序行为时，应确认候选提交自身能够通过测试，不能只检查所有未提交变化叠加后的状态。

取消暂存与恢复工作文件

“不想提交这部分内容”与“不想保留这次编辑”表达不同目标。前者通常改变候选选择，后者改变工作文件。下面始终说明来源和目标，使读者在保留最新编辑的前提下选择动作（图 3.10 ）。

只取消候选选择，保留工作文件

假设你已经 add 了 notes.txt，随后决定稍后再提交。可以执行：

撤销暂存，保留已保存编辑
git restore --staged -- notes.txt
git status --short
git diff -- notes.txt

在本章已经有 HEAD 的前提下，--staged 指定更新索引，未显式指定来源时从 HEAD 恢复候选状态。工作区内容保持不变。它解决的是“这次先不提交”，不是“把文件改回去”。-- 分隔选项与路径，使路径含义更明确。

如果文件内容没有变化，这条命令可能看不出明显结果。请先制造一项小修改并暂存，再观察操作前后的 cached diff 和普通 diff：前者消失，后者保留，才构成完整验证。

恢复命令需要明确来源和目标（图 3.11 ）。两类操作可能针对同一个路径，却改变不同层次；应通过候选差异与未暂存差异分别验证，避免把一个空输出当作全部内容已恢复。

丢弃工作区编辑必须先确定保留目标

git restore -- notes.txt 默认从索引恢复指定工作文件，会丢弃该文件相对索引的未暂存编辑。与前一小节仅多或少一个选项，影响对象却不同。学习时先用只读命令保存和检查差异，必要时把文件复制到仓库外。表3.4给出本节所用的比较项目。使用时应同时核对前述适用条件。

表 3.4 restore 的两个常见目标；本表假设已有 HEAD
动作默认来源与目标工作编辑是否保留
restore --staged -- 路径HEAD 到索引工作文件保留
restore -- 路径索引到工作区相对索引的编辑会被覆盖

不要把“Git 有历史”理解成“任何未提交编辑都能找回”。如果某段内容从未写入对象数据库，也没有外部备份，reflog 不会凭空生成它。第 8 章会将撤销与恢复放在完整状态矩阵中讨论。

忽略、删除与停止跟踪

一个路径可以存在于磁盘、被索引跟踪，或者已经出现在历史中，这些条件不能合并为一个“有或没有”。忽略规则影响发现未跟踪文件，删除和停止跟踪则作用于其他范围；本节依次对照这些效果（图 3.12 ）。

忽略规则不会改写既有跟踪事实

在本章仓库中创建并提交一份小型本地说明，再把它加入忽略规则：

验证已跟踪文件仍会报告修改
printf 'mode=study\n' > local.conf
git add local.conf
git commit -m "chore: add a study configuration"
printf 'local.conf\n' > .gitignore
printf 'mode=practice\n' > local.conf
git status --short
git ls-files -- local.conf

虽然 .gitignore 中已经列出 local.conf，status 仍应报告这个已跟踪文件发生变化，ls-files 仍列出路径。忽略规则主要处理尚未跟踪的路径，并不自动移除索引条目。

若这个文件确实只应保留在本机，可以使用 git rm --cached -- local.conf 从索引停止跟踪，同时保留工作文件；随后提交这个删除与忽略规则。这里的“删除”指下一份快照不再包含该路径，不会抹掉旧提交中的文件。请先查看 cached diff，确认这正是你的意图，再提交。

工作文件删除也需要记录

通过文件管理器删除一个已跟踪文件，只改变工作区，索引和历史仍可能包含它。要让下一次提交记录删除，可以用 git add -u -- 路径 暂存相关删除；也可用 git rm -- 路径 同时处理工作文件与索引。二者前提和影响不同，操作前先确认需要保留的内容。

重命名同理：可以在文件系统中改名，再暂存新旧路径，也可以用 git mv。之后通过 status 和 diff 阅读 Git 对变化的判断。不要把 mv 理解成将一条不可更改的重命名事件写入历史；历史首先保存各次快照。

索引到底保存了什么

只读观察索引条目
git ls-files --stage

正常条目会包含文件模式、对象标识、stage 编号和路径。这里的对象标识关联候选文件内容；它不是当前提交的标识。正常情况下 stage 为 0；发生合并冲突时，同一路径可能暂时有其他阶段条目。

所以，“索引保存完整快照”是一种便于理解的逻辑描述：它足以描述下一次提交的候选树，而非只记下一份行差异。物理上，条目引用对象内容，并附有用于判断文件变化的元数据。不能据此说整个文件正文都直接存放在 .git/index 中。

索引保存构造候选树所需的信息，不能把它理解为只有文件名的一张清单（图 3.13 ）。模式、对象标识和阶段共同限定条目的含义，查询时应结合各字段阅读。

这一区分帮助我们同时理解两件事：为什么部分暂存可以形成与工作区不同的候选版本，以及为什么提交不需要重新询问编辑器究竟改了哪些行。Git 已经能够从索引构建候选树。

实验拓展：把一个修改拆成两个可解释的提交

同一次编辑可能包含可以独立评审的变化。本实验把选择、检查和提交按意图组织，要求每一步说明候选范围，而非按文件数量机械拆分。

任务背景与提交边界

课程说明中既有实验地点，又有参考资料链接。地点调整与链接纠错属于两个独立决定：前者需要通知学生，后者只修正阅读入口。如果将二者合为一项提交，日后只撤销地点调整时就必须重新筛选内容。索引使我们可以在一次编辑之后，按任务意图组织提交。

本实验采用两个文件，先让提交边界变得直观；掌握后再迁移到同一文件中的部分暂存。所有步骤在新建的 split03 中完成。首次提交建立基线，后两次提交分别记录地点与链接的变化。

第二次编辑不会自动更新索引（图 3.14 ）。只有再次选择相应内容，候选才与第三版工作文件一致；这个过程也解释了为何提交之前必须重新核对候选。

建立具有两个独立任务的基线
mkdir split03
cd split03
git init -b main
git config user.name "Git Learner"
git config user.email "learner@example.invalid"
printf 'Room: A101\n' > room.txt
printf 'Guide: https://example.invalid/old\n' > links.txt
git add room.txt links.txt
git commit -m "docs: establish course information"
printf 'Room: B202\n' > room.txt
printf 'Guide: https://example.invalid/guide\n' > links.txt
git diff --stat
git add room.txt
git diff --cached --name-only
git diff --name-only

此时已暂存差异应只包含 room.txt，未暂存差异应只包含 links.txt。判断应以索引当前选择的内容为依据；编辑发生的先后不能直接说明候选范围。若输出同时出现两个文件，应停止提交，先核对暂存范围。

分别提交，并核对各自的变化
git commit -m "docs: move the course to room B202"
git diff HEAD^ HEAD --name-only
git add links.txt
git commit -m "docs: correct the reading guide link"
git log -3 --oneline
git diff HEAD^ HEAD --name-only
test -z "$(git status --porcelain)"
test "$(git rev-list --count HEAD)" = 3

最后的历史应有三个提交。第一项是基线，第二项只改变地点，第三项只改变链接。可以用每项提交与其父提交的比较证明边界，而不能仅凭提交说明作判断。说明写得准确，仍可能因误暂存而包含额外内容。

文本、编码与换行的背景

文本差异来自字节内容及其解释规则，跨系统时编码和换行也会参与比较。先理解这些背景，再使用属性与规范化工具，才能判断变化是业务修改还是表现差异。

文件看起来相同，为何仍有差异

文本编辑器展示的是字符和布局，Git 比较的是经过相关属性处理后的内容。行尾方式、文件末尾换行、制表符与空格、字符编码，都可能造成肉眼不容易察觉的差异。出现整篇文件被重写的补丁时，应先检查这些因素，再判断是否发生了大规模语义修改。

LF 和 CRLF 是两种常见行尾形式。跨平台项目可以通过属性规则约定仓库中的规范化方式，但规则需要与现有文件状态共同考虑。不能在不检查差异的情况下直接进行全仓库转换，否则格式调整会混入功能修改，削弱后续检索与评审的效果。第 14 章将进一步讨论仓库属性。

二进制文件也可以跟踪，但可读性不同

Git 能保存许多类型的文件，并不只限于程序源码。然而，对图像、压缩包或办公文档，文本补丁通常不能直接展示语义变化。即使文件成功提交，评审者仍可能需要专用比较工具或导出的预览资料。

因此，选择资料格式时应同时考虑编辑需求和协作可读性。例如正文采用可审阅的文本源文件，图片保留可编辑源与导出结果，并在提交说明中交代两者的对应关系。版本控制的存储能力与人能否理解变化，是两个不同的问题。

状态分析：删除、忽略与停止跟踪

磁盘存在、索引跟踪与历史保存是独立条件。下面对照三个常见动作，说明新快照、当前文件和旧提交分别如何变化，避免将它们统称为删除。

删除文件是一项可以记录的变化

已经跟踪的文件从工作区消失后，Git 可以把删除作为差异展示。若确实需要从下一版中移除，应将删除纳入索引并提交；若仅误删，应从明确来源恢复。看到删除状态就立即恢复，或看到文件不存在就认定历史丢失，都忽略了工作区与提交快照之间的区别。

忽略规则作用于候选发现

忽略规则主要减少未跟踪文件进入日常候选的干扰。它不删除已提交历史，也不会自动停止跟踪既有文件。假设 local.conf 已经入库，后来写入忽略规则，旧版本和当前索引仍可能包含它。只有明确改变跟踪状态并提交，后续版本才会体现这种选择。

忽略规则主要控制未跟踪路径的常规发现行为（图 3.15 ）。对已经跟踪的路径，停止跟踪需要另行调整索引；新增规则不会把旧提交中的内容清除。

如果该文件曾含有效凭据，停止跟踪也不足以完成事故处置。应先撤销或轮换凭据，再评估传播范围与历史清理。第 15 章将展开处理流程。本章需要掌握的是：文件发现规则、当前版本内容与历史中已有内容，分别属于不同层次。

迁移练习：设计一项能够独立撤销的提交

请为课程项目设计三项修改：调整时间、修正文句、增加一份参考资料。说明哪些修改应合并，哪些应拆分，并用补丁验证提交范围。允许不同答案，但每个边界都应能够由同一目的解释。

参考分析：时间调整与相应通知文档可能应共同提交，因为两者必须保持一致；无关文句修正可独立提交；新增参考资料若仅支持时间调整的附件，则还需考虑其依赖关系。合理边界使每项提交形成可理解、评审和验证的完整变化，具体行数取决于任务及其依赖。

跨平台文本协作：从字节差异到属性约定

为什么同一行文字会产生不同补丁

文本行的结束方式并不总是相同。某些环境使用 LF，另一些环境常见 CRLF；编辑器还可能自动改变文件末尾换行或缩进。这些变化未必改变读者看到的文字，却会影响补丁规模。若一次功能修改同时重排了全部行尾，评审者就更难找出真正的业务变化。

跨系统协作应为文本与二进制类型建立明确约定，使不同系统的成员能够依据同一规则处理文件。Git 属性规则可以随仓库分发，使新成员取得同一套项目规则。个人配置仍可能影响行为，因此诊断时应查询实际属性，而非只凭全局配置作推断。属性语义和模式匹配细节可参阅官方手册(Git Project 2026a)。

规则的对象是路径，而非文件扩展名的直觉

.gitattributes 使用路径模式指定属性。扩展名仅组织规则的一种常见依据，并不能保证文件内容一定属于某种类型。项目可以为文本设置规范化要求，为确认为二进制的路径禁用文本转换，也可配置专用差异或合并驱动。外部驱动若需要额外程序，必须写明安装与信任前提。

引入属性时，应先审查项目中实际有哪些文件，再决定匹配范围。把所有未知文件强行当成文本可能损坏不适合转换的内容；把所有文件都当成二进制则会失去有用的文本差异。规则应来自项目需求，而非复制一个很长但无人理解的配置文件。

独立实验：观察规范化后的索引内容

下例使用 Python 明确写出 CRLF 字节，避免编辑器设置干扰。规则要求 *.txt 以文本方式处理，并在检出时使用 LF。暂存以后，我们直接从索引读取内容，检查规范化结果。

创建属性规则与具有CRLF行尾的输入
mkdir attributes03
cd attributes03
git init -b main
git config user.name "Git Learner"
git config user.email "learner@example.invalid"
printf '*.txt text eol=lf\n' > .gitattributes
python3 - <<'PY'
from pathlib import Path
Path('note.txt').write_bytes(b'alpha\r\nbeta\r\n')
PY
git check-attr text eol -- note.txt
git add .gitattributes note.txt
python3 - <<'PY'
import subprocess
staged = subprocess.run(['git','show',':note.txt'],capture_output=True,check=True).stdout
assert staged == b'alpha\nbeta\n'
PY
git commit -m "chore: define the text normalization rule"

本例证明的是索引中的候选内容符合规则，不要求工作文件在暂存动作后立即被重写。暂存可以规范化写入的内容，而原工作文件可能仍保持已有字节。若读者只检查编辑器状态，可能误判规则没有生效；若只检查提交结果，也可能忽略工作区中仍需处理的差异。

属性描述路径内容的处理约定，文件字节描述当前实际输入（图 3.16 ）。改变规则后需要审查规范化结果，不能假定已有索引和历史已自动整体改写。

既有仓库的规范化应单独审阅

对已经跟踪的内容引入新规则时，可先在独立分支评估，再使用重新规范化暂存的方式形成明确补丁。提交前应检查文件范围、二进制识别和实际变化。不要把整仓库规范化混入一个无关功能提交，否则后续历史查询会受到大量格式差异干扰。

修改内容后重新检查候选与空白问题
printf 'alpha\nbeta\ngamma\n' > note.txt
git add --renormalize .
git diff --cached --check
git diff --cached --stat
git commit -m "docs: extend the normalized note"
test -z "$(git status --porcelain)"

--renormalize 重新处理已跟踪内容，不应误解为自动发现全部未跟踪文件。diff --check 可以检测一部分空白问题和冲突标记等异常，但不验证中文术语、链接正确性或程序语义。项目仍需要与内容类型相匹配的其他检查。

文件名、大小写与编码的协作约束

不同文件系统对大小写的处理可能不同。仅以大小写区分的两个路径，在某些系统上难以同时检出；只改变文件名大小写，也可能需要通过临时名称完成明确重命名。跨平台项目应避免依赖这种歧义，并在命名规范中统一大小写和分隔方式。

中文文件名可提高教材资源的可读性，但脚本必须正确处理空格、引号和编码。终端显示转义序列不一定意味着路径损坏；应区分展示设置与实际存储。自动处理路径列表时，宜采用命令支持的零字节分隔形式，避免把换行或空格当作所有路径的可靠边界。

本节迁移任务是为自己的课程资料设计最小属性规则，并解释每条规则适用哪些路径。验收时检查一个新克隆，而非只在原作者目录中观察效果。只有新环境也能按文档得到一致结果，规则才具备协作价值。

忽略规则：从项目习惯到可验证模式

先区分共享规则与个人例外

项目产生的构建目录、临时日志和中间结果，往往需要所有协作者共同忽略，适合写入版本化的 .gitignore。某位成员自己的编辑器缓存或本地试验文件，则可能更适合使用本地排除机制。选择位置的依据是规则是否属于项目共同约定，而非哪个文件更容易找到。

规则只影响相关未跟踪内容的发现和选择，不会抹去历史。对已经跟踪的文件，即使后来匹配忽略规则，仍应按正常差异审阅。若文件不应继续出现在后续版本，应另行改变跟踪状态，并说明是否仍需保留本地内容。

目录规则、通配符与反向规则

忽略模式并不等同于终端的任意路径展开。根目录锚定、目录结尾斜杠、通配符和反向规则各有含义。多级规则还会受位置与优先关系影响，应使用实际路径验证。特别是父目录已经被排除时，不能简单依靠对子路径的一条反向规则取得预期效果(Git Project 2026b)。

一个常见需求是忽略输出目录里的全部生成物，却保留一份手写说明。与其猜测复杂模式，不如先明确目录本身是否允许遍历，再排除其内容并保留说明。下面的独立实验采用这种组织方式。

保留输出说明，忽略生成结果
mkdir ignore03
cd ignore03
git init -b main
git config user.name "Git Learner"
git config user.email "learner@example.invalid"
mkdir build
cat > .gitignore <<'EOF'
/build/*
!/build/README.md
*.tmp
EOF
printf '# Build output directory\n' > build/README.md
printf 'generated data\n' > build/result.bin
printf 'temporary notes\n' > scratch.tmp
git check-ignore -v build/result.bin scratch.tmp
if git check-ignore -q build/README.md; then exit 1; fi
git status --short --untracked-files=all

check-ignore -v 帮助定位命中的规则来源和行号，适合解释“为什么这个文件没有出现”。对保留文件的查询则应不再报告被忽略。读者应同时检查发现列表，确保规则没有无意排除需要提交的资料。

形成明确的资料版本并核对跟踪范围
git add .gitignore build/README.md
git commit -m "chore: document and filter generated output"
git ls-files
test "$(git ls-files | wc -l | tr -d ' ')" = 2
test -z "$(git status --porcelain)"
test -f build/result.bin

状态干净时，生成结果仍可以存在于磁盘。由此可见，干净状态不能解释为“目录里只有 Git 保存的文件”。同样，忽略规则也不是删除规则；实际清理工作应另行确认范围，不能直接把所有被忽略内容都当作可丢弃资料。

同样从下一次快照中移除一个路径，可以对应不同的工作现场结果（图 3.17 ）。操作前应确认是否还要在磁盘保留该文件，完成后分别检查候选和工作目录。

为什么不宜随手强制加入文件

强制暂存可以突破普通忽略选择，但应有明确理由。例如确需跟踪一个示例文件，而现有规则过宽，可能应该修正规则，而非让每位成员反复使用强制选项。否则项目规则与实际行为长期不一致，会增加新成员困惑。

如果文件属于凭据、个人设置或不可公开数据，强制加入更不是解决“看不到文件”的方法。应先判断文件性质，再选择合适保存位置。技术上能加入，不能推出项目上应该加入。

规则审阅与迁移任务

请为一个包含源资料、临时图像和构建产物的课程仓库编写最小规则，并提供三个正例与三个反例。每个例子说明文件是否应被跟踪，以及实际查询是否符合判断。规则变化应单独审阅，特别留意宽泛通配符是否误排除新教材材料。

验收时从新克隆开始生成一份输出，确认共享规则仍然有效；再检查本地个人例外是否需要另行配置。共享规则和个人环境分别验证，才能形成可交接的项目约定。

本章小结

本章用三行文本把三个状态分开：工作区是已保存编辑，索引是下一次提交的候选，HEAD 对应当前已提交快照。add 更新选择，commit 根据选择创建历史；同一文件出现两个 M，是两次比较都发现差异。

遇到状态问题时，先确定自己问的是哪两个对象之间的关系，再选择 diff。遇到撤销问题时，先确定想改变索引还是工作文件。部分暂存则把“提交一个完整意图”变成可以检查的具体动作。接下来阅读提交历史和分支时，仍要保留这套状态边界。

本章习题与解析

先独立作答，再展开解析核对思路。答案与教材同源，知识点随题列出。

应用3.1在三份内容分别为 3、2、1 行时，预测三种 diff 的新增行。执行验证后，说明每条命令为何得到该结果。＋

考查知识点 · 三份内容 / 三种diff / 比较方向

普通diff比较索引的2行与工作区的3行，只显示第三行新增；cached比较HEAD的1行与索引2行，显示第二行新增；diff HEAD比较HEAD与工作区，显示第二、三行。说明两侧比背诵输出更关键。

应先写出每条命令的左右两端，再标明相对增加的行。若把查询方向对换，同一行可能由新增变成删除。答案中的行数必须对应实际保存的字节；不同换行设置造成的显示差异应单独解释。

应用3.2执行 add 后又删除了工作文件。索引和 HEAD 会自动删除该路径吗？在新实验文件上验证，并列出至少两个只读证据。＋

考查知识点 · 工作文件删除 / 索引条目 / 提交树

删除工作文件不自动重写索引和HEAD。可用git show :路径读取暂存内容，用git show HEAD:路径读取历史内容，再用status或普通diff观察工作区删除。是否提交删除取决于之后选择的候选。

在未重新暂存之前，候选仍引用原blob。读取索引与历史路径可以证明记录尚在；普通diff则显示工作区缺少该路径。只有后续把删除选择到候选并提交，新快照才表达这一删除决定。

应用3.3构造状态 MM，并解释两个 M 分别比较什么。若第一次修改在文件首部、第二次修改在末尾，是否仍可能是 MM？＋

考查知识点 · 短状态两列 / 候选差异 / 工作区差异

短状态第一列比较HEAD与索引，第二列比较索引与工作区。两列都是M表示两次比较均有修改，与两次编辑是否位于同一行无关。首部和末尾分别修改也可以形成MM。

两列反映两次独立比较，不能依据字符重复推断同一修改被保存了两次。应分别读取cached diff和普通diff，确认每组变化的位置与内容，再解释当前提交实际会采用哪一组结果。

应用3.4用 add -p 将一个文件中的两项修改分成两次提交。提交每次 cached diff 的检查记录，说明为何这是两个独立意图。＋

考查知识点 · 部分暂存 / 提交粒度 / 依赖关系

先用add -p选择第一项变化，检查cached只含该意图，再提交；重复选择第二项。两个提交应能分别说明目的与影响；若其中一项依赖另一项才能工作，拆分时需重新设计顺序或保持必要上下文。

检查每个提交是否能单独说明目的，并尽量保持必要功能的一致性。若函数签名和调用方必须同时修改，强行拆开可能产生不可构建的中间版本；合理的粒度由任务依赖决定，不能简单按文件数或行数评判。

应用3.5同学希望“取消暂存但保留最新编辑”，却使用 restore 而没有 –staged。解释影响对象的区别，并说明为什么不能承诺恢复全部丢失编辑。＋

考查知识点 · restore来源 / 写入目标 / 编辑保全

restore默认通常写工作区，restore --staged写索引。取消暂存应明确目标索引；误覆盖且从未被add、提交、stash或其他工具保存的编辑，Git未必有恢复来源，因此不能承诺全部找回。

不带source时仍需理解默认来源：仅恢复工作区通常取索引，恢复索引通常取HEAD。执行前先保存尚需保留的编辑，执行后分别读取索引与磁盘，确认目标层发生预期变化，另一层的内容按要求保留。

应用3.6验证 .gitignore 不会自动停止跟踪已有文件。若改用 rm –cached，工作文件和历史文件分别会怎样？＋

考查知识点 · 忽略 / 停止跟踪 / 历史保留

先跟踪文件，再增加忽略规则，修改后仍会出现受跟踪变化。rm --cached通常从索引移除路径，保留磁盘文件；提交后新快照不再包含该路径，旧提交中的版本仍存在。还要检查命令的保护条件。

可在后续提交中确认路径已经从新树消失，同时用旧提交路径读取原内容。这样能证明停止跟踪影响新候选和后续快照，而旧记录仍由历史关系提供。涉及敏感文件时，停止跟踪也不能替代凭据失效和传播处理。

基础3.7解释“索引逻辑上能描述完整候选快照”与“索引条目引用对象内容”为什么不矛盾。＋

考查知识点 · 索引条目 / blob / 候选树

索引条目包含路径、模式与内容对象标识等信息，条目总体可以描述候选快照；内容无需全嵌在索引文件里。逻辑完整性描述可确定的项目状态，条目引用描述这种状态如何表达。

使用ls-files --stage读取路径、模式与对象标识，再用cat-file读取相应blob。两步组合说明索引通过引用组织内容。工作文件的时间信息可用于加速检查，但对候选内容的解释仍需回到对象和条目。

应用3.8你只测试了工作区中的完整程序，然后部分暂存一半修改。为什么不能据此认定候选提交一定通过测试？给出一个可能失败的例子。＋

考查知识点 · 候选检查 / 接口一致性 / 独立构建

部分暂存可能拆开接口与调用。例如工作区同时修改函数签名和调用方，测试通过；只暂存函数签名后，候选仍使用旧调用，构建可能失败。应检出并验证候选快照，而不是把工作区结果直接移用。

一个有效反例应同时展示工作区构建通过，以及由索引物化出的目录构建失败。随后重新暂存缺失的依赖修改并复测。只展示错误输出而未确认输入来自索引，不能证明问题由部分暂存引起。

应用3.9为跨Windows与Linux的文本项目设计.gitattributes规则，并说明首次引入规则后怎样检查已有受跟踪文件。区分属性匹配、工作文件字节与候选规范化结果，列出避免无关二进制变动的方法。＋

考查知识点 · 文本属性 / 换行规范 / 规范化候选

先按文件类型确定规则，对文本约定规范化策略，对图片等二进制资源排除文本处理；使用check-attr查看指定路径的有效属性，再比较实际候选。新增规则不会凭空重写全部旧对象，应在受控范围检查renormalize等操作形成的差异。

验收需要读取候选内容并核对换行、路径和文件类型，确认变化符合约定且不夹带无关编辑。规范化提交宜与功能修改分开，便于评审和追溯；两个系统上的工作区表现可能不同，比较时仍应明确来源层次。

应用3.10项目中同时有未跟踪文件、已跟踪后被忽略的文件和被删除的受跟踪文件。请预测各自的状态与候选变化，说明路径参数、忽略查询及候选差异如何配合；不得通过一次无范围的add代替分析。＋

考查知识点 · 路径范围 / 忽略规则 / 增删状态

未跟踪文件尚未进入候选，是否显示还受忽略规则影响；已跟踪文件继续参与内容比较，即使新增忽略模式也不会自动停止跟踪；受跟踪文件的工作区删除需要按意图选择到候选。三者起始条件不同，应逐条记录路径与状态。

先用status和check-ignore识别条件，再以明确路径准备变化，最后查看cached diff确认拟提交结果。若希望保留磁盘文件而停止后续跟踪，需理解仅索引移除的范围，并检查旧历史仍可访问。答案应解释每个路径最终处于哪一层。

综合3.11校园卡项目同时修改接口、调用方、README和换行规则。工作区测试通过，但只允许先交付接口修复。请组织自足的候选提交，保留其余编辑，证明候选可独立构建；再说明怎样处理规范化差异，并给出一次错误拆分及其修正过程。＋

考查知识点 · 部分提交 / 属性规则 / 候选独立验证

先识别接口与调用方的必要依赖，把构成完整修复的路径或片段共同纳入候选；README草稿与无关规范化变化继续保留在工作区或单独安排。使用部分暂存后读取cached diff，确认候选具有独立说明和必要上下文，再将索引内容物化到新目录构建测试。

可故意只暂存新接口、遗漏调用方，观察工作区通过而候选失败；补入必要修改后重新验证。换行规则先查询属性，再单独审查规范化结果，避免将大量文本变化夹在功能修复中。提交材料应包含两个输入来源、前后测试、候选清单和未交付编辑的保留位置。

可以先建立保护入口并保全全部编辑，再逐块选择接口修复及其必要调用方和测试。将索引构造的树导出到独立目录进行构建，不能仅在原工作区执行测试。错误拆分可故意只选择接口声明而遗漏调用调整，记录独立构建失败，再补入依赖并重新验证。换行规范化另作清晰变化，检查属性来源和候选差异，避免大面积字节变化掩盖功能修复。完成后确认其余编辑仍在原现场。
