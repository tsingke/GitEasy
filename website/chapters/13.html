CHAPTER 13 · 实践篇

团队工作流与代码评审

张庆科 编著约 40 分钟13 道分层习题

两个人能够交换提交，还不等于团队已经形成稳定协作。谁能修改主线，什么时候请求评审，怎样决定合入与发布，出错后按什么单位回退，都需要共同约定。本章从一次课程资料改动出发，解释工作流如何连接需求、历史和责任。

学习目标：能按发布与权限需求选择工作流；能区分 fork、分支和 PR；能写出便于验证的变更说明与评审意见；能通过同一实例比较三种合入结果；能识别平台规则的覆盖范围，并形成可交接的协作约定。

协作约束 →\rightarrow 工作流选择 →\rightarrow fork 与贡献方向 →\rightarrow 需求和 PR →\rightarrow 评审与修订 →\rightarrow 合入对照实验 →\rightarrow 规则与交接。

工作流中的角色、分支与交付

同样叫 main 和 feature 的两个项目，可能有完全不同的协作规则：一个允许直接推主线，另一个要求审批；一个每次合入立即部署，另一个每学期发布固定资料包。只复制分支命名，不能复制这些约束。

设计工作流先回答四个问题：成果多久交付一次；是否同时维护多个已发布版本；贡献者是否共享写权限；每项变化由谁验证和批准。再决定分支寿命、整合方式、评审前提和回退单位。

Git 的分支、提交与合并提供机制，托管平台提供评审、权限与检查记录，团队约定将它们连起来。即使不用平台，也可以用邮件和文本记录完成评审；即使开了 PR，也不代表需求与验证已自动清楚。

集中式协作

集中式协作通常让团队围绕一个共同远端交换成果。小组可以使用很少的长期分支，通过短任务分支或有约定的主线提交完成工作。它容易开始，但仍需要处理非快进拒绝、冲突与质量规则。

这里的“集中”描述交换与组织方式，不改变 Git 每个克隆可以本地提交的分布式机制。共同远端是协作约定的中心，不能因此推断本机所有编辑都实时存在于中心。

GitHub Flow 与短任务分支

GitHub Flow 以短任务分支和评审整合组织变化(GitHub 2026b)。可以把它理解为：从合适基线开始一项任务，持续提交并请求反馈，完成必要验证后合入主线，再按项目规则发布或部署。资料、政策和文档项目也可以采用这类流程。图13.1用任务状态画出基本闭环，箭头表示流程，不是对象父引用。流程顺畅依赖小范围需求、及时评审与可靠检查，而非依赖分支名字必须叫 feature。

Git Flow 与并行版本维护

Git Flow 设计较明确的长期开发线和发布维护分支，适合讨论“新功能继续开发，当前版本准备发布，旧版还需修复”的场景(Driessen 2010)。它为不同阶段命名，但也增加跨线同步与分支维护成本。图13.2只表示职责关系，不是要求所有项目照搬全部分支。发布修复进入维护线后，往往还要确认主开发线是否需要相同修复；若只处理一侧，缺陷可能在后续版本再次出现。

主干开发

主干开发强调短周期集成，避免长期隔离的主题逐渐偏离共同基线。它可以使用很短的分支与评审，并不等于所有人不经检查直接修改主线。未完成的功能可能借助配置、分阶段实现或功能开关控制可见性。

它对自动检查、变化拆分和快速修复提出要求。仅要求“每天合并一次”，却没有能力验证小变化，可能把长期分支风险转成主线不稳定。工作流应和团队的验证能力一起设计。

不要为每个职责都创建永久分支。分支越多，需解释的同步关系也越多。相反，也不要把“保持简单”作为忽略旧版本维护责任的理由。好的约定应让新成员能回答改哪里、如何验证、谁来合入以及如何发布（图 13.3 ）。

fork、远端与 PR 是不同层次

fork 通常是托管平台为贡献协作建立的仓库关系，每个 fork 仍是一个仓库。branch 是仓库内指向提交的引用；PR 是平台上讨论某个来源向某个目标整合的请求。它们不是同一种对象，也不能用一个名称替代另外两个（图 13.4 ）。

对 GitEasy 的个人贡献路线，作者仓库为 https://github.com/tsingke/GitEasy。在自己的账户创建 fork 后，本地 origin 通常指个人副本，upstream 通常指作者仓库。这两个别名可以改名，实际权限来自账户、凭据与服务端规则。

从作者仓库直接 clone 得到读取副本，不自动取得推送权限。学习者应先确认自己准备向哪个仓库写入。课程模拟可以完全在个人课程副本内完成，不需要把每次练习请求都发送给作者。

创建请求前核对三项方向

第一项是目标仓库和目标分支，决定变化准备进入哪里；第二项是来源仓库和来源分支，决定比较哪一组提交；第三项是基线与同步状态，决定当前差异是否仍符合任务范围。

选错目标可能把课程练习送到不相关项目，选错来源可能夹入其他任务。创建前先在本地查看提交范围和文件差异，再在页面核对。页面按钮位置会变化，仓库和分支方向的含义保持可解释。

如果来源分支在评审期间继续前进，PR 的候选内容也会改变。原先通过的检查和评审是否仍适用，要按平台与团队规则判断；不能将“曾经有人批准过”理解为任何后续版本都已获批准。

把需求写成可检验的变化

以 GitEasy 新增一份索引观察实验为例，笼统需求“完善实验内容”缺少边界。更好的需求是：“让零基础读者观察 add 后再次编辑的三份内容，包含操作、预期结果和自检；从新目录按步骤可以复现。”（图 13.6 ）

一项团队任务需要从需求逐步落实到可检查的差异。图 13.5 将问题说明、主题分支、评审和检查连接起来，使每次合入能够回到明确的验收依据。图中的卡片是协作过程示意，真实平台页面在第16章另行展示。

这项需求限定学习目标与验收。作者可以据此决定哪些文件必要，评审者也能判断是否遗漏。顺便统一全书标点、重排所有目录或更换配色，会扩大范围，应该独立安排，而不夹入本项内容实验。

变更说明的一个教学情境

下面是尚未提交到平台的说明示例，不代表作者仓库已有对应 PR。标题可写“补充暂存后继续编辑的观察实验”。正文先说明读者目前难以区分工作区与索引，再说明新增步骤与输出判读，最后写明实际验证环境、起点和限制。

验证部分应具体，例如“在空目录运行，第一次 add 后继续编辑；普通 diff 显示后续编辑，cached diff 显示首次候选；提交后历史只含已暂存内容”。若只验证 macOS，应如实写出 Windows 尚未实测，而不使用泛称“全平台通过”。这种说明让评审者能从问题理解变化，再从步骤核对结果。只写“优化体验”“完善逻辑”“修复若干问题”，无法提供同等判断依据。

评审关注内容、证据与可维护性

评审既可以审程序，也可以审教材。优先检查需求是否实现、关键假设是否成立、失败如何处理、后来的人能否维护。措辞和格式有价值，但不应让无关偏好遮住真实错误（图 13.7 ）。

一条可执行意见包含位置、具体问题、影响和建议。例如：“步骤三没有说明当前目录。初学者可能在上一实验的仓库中执行 init。请在步骤前增加新目录说明，并从空目录复验。”它比“这里再详细一点”更容易落实。

讨论意见与阻断问题分别表达

如果是可选建议，注明它不阻断本次交付；如果是错误命令或缺少验证，说明为什么必须先修复。作者可以接受建议，也可以用证据解释另一种做法。讨论应围绕项目目标，避免把个人偏好写成普遍规则。

教学情境中的一次来回可以是：评审发现作者用工作区检查给索引候选背书；作者补上 --index 模式与部分暂存反例；评审从新目录复跑，确认错误候选确实被拒绝，再批准。批准依据是修订后的证据，不是作者回复“已改”。

修订以后重新确认什么

检查新的提交范围是否仍只包含本项任务，原先反馈是否被实际处理，新增改动是否需要重新运行实验。若整理了历史，旧评论的行位置可能变化，应提供新标识或更新说明；不要只用“历史已清理”掩盖实际内容变动。

维护者合入前再核对目标分支、当前主线、检查结果与尚未解决的讨论。多个 PR 分别通过不意味着组合后必然正确，尤其当它们影响相同接口或目录结构时，需要整合状态的验证。

完整实验：同一变化的三种合入历史

最终文件树相同，提交关系仍可以不同。本实验在一个新仓库中从相同主线和主题分别建立三个结果分支，比较 merge commit、squash 与本地 rebase 的性质。它展示 Git 机制，不声称逐字复制平台全部实现（图 13.9 ）。

合入方式影响提交父关系以及后续查询的入口。图 13.8 固定同一个分叉起点，对比保留双亲连接、压缩形成单个新提交和重放形成新父链三种结果。图中仅比较历史结构；最终文件是否符合要求，仍应通过内容审查和测试确认。

建立可比较的共同起点

创建主线与两次主题提交
mkdir lab13-integration
cd lab13-integration
git init -b main
git config user.name "Git Learner"
git config user.email "learner@example.invalid"
printf '# Course\n' > README.md
git add README.md
git commit -m "docs: establish course"
git tag workflow-base
git switch -c topic
printf '# Index exercise\n\nEdit, stage, then edit again.\n' > index.md
git add index.md
git commit -m "docs: add index observation"
printf '\nCompare working tree, index and HEAD.\n' >> index.md
git add index.md
git commit -m "docs: explain the three contents"
git switch main
printf '\nRead prerequisites before practice.\n' >> README.md
git add README.md
git commit -m "docs: explain the prerequisite"

main 与 topic 修改不同文件，避免冲突干扰关系比较。main 一次新提交，topic 两次新提交，共同基线有一次提交。操作前可以画出 M 和 F1、F2 的分叉。

保留双亲整合点

建立保留主题祖先的结果分支
git switch -c result/merge main
git merge --no-ff topic -m "merge: integrate index exercise"
git rev-list --parents -n 1 HEAD
git log --oneline --first-parent
git merge-base --is-ancestor topic HEAD

双亲整合提交连接原 main 与原 topic，topic 的原始提交成为结果的祖先。--first-parent 便于观察主线视角的整合节点。这个结构便于追踪一次主题如何接入，但最终文件和测试仍要检查。

把主题变化作为一项新提交

从同一 main 建立 squash 结果
git switch -c result/squash main
git merge --squash topic
git status --short
git diff --cached --stat
git commit -m "docs: add the complete index exercise"
git rev-list --parents -n 1 HEAD
git merge-base --is-ancestor topic HEAD

最后一条预期返回非零：squash 的新提交只有当前主线父提交，原 topic 不会因为补丁被合入就自动成为它的祖先。文件内容可以完整，但来源关联需由说明、PR 和其他记录补充。不要把范围内容相同误写成父链相同。

重放主题后形成线性结果

从原 topic 建立重放结果并比较文件树
git switch -c result/rebase topic
git rebase main
git log --oneline --graph --decorate --all
git diff result/merge result/squash
git diff result/merge result/rebase
git rev-list --parents -n 1 HEAD
git merge-base --is-ancestor topic HEAD

两项 diff 应为空，最后的祖先判断在本例中应失败。新父链包含 main 与重放后的两项主题提交，原 topic 仍指旧父链。平台的 rebase 类合入还有其具体元数据处理，应按平台说明理解，不把本地命令所有细节都套到网页按钮上。

依据回退与检索需要选择

表13.2比较三种方式。决定时需要问：未来希望按主题整体回退，还是逐项理解；是否保留主题内部的逻辑提交；来源和讨论在哪里追踪；团队怎样处理后续重复同步。

表 13.2 同一内容的三种历史表达
方式实验中的关系主要维护关注点
合并提交两个父，原主题是祖先整合边界清楚，需理解合并回退
squash新的单亲提交，原主题非祖先主题成为一项变化，来源另行关联

三种结果在本例中文件相同，不意味着复杂冲突场景一定同样相同。每一种方式都可能因为人工解决或选错范围而产生不同结果。合入策略是历史表达约定，不能替代内容判断。

把规则落到可验证的协作约定

团队约定至少应包含：主线用途、任务分支起点、请求说明要求、必需检查、评审责任、合入方式、发布与回退策略。对于 GitEasy 课程副本，可以先采用短任务分支、一名同伴评审、资料检查与明确版本标签，再按课程需要增加旧版维护（图 13.10 ）。

平台保护设置可以帮助实施部分规则，但应按实际可用功能核对。规则是否覆盖管理员、机器人、特定分支或直接推送，需要在测试仓库用故意失败任务验证。仅在文档中写“主线已保护”不足以证明所有路径都受约束。

权限分配遵循任务需要。自动检查只需要读取时，不额外赋予发布能力；负责发布的身份也不应因此默认获得无关管理权。仓库权限、凭据和运行代码的信任级别应一起考虑。

一个完成周期如何交接

合入后记录实际提交，确认主线检验结果，再关闭相应任务或发布。删除主题分支主要清理活跃名称，不自动擦除已经成为主线祖先的历史，也不自动删除平台讨论。

对下一位维护者，交接说明应能回答：版本在哪里，怎样运行检查，依赖怎样取得，哪些工作仍未完成，发生问题先看哪些证据。评审链接对平台协作有价值，离线交付也应有文本摘要，避免重要背景只能存在于个人记忆中。

案例研读：让评审形成可执行的决定

评审意见应指出问题所在、影响条件和可检验的改进方向。案例从含混反馈逐步形成可执行任务，再说明作者如何用变化和结果回应。

从需求到验收条件

某小组准备把实验报告提交方式由邮件改为仓库提交。如果需求只有“优化提交流程”，作者可能只修改一处说明，而评审者却期待同时更新命名规则、截止时间和评分依据。需求范围不明确使参与者对交付内容形成不同预期，需要先澄清验收条件。

需求应写成读者可以验证的行为：学生能找到提交入口；报告命名具有示例；截止时间含时区；教师能按固定位置取得材料；旧方式停用时间明确。每一项都应能在补丁或验证结果中找到依据。这样评审讨论便围绕任务是否满足，而非围绕个人偏好反复修改。

具体意见应使作者能够复现问题并判断修改方向（图 13.11 ）。处理线程之后仍需核对实际变化，不能将平台状态按钮替代对内容的检查。

评审意见需要包含理由与影响

“这里不好”难以执行，“请将截止时间写明时区，否则异地读者可能产生不同理解”则说明了问题、后果和修改方向。对可以接受但尚有取舍的设计，应区分建议与阻断项，避免作者把所有偏好都当作必须满足的要求。

作者回应时应说明已修改的位置、验证方式，或保留原设计的依据。简单回复“已改”无法帮助评审者判断新版本解决了什么。若补丁发生较大变化，应重新核对范围，不能沿用旧版本的通过结论。

协作练习：建立一份可审阅的变更说明

下面的独立实验用本地分支模拟提交评审前的材料准备。它不创建线上 PR，但将作者必须解释的内容组织成实际文件，后续可直接迁移到 GitHub。

准备具有明确验收范围的主题变化
mkdir review13
cd review13
git init -b main

交接说明保存在仓库外，是为了在本实验中区分待评审的产品内容与评审描述。真实平台上的 PR 正文承担类似沟通职责，但其本身不是普通提交对象的一部分。需要长期保存的设计理由，可以进一步写入项目文档，而不能只依赖某个临时讨论入口。

合入策略与长期维护

合入方式会影响以后调查、回退和维护的便利程度。选择时应同时考虑内容结果与历史结构，并将决定写成团队能够持续执行的约定。

一项策略同时影响哪些工作

保留合并提交有助于识别整合点，压缩合入有助于把主题作为一项主线变化，重放合入则可能形成线性序列。选择时要考虑回退、逐提交测试、来源追踪和团队习惯，而不能只依据日志是否简短。

无论选择哪种策略，都应检查最终主线内容，并确认评审所依据的版本与实际合入结果相匹配。自动化合入还可能在新的主线基线上执行，因此需要理解平台检查绑定的是哪个提交或合并候选。

完成任务还包括关闭反馈循环

合入以后，应说明目标版本、相关文档和后续事项。若需求仅部分完成，不能因 PR 已合入就关闭全部讨论。教学小组可以将任务分为已完成、需另行处理和明确不采用三类结论，并为每项结论保留理由。

迁移练习：评审通过以后，主线发生了相关修改。作者应怎样处理？参考分析是先取得新信息，判断主题是否仍满足需求，必要时整合并重新验证。过去的通过说明适用于当时审阅的内容，不能自动延伸到所有后续版本。

GitHub实践：从自己的派生仓库提交一项改进

平台贡献把本地变化放入真实所有权、评审和规则之中。下面选择范围明确的文档任务，逐步核对来源、目标和证据；无法访问私有原项目时使用授权教学副本。

学习目标与前置条件

本节把本地工作流迁移到真实平台。任务是在自己的 GitEasy 派生仓库中修正一项资料问题，并准备可评审的变更。需要可用账号、合法访问方式和网络。没有这些条件时，可先完成本章离线练习，再将未执行步骤如实登记。

本节不要求为练习而向作者仓库发送无实际价值的修改。可以在课程指定仓库内互评，也可以只在个人仓库形成完整任务记录；若确有教材勘误，再依据贡献说明提交真实请求。学习过程的真实性比制造一条公开记录更重要。

第一步：确认原项目与个人副本

浏览作者仓库时，先阅读 README、许可和贡献说明，明确项目用途。平台上的 fork 建立派生仓库关系，本地 clone 则取得可操作副本。两者不是同一个动作：创建 fork 不会自动在本机生成目录，克隆作者仓库也不会自动赋予写入作者仓库的权限。

在个人副本中取得本地仓库后，核对远端地址。通常 origin 指向个人可写副本，另设 upstream 指向作者仓库；这些简称是约定，最终以实际 URL 为准。账户切换或多协议并存时，还应确认推送使用的身份和地址。

线上练习模板：占位账号必须先替换
git clone https://github.com/YOUR_ACCOUNT/GitEasy.git
cd GitEasy
git remote add upstream https://github.com/tsingke/GitEasy.git
git remote -v
git fetch upstream

以上是需要替换参数的模板，不属于离线自动路线。若 upstream 已存在，应先查询配置，不要重复添加。获取只更新相关对象与观察记录，接下来的分支选择仍须由读者明确决定。

第二步：把问题限制在能够审阅的范围

选择一项具体问题，例如某章辅导材料的路径说明不清楚。先复现并记录现象，再写出修正后的读者行为：从仓库根目录能够定位正确文件，命令中的占位参数不会被误当成实际路径，验证方法清楚。

创建任务分支后，只修改与此问题有关的内容。不要把全篇格式重排、无关措辞调整或自动生成目录同时混入。若发现其他问题，可另行登记。范围清晰可以降低评审成本，也方便在需要时独立撤销。

第三步：提交前核对内容和证据

先查看工作区差异，再选择候选，最后检查候选补丁与说明。适用时运行本项目的材料检查和相关章节实验。自动路线通过以后，仍应人工阅读修改后的解释，确认没有改变原本正确的技术含义。

线上练习模板：仅推送个人任务分支
git switch -c docs/clarify-example-path
# Edit the relevant guide, then inspect and stage selected paths.
git diff
git add PATH_TO_THE_CHANGED_GUIDE
git diff --cached
git commit -m "docs: clarify the example path"
git push -u origin docs/clarify-example-path

模板中的路径必须替换为实际修改文件。若推送被拒绝，先看地址、权限、分支关系与规则；不要因为“仅文档”就跳过范围判断。成功推送只表示相应服务器接受了引用更新。

合入判断不能由单个绿色标记代替（图 13.12 ）。需求、历史结构和过程规则分别回答不同问题，团队应为每一项保留可核对的依据。

第四步：确认请求方向并撰写说明

创建请求时，接收仓库和目标分支表示变化希望进入的位置；来源仓库和比较分支表示作者提供的变化。跨 fork 请求尤其应逐项确认方向，并在提交前阅读平台展示的文件差异(GitHub 2026a)。

标题描述具体问题或结果。正文说明触发条件、修改后的表现和实际验证，必要时附图或链接。不要把作者与评审者的聊天过程写成项目长期说明，也不要将未执行的测试列为通过。证据不足时应写明限制，方便评审者安排后续检查。

第五步：理解检查结果和人工反馈

持续集成结果需要与实际提交对应。观察工作流名称、触发事件、检出版本与失败步骤，区分环境准备失败和内容规则失败。绿色状态只覆盖该工作流已经检查的范围，不能代替人工对需求和表述的判断。

来自派生仓库的贡献具有特定权限和运行条件，工作流不应为了方便检查而向不可信变化暴露高权限凭据。维护者应按最小权限组织检查，并审阅自动化文件的变化(GitHub 2026c)。学习者则只记录自己实际观察到的结果，不尝试绕过课程或平台规则。

第六步：修订、合入与交接

响应反馈时说明修改位置和依据。若不同意建议，围绕需求、证据与维护成本解释，不把讨论简化为个人偏好。新增提交或整理历史以后，应重新检查请求范围与验证结果；较大变化可能需要重新评审。

合入以后，确认实际接收位置、合入方式和结果内容。删除个人任务分支前，先确认所需成果已有清晰入口。随后获取新的主线信息，按团队约定更新个人副本。关闭请求不是学习终点，能够解释最终内容怎样进入共享历史，才完成了本节的协作闭环。

实验报告的最低要求

报告应包含个人派生关系、两个远端地址的角色说明、实际任务分支、变化范围、验证记录和评审结论。若只完成到推送，就说明停止位置；若在课程内模拟评审，就标明模拟范围。不要编造他人的评审意见或公开记录。

本节迁移任务是把一项真实可复现的文档问题修正为可接续成果。评价依据是方向正确、变化集中、证据真实和反馈闭环，而非请求数量或页面装饰程度。

本章小结

工作流把项目的发布、权限和验证需求转成共同规则。fork、分支与 PR 分属不同层次，评审把需求与实际变化联系起来，合入方式决定历史如何表达。机制与约定配合，才能形成可以持续维护的协作。

对一个小任务把范围、证据和交接完整做清楚，比先引入复杂分支体系更有教学价值。之后再根据版本维护和团队规模增加约束，每项约束都应解释其要解决的问题。

本章习题与解析

先独立作答，再展开解析核对思路。答案与教材同源，知识点随题列出。

应用13.1为一个每周更新资料、每学期发行定稿的课程选择工作流，解释是否需要长期发布分支。＋

考查知识点 · 工作流选择 / 发布节奏 / 维护成本

可采用短期主题加main持续更新，并用标签标记学期定稿；若旧学期需独立修订或长期支持，再建立维护分支。长期发布分支应解决明确并行维护需求，而不是为了满足流程图而创建。

按交付频率、团队规模和支持版本数量比较短期主题与长期维护分支。每周资料更新未必需要复杂发布线，学期定稿可用标签固定；有持续维护责任时再安排相应分支与移植规则。

基础13.2区分集中式协作与 Git 的分布式机制，说明共同远端承担什么角色。＋

考查知识点 · 分布式机制 / 共同远端 / 协作约定

集中式协作是团队围绕共同远端组织共享和规则，并不改变Git各仓库可本地保存与操作历史的分布式机制。共同远端承担约定的交换与整合入口，不是所有对象天然唯一的物理来源。

共同远端为团队提供共享入口和规则执行位置，各协作者仍可独立建立本地提交。集中采用一个协作入口属于组织选择，与Git的数据机制可以同时成立；两者不宜被写成互斥分类。

应用13.3画出 GitEasy 作者仓库、个人 fork、本地克隆与两个远端别名，标出读取和推送方向。＋

考查知识点 · fork / clone / 别名 / 通信方向

原项目与个人fork分别属于不同所有者，本地克隆配置origin指个人副本、upstream指原项目。fetch从所选来源读入，push向有权限的目标写入，PR在平台提出跨分支整合。名称可自定，以实际地址为准。

图中保留四个位置的独立边界，并对每个箭头写出实际来源与目标。fork属于平台侧仓库关系，clone建立本地副本，origin与upstream属于本地别名。来源名称本身不构成写入授权。

应用13.4为新增索引实验写需求与 PR 说明，包含可观察验收和实际验证范围。＋

考查知识点 · 需求验收 / PR范围 / 提交可评审性

需求写明索引实验要让读者观察什么以及通过条件；PR列出新增路径、示例命令、断言和文档入口。说明只在某系统执行过，是否运行其他平台和线上流程；未执行范围明确保留。

可把需求写成能够观察的行为，再列出相应文件、提交及测试。说明应围绕最终变化组织，避免把无关格式修改夹入功能任务；明确哪些结果已经运行，哪些还需要环境或他人验证。

应用13.5把“这里不清楚”改成一条包含位置、影响和可落实建议的评审意见。＋

考查知识点 · 评审意见 / 位置 / 影响 / 建议

例如：第三段把fetch描述为修改当前文件，读者可能误把抓取当作整合；建议分别说明跟踪引用更新与工作区状态，并增加抓取前后status和show-ref对照。意见包含位置、影响与可验证建议。

有效意见应指出具体语句或路径，解释它怎样影响理解或行为，并提出能够核验的修改方向。作者响应时补充修订与测试位置，使讨论能够闭合；笼统评价或单纯表达喜好难以推动代码改进。

应用13.6完成三种合入实验，同时比较树、父标识和祖先关系，不以提交图外观代替验证。＋

考查知识点 · merge / squash / rebase合入

分别建立merge、squash与rebase方式结果，比较最终树、rev-list --parents和merge-base祖先判断。可相同内容而不同父链；应提交实际标识与查询，而不是只提交一张看起来相似的图。

三种策略应从同一起点在独立副本实验。最终树可以一致，但提交数量、父关系和来源主题的祖先地位不同。选型应结合维护与追溯要求，不能以历史图是否整齐作为唯一依据。

基础13.7解释 squash 后为什么来源主题不一定成为结果祖先；这与最终文件是否完整有什么关系？＋

考查知识点 · 压缩合入 / 来源祖先 / 任务完成

squash以组合变化形成新提交，但通常不把原主题头接成父链，因此来源头不一定是结果祖先。内容完整由树、差异和测试核对，祖先归属由提交关系核对，两者并不矛盾。

squash将变化形成接收分支的新提交，通常不把来源头接为父。任务可已完成而祖先查询仍显示来源独有提交，清理时应同时检查最终内容与任务记录，避免再次重复合入同一意图。

应用13.8讨论来源分支修订后，先前评审与检查是否仍适用，需要核对哪些规则。＋

考查知识点 · 检查时效 / 批准状态 / 来源更新

新推送可能改变已经检查的文件、提交或依赖。需要核对检查针对哪个提交、旧评审是否失效、是否要求重新批准及是否允许例外。不能把先前的绿色和批准无条件移用到后续版本。

将检查结果与确切head或平台合并测试提交关联。来源发生变化以后，旧评审和旧运行是否仍有效需要依据规则与差异判断。新的功能、依赖或安全相关修改应重新评估，而不是继承一个脱离版本的绿色标记。

应用13.9为课程副本制定最小协作约定，并设计一项故意失败来验证合入限制。线上未执行时如实标明。＋

考查知识点 · 合入规则 / 允许与拒绝 / 最小权限

最小约定明确主题范围、提交说明、测试、评审和合入条件。设计一个能确实违反要求的候选，观察平台拒绝，再修正观察允许；记录身份和例外。仅编写规则模板时应称为设计，不能称强制规则已验证。

在练习仓库分别验证正常提交通过、故意失败被拒绝以及权限例外的条件。若没有实际运行平台规则，应交付配置草案与待验步骤，不能仅凭规则页面截图就断言保护已经覆盖全部入口。

应用13.10提交一份合入后交接说明，涵盖实际版本、检查入口、依赖和未完成事项。＋

考查知识点 · 交接 / 确切版本 / 后续责任

交接列出目标提交与合入方式，提供运行检查入口、依赖和实际结果，说明未完成事项和后续位置。删除主题之前核对保留入口；让接手者从干净目录重建，而不是依赖作者现有工作区。

交接说明应让接手者从新目录取得指定版本，定位依赖和检查入口，并识别仍未完成的事项。把源码、平台记录和运行状态分别列出，能够减少“文件拿到却无法继续维护”的情况。

应用13.11比较短期主题、主干开发和多版本维护的使用条件。为“每周课程资料更新、每学期定稿、旧学期仅修错”的项目选择流程，说明哪些分支长期存在、标签何时建立及修复如何在各线传播。＋

考查知识点 · 主干开发 / 长期维护 / 发布约束

日常变化可通过短期主题进入主线，学期定稿用标签固定；需要继续修正的旧学期可以建立受控维护线。是否长期保留更多分支，取决于并行支持责任、验证成本和发布节奏，不能套用固定数量。

修复从适合的基线形成独立变化及测试，再按需要移植并分别发布。流程说明应明确接收者、检查与结束条件，使历史能够服务维护，而非只形成外观复杂的分支图。对不再支持的版本，还需写清停止维护约定。

应用13.12某PR的head未变，但接收分支已经升级依赖；另一个PR在批准后追加了功能提交。请分析原有检查和批准能否沿用，说明基线变化、合并测试提交、必需检查与人工意见之间的关系。＋

考查知识点 · 规则与检查 / base变化 / 评审时效

head未变也可能与新的base形成不同组合，是否需要重新构建与测试应结合实际集成目标和规则判断。追加功能提交则改变了受审范围，旧检查对应的版本与旧意见是否仍适用，都需要重新核对。

记录检查所用提交、基线和目标，而不只记录一项永久绿色状态。自动化验证与人工审阅各有覆盖范围；规则可以要求更新后的检查和批准，但其实际效果仍需在练习仓库验证允许与拒绝路径。

综合13.13校园卡一次PR同时修改支付接口、Qt界面和大量格式，评审期间又更新了base。请拆分任务并给出验收，比较merge、squash与rebase合入对追溯和后续维护的影响，处理失效检查与意见，最后交付接手者可复现的版本及未完成事项。＋

考查知识点 · 评审拆分 / 合入策略 / 交接维护

先把功能必要依赖与无关格式变化分离，领域接口和界面接入按能独立验证的阶段组织；每个PR说明背景、影响和实际测试。base或head变化后，核对原意见与运行所对应的版本，必要时重新检查，避免继承脱离当前组合的批准。

合入策略依据团队对祖先追溯、提交粒度和维护的要求选择，并分别检查结果树与父关系。交接给出确切合入版本、依赖、构建与测试入口、维护移植计划及未完成事项。另一位同学从新目录复现，才能检验报告是否足以支撑接续。

可将接口及必要调用调整、界面接入、格式规范化拆成各自可解释的变化，同时明确跨任务依赖。base更新后重新检查比较范围，并针对新的head和适用整合输入执行检查，逐条回应原评审意见。若采用压缩合入，应在说明中保存任务与原提交的联系；若采用变基合入，明确新身份及维护定位方式。最终从交付标签独立构建，提供需求清单、测试结果和未完成事项，不能以线程已处理代表所有意见已获认可。
