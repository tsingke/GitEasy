CHAPTER 17 · 实践篇

校园一卡通系统版本管理实训

张庆科 编著约 78 分钟15 道分层习题

校园软件团队需要把“能够运行的程序”发展为“能够持续维护的项目”。本章以校园一卡通业务管理系统为载体，组织需求、C++实现、Qt界面、双人协作、GitHub评审、回归修复、版本发布与独立交接。每项Git操作都对应明确的工程问题，并要求说明结果证据。

学习目标：能按业务需求拆分主题与提交；能分别验证核心与界面；能处理推送竞争与内容冲突；能组织Issue和PR贡献；能整理私有历史、定位回归并移植维护修复；能验证候选、标记发布并从备份重建项目。

业务边界 →\rightarrow 可构建基线 →\rightarrow 核心与界面并行开发 →\rightarrow 协作与评审 →\rightarrow 问题定位与修复 →\rightarrow 维护发布 →\rightarrow 验证与交接。

项目背景、角色与迭代目标

高校校园服务台希望用一个桌面程序处理演示卡业务：开卡、充值、消费、挂失、解挂及流水导出。这个场景学生容易理解，同时包含状态、不变量和协作接口，足以展示企业项目中常见的版本管理约束。课程使用合成账户，不接入真实支付或学生信息系统。

从业务陈述形成验收条件

“支持消费”不能直接成为完整验收条件。应继续询问：卡不存在时如何处理，挂失后能否消费，余额不足是否改变流水，同一请求重复提交是否再次扣款。将这些问题写成可观察断言，才能判断程序是否完成需求，也才能在后续合并与维护中发现回归。

本项目把金额存为整数分，演示学生卡单日消费限额500.00元、教工卡1000.00元，账户余额上限1000000.00元。这些是课程设定，不代表任何学校政策。业务拒绝要求余额与流水保持原状态；幂等重试要求相同请求返回原回执，参数冲突则拒绝。表17.1把功能与版本管理证据联系起来。学生在实现之前就应看到验收要求，避免最后才补写与代码无关的报告。

团队角色与责任

维护者确认需求、评审规则与发布范围；领域开发者实现业务与测试；界面开发者连接输入、服务和显示；测试与发布角色从干净目录重建并检查交付。小组人数有限时可以轮换角色，但报告明确每一阶段由谁承担哪种责任。

项目任务应沿需求、实现和验证建立对应关系（图 17.1 ）。围绕同一条规则安排分支与提交，使评审者能够定位实现位置，并判断测试是否覆盖了验收条件。

本地双人实验用两个克隆模拟独立现场，其价值是可重复地观察对象传输和整合。它不等于拥有两个真实平台账户，也不能产生真实的第三方批准。在线任务再加入权限、PR及评审证据，两部分结果分别记录。

最低交付与可选拓展

最低交付包含完整核心源码、Qt界面源、自动测试、清楚的构建说明、版本历史及交接报告。具备Qt环境时运行界面与交互测试；没有Qt时先完成核心路线，再登记界面待验收状态。不能用“已提供GUI文件”替代“GUI已运行”。

数据库持久化、并发事务、统一身份认证、设备通信及清结算作为进一步设计课题。本例的CSV是运行期间流水导出，不是完整状态备份；关闭程序后内存账户不会自动恢复。项目应明确这些边界，使版本管理实训接近真实工程中的范围控制。

企业研发中的规划、任务与交付

企业研发方法首先体现为对需求、边界和证据的组织。本项目把需求说明、模块设计、任务开发、评审检查和维护交付联系起来，使一次修改能够沿着任务编号追溯到实现、测试及发布版本。图 17.2 给出主要环节；每个环节都应形成可以继续检查的材料，后续迭代也可以据此返回并修订既有决定。

从需求进入条件到任务完成标准

需求进入开发前，应回答使用者是谁、在什么条件下触发操作、成功后能观察到什么，以及哪些情况必须拒绝。例如，CSV币种任务的目标是让报告脱离窗口仍能被正确解释；验收既检查表头，也检查数据行，同时确认导出没有改变账户状态。若只写“增加导出功能”，开发者和评审者容易对完成范围形成不同理解。

任务卡还应列出涉及的模块、依赖的接口和验证方法。金额解析属于基础模块，余额变更属于业务服务，保存对话框属于Qt适配层。先确定这些责任，能够使开发分支围绕一项工作展开，并减少多个成员在同一文件中混合实现无关需求。配套项目的docs/enterprise-project-plan.md与docs/iterations.md分别提供总体方案和任务拆分。

完成标准同时约束代码和过程：候选差异应只包含本任务；实现、必要测试和说明共同提交；相关构建通过；评审意见得到回应；合入后的目标分支重新检查。CI能够证明特定提交在指定环境执行了哪些检查，却不能自行决定业务需求是否完整满足。涉及界面的任务还需要实际交互证据，不能用核心测试代替。

设计决定应随项目一起保存

模块拆分、金额单位、日期来源和持久化范围都属于设计决定。配套项目用简短的架构决策记录说明背景、选择、替代方案与影响。例如，选择整数分以后，输入解析、计算和展示都应遵守同一单位；选择进程内存储以后，CSV报告便不能被描述为完整数据库备份。决定有了版本，后来的维护者才能知道某项限制源于当前范围，还是源于未完成的实现。

接口变更应在实现之前与依赖方确认。若业务服务改变返回视图，Qt和CLI需要共同核对；若只修改报告字段，则应尽量把变化限制在导出模块及相应测试。评审不仅检查最终文件，也检查变化是否符合原先约定的边界。出现新的业务要求时，可以修订架构记录，再安排有依据的迁移和验证。

把Git知识落实到工作证据

本章连续路线覆盖共同基线、分支开发、远程交换、合并冲突、回归修复、维护回移、历史整理、二分定位、候选检查、标签和恢复。其余专题通过明确的工程任务衔接：换行规则用于统一C++源文件；对象与引用用于解释历史和冲突现场；补丁与附注用于受限交换和补充说明；LFS、子模块、稀疏检出和部分克隆用于依赖与规模演进；钩子、凭据和历史清理用于工程治理。

配套docs/git-skill-matrix.md列出45项技能工作包，区分连续演练、章节专项与人工平台任务。读者应按第1至16章的模型完成相应实验，并回到校园项目说明应用理由。大文件服务、真实权限和人工评审需要各自的环境与证据，离线路线通过不能代替这些结果。

个人实践时，可依次承担需求、开发、评审和发布角色，并注明哪些记录属于自检；团队实践时，应由不同成员对主要业务变化进行复核。最终报告用实际任务编号、提交、PR和测试相互连接，不填写虚构的Issue、审批人或成功截图。这样的过程训练，才有助于把一个教学项目中的方法迁移到后续大型工程。

阅读工程目录与构建入口

进入源码后，先理解文件职责，再开始修改。清晰目录使任务可以分工、差异能够评审，也使接手者能够判断某项变化应在哪一层发生。目录结构不是装饰，它承担了降低协作成本的作用（图 17.3 ）。

源码、测试、界面和工具分层

GitEasy中的projects/campus-card为完整项目。include/campus/提供领域接口，src/实现核心与命令行演示，tests/保存业务断言，gui/连接Qt界面，docs/登记需求和协作约定，tools/提供候选检查及教学辅助程序。构建结果写入单独目录，不与源码混放。

核心与界面分层使不同环境能够验证相应目标（图 17.4 ）。基础业务测试不应依赖窗口是否成功显示，界面检查则补充按钮、输入与结果展示的交互证据。

.gitignore排除构建缓存，.gitattributes统一文本规则。忽略不等于删除历史中的文件，属性也不代替代码格式约定。提交前检查候选列表，确认工程能够在另一个目录从源码重建，而非依赖本机已有产物。

头文件、实现文件与构建目标

多文件编程的关键在于职责和依赖的明确。头文件说明其他模块可以使用的类型与接口，实现文件保存具体算法和状态处理；CMake再把若干编译单元组成库或程序。不要通过包含.cpp文件拼接工程，也不要为了减少文件数量而把窗口、金额算法与账户容器集中到一个入口中。

图 17.5 呈现本项目的依赖方向。CLI与Qt调用业务服务，服务组合金额、日期、持卡人与报告模块；基础模块不引用Qt类型。这样既能在没有图形环境时验证规则，也能让界面与业务沿不同任务分支推进。

表 17.3 列出文件与责任。读取源码时，先从头文件确定可调用接口，再进入实现和测试；准备修改时，则从需求判断应改变哪一个模块，避免沿着文件名随意增加代码。

让模块边界形成可测的契约

campus_domain保存不依赖Qt的基础模块，campus_core保存业务服务，并通过公开依赖取得基础接口。单元测试可直接链接基础库，服务集成测试再验证多个模块共同完成业务的结果。一个模块有了独立测试，其他成员就可以依据稳定接口工作，而不必先打开完整窗口。

日期是一个容易被忽略的依赖。若测试总是读取执行当天，同一请求在不同日期运行便可能具有不同语义。本项目通过DayProvider传入可调用对象：普通运行使用系统日期，测试使用lambda固定业务日。代码 17.1 节选实际测试，显示日期、请求和余额如何共同进入可重复判断。

注入业务日期并检验充值重试
        std::string day = "2026-11-12";
        campus::CardService service([&day] { return day; });
        service.openStudent("S1", "student-1", "Demo");
        const auto first = service.topUp("S1", 10000, "R1");
        check.require(first.day == day, "topup must use injected date");
        service.topUp("S1", 10000, "R1");
        check.require(service.history().size() == 1 && service.card("S1").balance == 10000,
                      "topup retry duplicated");

可注入依赖有明确的使用边界。它使测试能够控制条件，却不自动解决生产系统的时区、跨日重试或永久幂等问题。接口改变后仍须更新需求与测试，不能把一个方便替换的函数当成完整业务协议。

用注释表达原因、单位与不变量

项目注释重点说明金额以分保存、基类为何需要虚析构、所有权何时移动、拒绝路径应保持哪些状态，以及报告为什么不承担恢复。函数名已经清楚表达的逐行操作，无需再重复一次；跨模块约定和容易误用的边界，则应放在接口附近。

代码统一格式，格式性变化与业务变化分开组织。教学辅助脚本使用明确定位标记构造基线、回归和币种任务，不依赖空格数量；这些标记只服务于复现实验，不参与业务运行。学生仍须阅读git diff与测试，说明改变了什么、为什么改变以及结果如何验证。

C++11核心与Qt6界面的标准边界

campus_domain、campus_core与命令行、核心测试目标按C++11构建。Qt6要求支持C++17或更新标准的编译器，因此campus_gui目标单独采用C++17(The Qt Company 2026)。这并不把核心代码中的C++11特性改称为C++17，也不承诺Qt6能够按C++11模式编译。

默认关闭GUI，使没有Qt的学生仍能完成Git主线。启用GUI后，CMake会明确查找Qt6 Widgets；找不到组件时停止配置，而不悄悄跳过目标后报告“全部通过”。依赖错误应作为环境问题记录，与业务测试失败区分。

在独立目录构建完整项目核心
cmake -S projects/campus-card -B build-campus -DCMAKE_BUILD_TYPE=Release
cmake --build build-campus --parallel 2
ctest --test-dir build-campus --output-on-failure

这些命令从GitEasy根目录执行。-S指定源码，-B指定构建目录；后续构建与测试都指向同一目录。Windows采用多配置生成器时，构建增加--config Release，测试增加-C Release。测试结果应注明实际生成器，不用不同平台路径的细微差异判断程序错误。

领域模型：封装、继承与多态

读懂领域模型有助于形成有意义的提交和评审。无需在这里重新完成一门C++课程，但应能说明每个类保存什么、谁负责校验以及界面为何不直接修改余额。否则，Git记录的仅文件变化，而非可以解释的工程决定（图 17.7 ）。

综合项目把业务规则与界面操作分开组织，便于在版本管理过程中独立验证。图 17.6 概括持卡人、校园卡、服务和界面的协作关系，类名与工程保持一致。左侧界面为示意绘制，实际Qt程序的运行截图另见本章，二者不应混作运行证据。

让余额与状态留在服务内部

CardService保存卡对象与交易记录，提供开卡、充值、消费和状态变更接口。外部得到的是CardView，用于读取卡号、姓名、类别、余额和状态，而非直接获取可任意赋值的内部账户。这样可以把业务约束集中到明确入口。

消费先检查金额、请求标识和日期，再处理重复请求，随后核对卡状态、余额与单日额度。只有检查和记录准备成功以后，才更新余额。测试不仅捕获异常，还核对拒绝前后余额和流水数量一致，从而约束失败路径的效果。

不同持卡人类别可以通过统一接口提供策略，业务服务按接口使用结果（图 17.8 ）。测试应同时覆盖各具体实现和服务的边界行为，不能只验证类型能够构造。

用抽象持卡人接口表达类别差异

CardHolder定义类别与单日限额的虚接口；StudentHolder和StaffHolder覆盖它们。CardService通过基类指针调用接口，不需要在每次消费中重复编写“如果是学生，否则如果是教工”的类别分支。

基类具有虚析构函数，std::unique_ptr<CardHolder>管理派生对象生命周期。这里的继承用于表达稳定接口下的规则差异，多态由运行时对象决定调用。若以后增加访客卡，仍需明确新类别的业务规则并添加测试，不能只增加一个界面选项。图 17.9 区分继承与所有权。两个派生类实现共同接口；服务通过内部Card对象持有账户及其持卡人，不把界面与业务继承关系混画成同一种连接。

代码 17.2 直接节选自配套可编译头文件。两个覆盖函数虽简短，却使调用方能够通过同一接口取得不同规则；测试再分别选择学生卡与教工卡验证效果。

辨认实际使用的C++11特性

项目使用enum class区分卡状态与业务类型，使用override检查虚函数覆盖；auto与范围for简化遍历，lambda用于排序和界面连接，std::move与独占智能指针表达所有权转移。代码以new直接构造交给智能指针，不把C++14才提供的make_unique写成C++11内容。

这些特性影响评审重点。移动之后的所有权需要明确，引用返回不能越过对象生命周期，异常发生后不能留下部分更新。规范的PR说明应解释相关不变量，而非仅罗列“使用了继承与多态”。

金额、请求与业务不变量

版本管理需要能够判定结果的业务基础。选择金额处理与请求重试作为重点，是因为它们能够展示“程序运行结束”与“业务结果正确”的区别，并使测试成为合并和维护时真正有用的证据（图 17.11 ）。

同一请求的重试需要避免重复扣款。图 17.10 以余额100.00为观察起点，流水数仅统计本组请求新增的消费记录。R1首次消费20.00后，合法重试返回原回执，参数冲突被拒绝；挂失后的新请求R2也被拒绝。工程先查询已有请求记录，已完成R1的合法重试不受后来挂失影响；此前充值仍保留在完整流水中。

为什么按整数分保存金额

十进制金额若先转为二进制浮点数，再乘以100转换，可能引入不适合财务语义的舍入问题。本例直接解析字符：整数部分、至多两位小数和边界检查分别处理。12.3得到1230分，0.05得到5分，超过两位小数、负数和不完整输入被拒绝。

业务核心使用最小货币单位保存金额，界面负责格式化显示（图 17.12 ）。图示以100.00元余额和20.00元消费说明计算与显示的对应，重试不再次改变余额。

整数存储也不自动消除全部问题。充值前检查余额上限，消费前检查是否足额，累计金额仍有范围要求。测试覆盖边界与拒绝后的状态，避免只用一个正常金额证明解析和记账都正确。

代码 17.3 节选实际消费路径。先检查可用余额，再累计当日消费并读取多态限额，最后只计算下一余额；真正的记账与余额写入在后续统一处理。评审时应顺着这个先后关系检查，不把其中任意一行孤立当作全部业务保证。

重复请求为何不重复扣款

界面或调用者可能因不确定结果而重试。requestId使服务能够识别已经处理的业务：卡号、业务类型、金额与日期相同，返回原回执；同一标识对应不同参数，则作为冲突拒绝。回执中的余额是原来记账后的余额，不一定等于账户此刻余额。

状态变化和消费处理应分别验证（图 17.13 ）。挂失后的新请求需要被拒绝；恢复卡片状态后，消费仍受余额、限额与请求规则约束，不能跳过其他检查。

本例把日期纳入请求语义，默认日期由可注入的DayProvider提供，普通运行读取本机日期，测试固定业务日；跨日重试或跨系统时区需要进一步设计明确协议。项目没有把内存幂等表称为永久防重数据库，交接报告也应说明退出程序后该表不会保存。这些边界应在需求中写清，再决定未来迭代如何增强。

图形界面把输入、业务结果和状态变化放到同一窗口，适合课堂演示。但可视化并不意味着可以复制一套独立的业务规则；界面应调用核心服务，并把结果重新读取到表格中（图 17.14 ）。

输入表单、按钮与模型

窗口提供卡号、姓名、账户类型和金额输入，按钮分别对应开卡、充值、消费、挂失、解挂与导出。选择账户行可以填写卡号。事件通过lambda调用CardService，捕获业务拒绝后显示提示；成功后刷新账户和流水。

git ls-files -u显示未合并索引阶段，为冲突两侧及共同基提供证据。文件中的标记方便编辑，但索引阶段才明确告诉我们操作尚未完成。不要在此时反复发起新的合并。

依据需求形成共同结果

本次教学决定同时保留南北两个服务台。编辑结果不采用简单的“全部保留当前方”或“全部采用对方”，而是写出新的业务表述。暂存以后再检查候选，提交说明记录决定，最后推送。

形成共同说明并完成合并
printf 'Service desks: north and south campuses\n' > docs/demo-policy.md
git add docs/demo-policy.md
git diff --cached --check
git commit -m 'merge: support both campus service desks'
git push origin main
git rev-list --parents -n 1 HEAD
cd ..

报告应同时交付最终行、合并节点的父关系与决策依据。只提交一个没有冲突标记的文件，不足以说明是否保留了双方需要的内容。对源代码冲突，还应增加业务测试；文本整合成功与程序语义正确需要分别判断。

迭代五：发布基线并建立回归修复

团队先标记已经通过现有检查的版本，再通过一个新输入暴露旧测试未覆盖的条件：只有空格的姓名不应成为有效持卡人。这个过程展示测试为何需要随需求和问题证据增长，而非把第一次绿色结果当作永久保证。

标记课程发布起点

附注标签记录发布意图；它没有让代码自动获得某种质量等级。发布说明中应列出现有功能与尚未覆盖的业务条件。

回归修复需要保留发布起点、失败版本和修复结果（图 17.21 ）。把能够稳定暴露问题的测试与修复放在同一条可追查链上，有助于以后定位和维护。

甲取得共同成果并标记首个课程发布
cd team-a
git fetch origin
git merge --ff-only origin/main
git tag -a campus-v0.1.0 -m 'Campus core and Qt source teaching baseline'
git push origin campus-v0.1.0
git switch -c fix/nonblank-holder
python3 "$GITEASY_CAMPUS/tools/name_validation_patch.py" --tests-only
cmake --build build --clean-first --parallel 2
if ctest --test-dir build --output-on-failure > build/regression-before.log 2>&1; then exit 1; fi
cat build/regression-before.log
grep -q 'FAIL blank holder name' build/regression-before.log

回归测试先失败，说明它确实能够识别基线缺陷。还要阅读失败信息，确认失败来自空白姓名被接受，而非编译器、路径或其他无关原因。未经定位的失败不能直接作为本次问题的证明。

修复实现并保留测试

修复检查标识和姓名中是否存在非空白字符；测试保留该输入作为以后变更的约束。实现与回归测试在同一修复提交中交付，便于维护分支一起移植。

实现非空白校验并合入修复
python3 "$GITEASY_CAMPUS/tools/name_validation_patch.py" --implementation-only
cmake --build build --clean-first --parallel 2
ctest --test-dir build --output-on-failure
git add src/card_holder.cpp tests/test_card_service.cpp
git diff --cached --check
git commit -m 'fix: reject whitespace-only holder identity'
fix_commit=$(git rev-parse HEAD)
git switch main
git merge --no-ff fix/nonblank-holder -m 'merge: validate nonblank holder identity'
git push origin main
cd ..

fix_commit保存的是本次实际运行产生的标识，不是教材中的固定哈希。后续移植依据这个标识选择修复，而非按相似提交说明猜测。若重新打开终端，应从历史重新取得并核对该值。

迭代六：维护分支与定向移植

已发布版本的维护需要控制范围。维护者希望引入姓名校验修复及其测试，不希望顺便带入未来尚未发布的实验功能。由发布标签建立维护分支，再对比拣选前后的路径范围，是一种清晰的操作路径。

从发布标签建立维护现场

新克隆模拟维护人员的独立现场。它通过当前中心取得对象后，从campus-v0.1.0建立维护分支；因此开始位置由标签决定，而非由克隆时的最新main决定。

主线修复移植到维护分支后，目标的依赖与接口可能不同（图 17.22 ）。维护发布需要在该分支重新构建和测试，不能沿用主线结论覆盖目标版本。

将指定修复移植到维护分支
git clone center.git maintainer
cd maintainer
git config user.name 'Release Maintainer'
git config user.email 'maintainer@example.invalid'
git switch -c maintenance/0.1 campus-v0.1.0
git cherry-pick "$fix_commit"
git diff --name-only campus-v0.1.0..HEAD
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --clean-first --parallel 2
ctest --test-dir build --output-on-failure
python3 - <<'PYVERSION'
from pathlib import Path
p=Path('CMakeLists.txt');p.write_text(p.read_text().replace('VERSION 0.1.0','VERSION 0.1.1'))
PYVERSION
git add CMakeLists.txt
git commit -m 'build: identify maintenance release 0.1.1'
git tag -a campus-v0.1.1 -m 'Maintenance fix for nonblank holder identity'
git push -u origin maintenance/0.1
git push origin campus-v0.1.1
cd ..

维护分支另用一次构建元数据提交把版本号从0.1.0更新为0.1.1，使CMake版本与维护标签对应。拣选通常建立新的提交身份，原修复与维护修复可以表达相近变化，却拥有不同父项。验收既比较业务效果，也比较维护范围。若补丁依赖目标版本不存在的接口，应分析依赖并改写适配，不能为让命令成功而直接合入整个开发主线。

迭代七：整理尚未共享的工作提交

开发过程中可以先记录局部进展，交付前再把需要共同解释的变化组织起来。本节只整理未推送的主题，不修改已被同伴依赖的共享main。目标是形成一项完整意图，不是单纯减少提交数量。

尚未共享的提交便于按完整意图整理，但仍需保存起点和验证结果（图 17.23 ）。整理后重新阅读差异与父链，确认补充内容没有遗漏，也没有混入无关修改。

使用fixup表达补充关系

第一条提交建立升级说明，第二条提交补充同一说明并明确标记为修正前一提交。随后以交互式变基的自动压缩规则把两者组织为一次可解释变化。

对未共享的说明提交进行自动压缩
cd team-a
git switch -c feature/upgrade-guide
printf '# Upgrade guide\n' > docs/upgrade.md
git add docs/upgrade.md
git commit -m 'docs: describe campus card upgrade'
printf '\nRun the core tests before deployment.\n' >> docs/upgrade.md
git add docs/upgrade.md
git commit --fixup HEAD
GIT_SEQUENCE_EDITOR=true git rebase -i --autosquash HEAD~2
git rev-list --count main..HEAD
git show --stat HEAD
git switch main
cd ..

GIT_SEQUENCE_EDITOR=true只用于让本次脚本接受Git自动生成的整理计划；日常交互可以使用自己熟悉的编辑器。整理后检查内容两部分均保留，提交数量为1，再决定是否推送这一主题。

迭代八：用二分定位业务回归

当多次变化以后出现问题，逐个猜测容易遗漏证据。二分需要一个已知通过的版本、一个已知失败的版本，以及能够区分两者的检查。本节只在未共享的故障演练分支注入缺陷，不向中心推送故意破坏的历史。

构造可辨认的失败范围

演练把挂失检查条件替换为恒假，使挂失卡继续进入资金操作。由于已有测试检查挂失拒绝，业务回归能够被自动识别。前后加入无关文档提交，模拟实际调查中并非每个提交都触及故障的情况。

自动二分要求判定脚本稳定且含义明确（图 17.24 ）。业务失败与运行异常应使用不同结果处理，定位完成后还要阅读候选差异，说明证据支持的因果范围。

在独立演练分支注入挂失校验回归
cd team-a
git switch -c drill/lost-card-regression
good_commit=$(git rev-parse HEAD)
printf 'Investigation starts from a known passing baseline.\n' > docs/investigation.md
git add docs/investigation.md
git commit -m 'docs: record investigation baseline'
python3 "$GITEASY_CAMPUS/tools/lab_scenario.py" disable-lost-check
git add src/card_service.cpp
git commit -m 'test: inject lost-card regression for bisect drill'
bad_commit=$(git rev-parse HEAD)
printf 'Keep evidence for each tested revision.\n' >> docs/investigation.md
git add docs/investigation.md
git commit -m 'docs: explain investigation evidence'

运行判定并恢复工作入口

判定脚本对当前检出的版本构建并测试：通过返回0，测试失败返回1，无法构建返回125表示暂时跳过。跳过可能使定位结果不唯一，报告应如实记录。本例各候选均可构建，因此能够定位实际注入缺陷的提交。

二分定位并回到正常主线
git bisect start HEAD "$good_commit"
git bisect run python3 "$GITEASY_CAMPUS/tools/bisect_check.py"
test "$(git rev-parse refs/bisect/bad)" = "$bad_commit"
git bisect log
git bisect reset
git switch main
cd ..

“第一个失败提交”是相对于当前判定条件与边界而言，不等于作者主观上最早犯错的位置。若测试不稳定，或业务在中间版本暂时恢复，二分的推理前提会受影响。真实问题中应先稳定判定，再决定如何修复。

迭代九：验证索引中的候选内容

在工作区运行测试只说明当前磁盘内容符合检查，而提交使用索引选定的内容。本节故意让两者不同，说明为什么自动提交检查不能简单运行一次工作区测试便宣布候选通过。

建立工作区正确、索引错误的反例

先把错误的挂失检查暂存，再仅恢复工作区中的正确版本。此时文件显示同时具有暂存与未暂存变化；两个版本不同是实验要求，不是Git状态损坏。

部分暂存可能使磁盘文件与候选不同（图 17.25 ）。综合实训应分别验证实际检查的输入，并在独立目录重新构建提交，防止把工作现场的成功误作候选完整的证明。

制造候选与工作文件不一致
cd team-a
python3 "$GITEASY_CAMPUS/tools/lab_scenario.py" disable-lost-check
git add src/card_service.cpp
git restore --source=HEAD --worktree -- src/card_service.cpp
git status --short
cmake --build build --clean-first --parallel 2
ctest --test-dir build --output-on-failure
if python3 tools/check_candidate.py; then exit 1; fi

check_candidate.py把索引中的受跟踪文件检出到独立临时目录，再进行构建测试。因此它应识别已暂存的错误，即使工作区中的测试通过。未跟踪文件不会被悄悄补进候选，这正是检查提交内容所需要的范围。

修正候选并确认状态

本例工作文件已经是正确版本，只需要取消错误的暂存选择，再检查干净候选。恢复命令应明确目标层，避免为了取消暂存而同时覆盖工作文件。

恢复正确候选并重新验证
git restore --staged -- src/card_service.cpp
python3 tools/check_candidate.py
git status --short
cd ..

团队可以把候选检查接入本地钩子以提供早期反馈，同时在服务器运行受控检查。本地钩子可以被绕过，也不会因为普通clone自动成为强制规则。两种检查相互补充，不能以其中一种的存在代替另一种的职责。

迭代十：独立恢复发布与并行维护

交付不是把开发目录压缩后交给下一位同学。需要明确发布位置、依赖、检查与数据覆盖，使接收者可以从新目录取得相同源码并完成验证。本节分别处理源码归档、Git历史备份和工作树现场。

形成归档与Git历史备份

先取得维护标签，再创建对应源码归档与覆盖当前引用的bundle。归档只保存所选版本的文件；bundle保存命令所选Git历史，不含全部平台资料。两者用途不同，文件名也分别表达。

交付资料应与接收者的任务对应（图 17.26 ）。只需要运行某一版本与需要继续维护历史，是不同恢复目标；完成交接前应在独立位置逐项验收。

创建并恢复校园项目交付材料
cd team-a
git fetch origin --tags
git archive --format=zip --output=../campus-v0.1.1-source.zip campus-v0.1.1
git bundle create ../campus-history.bundle --all
git bundle verify ../campus-history.bundle
cd ..
git clone campus-history.bundle restored
cd restored
git switch -c verify/release campus-v0.1.1
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --clean-first --parallel 2
ctest --test-dir build --output-on-failure
git describe --tags --exact-match
git status --short
cd ..

恢复后的克隆从指定标签建立验证分支，避免把bundle默认分支误当作要验收的发布。报告记录实际构建环境与结果，并另外列出Qt开发组件、未提交草稿、外部数据以及GitHub讨论和附件的保全方式。

使用工作树同时维护不同版本

维护版本与开发主线可以通过两个工作树并行检出，共享对象库却保留各自工作文件与索引。为减少目录清理时的混淆，本次把构建目录放到工作树外部；完成验证后正常移除该工作树。

在独立工作树验证维护标签
cd team-a
git worktree add -b verify/maintenance ../maintenance-tree campus-v0.1.1
git worktree list
cmake -S ../maintenance-tree -B ../maintenance-build -DCMAKE_BUILD_TYPE=Release
cmake --build ../maintenance-build --parallel 2
ctest --test-dir ../maintenance-build --output-on-failure
git worktree remove ../maintenance-tree
cd ..

工作树不是完整备份，也不隔离共享引用的所有变化。团队成员应始终说明当前目录、分支和构建输入。通过这条路线，学生已经把对象与状态模型用于需求实现、协作整合、问题定位、维护发布和独立交接。

将本地协作迁移到GitHub

本地路线已经证明提交、整合和恢复的模型，线上任务再加入实际身份、平台规则和人工评审。不要在这一步把本地中心地址机械替换为作者仓库后直接推送；应使用自己的课程仓库或获得明确维护权限的项目（图 17.27 ）。

建立需求与里程碑

建议建立“核心基线”“Qt界面”“维护修复”三个交付阶段，把CC-01至CC-06登记为实际Issue。每条任务写明范围、验收与依赖，再由小组认领。题目中的CC编号是课程需求标识，不是GitHub已经存在的Issue编号。

对空白姓名缺陷，报告原版本、输入与实际结果，再补充回归测试。Issue关联修复PR，合入和发布以后记录验收位置。若课程只允许本地模拟，则保存同样结构的Markdown任务表，并明确未建立线上记录。

迁移到GitHub后，本地的提交与引用模型仍然成立（图 17.28 ）。平台记录补充请求方向、讨论和检查依据；展示时应标明真实记录，教学模板不填入虚构批准。

提交可评审的核心与界面PR

核心PR说明业务规则及成功、拒绝测试；界面PR说明输入流程、依赖、核心复用和界面验收。把大范围无关格式调整从功能PR中分开，避免评审者在噪声中寻找真正变化。提交列表与文件差异均应与标题所称范围一致。

PR的base指向准备接收变化的课程主线，head指向自己的主题分支。来自fork时同时核对所有者。至少完成一轮具体意见与响应；若没有其他评审者，不编造批准记录，可由教师安排交叉评审或在报告中标注自检范围。

本书配套工程于2026年11月11日建立了实际的拉取请求#1，将校园一卡通源码和第16、17章材料提交到main。读者可在Files changed查看差异，在Commits定位提交，在Checks核对自动化结果。该记录由作者工作区提交，不能据此认定已获得独立评审；访问私有项目还需要相应权限。课堂任务应使用自己的主题分支，记录同样的证据关系。

配置并验证工程检查

配套工作流分别执行核心构建与Qt构建，默认使用只读源码权限。必需检查名称应与实际作业匹配；规则效果在练习仓库验证，不直接更改作者项目权限。失败时先读取提交、作业、步骤和输出，再判断需要修改代码还是环境配置。

对于外来PR，基础构建测试不需要真实支付或学生系统凭据。真实生产集成若在后续课程加入，应有独立权限与受控环境。学习项目不能因为一个自动化模板能执行脚本，就被表述为已经具备完整企业部署能力。

发布与交接验收

交接应使另一位同学能够从新目录取得指定版本、运行检查并继续维护。报告围绕需求、操作、证据和限制组织，避免把大量无说明截图堆在一起。图像用于定位界面，文本和提交标识用于复现事实（图 17.29 ）。

建立可核验的交付清单

交付清单包括确切提交与附注标签、源码与构建命令、核心和Qt测试结果、真实Issue/PR入口或未执行说明、维护修复范围、备份恢复记录与已知限制。构建产物按系统说明来源，不以“可以双击”代替可重复构建。

GitHub Release记录用户可理解的变化、兼容性和取得方式；归档、Git历史和平台记录分别保全。未提交草稿不能期待从标签恢复，内存业务状态不能期待从源码恢复。交接者应能指出每类材料的保存位置。

按结果、过程与解释共同评价

结果评价关注程序与检查是否满足验收；过程评价关注分支、提交、评审与发布是否可追踪；解释评价关注是否理解冲突、范围与恢复前提。三个方面相互支持，不能以最终余额正确掩盖丢失同伴提交，也不能以图形历史整齐替代业务正确。

建议教师抽取一个未在报告中预先固定的变式，例如新增访客卡规则、调整合成限额或更换导出字段，要求学生先预测影响范围，再组织实现与验证。能够迁移到新任务，才说明学生已经把命令知识转化为工程能力。

本章小结

校园一卡通实训把领域规则、程序实现与协作历史共同组织为可交接成果。需求形成可观察断言，核心与界面分别验证；提交表达独立意图，分支承载任务，整合保留需要的成果。非快进拒绝、文本冲突、业务回归和候选失败来自不同条件，需要使用相应证据分析。

维护与发布继续约束变化范围：未共享工作可以整理，已分发版本需要可追溯修订；定向移植同时验证内容与依赖；归档、Git历史、平台记录和业务数据分别说明覆盖。掌握这些判断后，Git命令才成为能够迁移到真实项目的工程方法。

需求写明挂失只限制新的资金业务而保留旧记录；测试包含正常消费成功、挂失消费拒绝及余额流水不变。提交交付实现和回归测试，PR再核对范围、环境和评审结果。不同证据分别支持行为与协作结论。

成功路径和拒绝路径应分别指定输入与状态。挂失拒绝除了产生错误提示，还应确认余额及流水不变。提交链接实现与测试，PR再说明验证环境和范围，需求编号使这些材料能够互相定位。

CardHolder提供类别与限额接口，学生和教工派生类覆盖；CardService封装余额、状态和交易。基类虚析构配合unique_ptr管理派生对象，调用虚函数实现类别规则。界面读取视图并调用服务，不直接给余额赋值。

应用17.3说明多文件工程中campus_domain、campus_core、CLI与Qt目标的依赖关系，解释核心C++11与Qt界面C++17为何分别设置。给出独立构建与测试证据，并用日期注入说明如何使业务检查可以重复。＋

考查知识点 · 多文件模块 / 构建目标 / C++语言标准 / 日期依赖注入 / 可重复测试

基础模块分别声明金额、日期、持卡人与流水接口，由campus_domain库保存实现；campus_core组合这些模块并实施账户业务。CLI和Qt依赖服务，基础模块不包含Qt类型。每个头文件应明确依赖，实现文件只包含自身职责，构建由CMake组织编译和链接，不能通过包含源文件拼接程序。

分别在新目录构建核心和启用Qt的工程，保留实际编译标准、CTest结果及确切提交。核心目标按C++11检查，Qt目标按依赖要求采用C++17。测试向服务注入返回固定业务日的lambda，验证充值日期、消费日期和重复请求结果，再改变日期检查冲突或拒绝后的状态；普通运行仍可使用系统日期适配器。

应用17.4完成并行导出与界面任务，比较推送前后本地main、origin/main与中心main。＋

甲先推送后中心main更新，乙未fetch时origin/main仍可能旧；乙本地main已含自己的主题而与中心分叉。fetch更新观察记录，合并建立共同可达历史后再推送。每个位置分别用查询记录，不能以一个名字替代三个入口。

建议在每次抓取、合并和推送前后记录三个位置的提交标识，再解释哪些动作更新哪一端。非快进拒绝保留了本地成果，后续整合应让两项功能及其测试共同成立，而非以覆盖方式消除提示。

应用17.5提交服务台冲突的索引阶段、最终文本和父关系，并解释为什么选择共同结果。＋

冲突时保存ls-files -u与双方文本；最终写明南北服务台共同安排，暂存后完成合并并核对两个父项。选择依据来自业务要求，而不是文件标记的左右顺序。工作文件、索引和提交证据应对应同一次解决。

保留基线与双方文本，再说明共同服务方案的业务依据。完成后检查未合并条目清空、最终文件符合要求且提交具有预期父项。删除冲突标记只完成文件编辑，尚需候选选择与整合验证。

应用17.6先用回归测试证明空白姓名问题，再交付实现与测试；说明原测试通过为何不能排除该缺陷。＋

考查知识点 · 回归测试 / 预期失败 / 修复验证

先只加入空白姓名断言，应观察它因旧实现接受输入而失败；修复后同一断言及既有测试通过。原检查没有覆盖这一输入，因此其绿色结果并不能排除缺陷。报告区分真正业务失败与环境失败。

应用17.7在维护分支拣选修复，核对路径范围与业务结果，说明新旧修复的提交身份关系。＋

考查知识点 · 维护分支 / 拣选 / 修复范围

维护分支从指定标签开始，cherry-pick只选择修复提交，比较变化路径并运行回归。新提交通常以维护头为父，身份与主线修复不同；相近补丁效果不代表父链相同，依赖也需重新验证。

先确认维护基线及所需依赖，再拣选实现和回归测试，检查没有夹带新主线的无关功能。新提交通常具有不同父项和标识，应通过差异、测试与任务记录说明它移植了相同修复意图。

应用17.8完成未共享提交整理与二分演练，分别说明内容不变量和判定条件的边界。＋

考查知识点 · 私有整理 / 二分 / 稳定判定

未共享整理应保留需要的最终内容与可解释意图；二分需要明确好坏边界及稳定判定，构建不了的版本按策略跳过。记录实际首个失败标识与条件，不把当前检出位置机械视为最终结论。

autosquash以后检查最终树和提交意图；二分以前验证好坏边界及判定程序。每个候选版本均重新构建，构建失败与业务失败分别处理。整理与定位解决不同任务，报告不宜只展示最后一张历史图。

应用17.9重现工作区通过而候选失败的情况，再修正索引；说明候选检查为何需要独立目录。＋

考查知识点 · 索引物化 / 候选构建 / 工作区差异

把错误实现暂存，再只恢复工作区正确内容，工作区测试通过而索引检出测试失败。修正索引后重测。独立目录避免未暂存文件、未跟踪依赖或已有构建产物悄悄补齐候选，保证检查对象就是拟提交内容。

把待提交内容检出到独立目录，防止未暂存的修正混入测试。先观察坏候选失败，再重新暂存修正并复测，核对拒绝确实来自预期业务断言；这比仅检查当前编辑器中的程序更能约束交付。

应用17.10在自己的GitHub项目完成一次可核验贡献，记录base、head、检查和评审状态；没有实际评审时如实说明。＋

考查知识点 · 真实贡献 / 检查提交 / 评审范围

使用自己的仓库与主题分支，记录base/head、提交、测试和真实PR地址。评审意见及响应只能记录实际发生内容；没有他人批准时说明自检范围与等待状态，不把本地双人模拟称为真实平台评审。

记录接收和来源位置、确切head、实际检查链接及意见处理过程。平台自动运行不产生独立人工批准，作者自己的检查也应准确说明。来源更新以后，重新确认旧运行和旧讨论是否仍适用。

应用17.11从bundle恢复发布标签并构建，列出未被bundle覆盖的资料与业务状态。＋

从bundle克隆后切到维护标签，独立构建与测试并核对版本。bundle不自动含平台Issue/PR、附件、Qt安装、未提交草稿及程序内存中的账户数据；每项缺口分别安排保存与恢复。

在新目录从历史包取得发布标签，验证标签和源码后构建，并记录依赖来源。业务账户保存在本例内存中，不随源码历史恢复；Issue、评审与外部附件也需另列保存方式，不能由clone成功推断已经具备。

应用17.12提交完整交接报告，并设计一项新需求，说明将如何拆分分支、测试、评审和维护范围。＋

考查知识点 · 交接报告 / 新需求 / 维护责任

交接包含确切版本、环境、构建、检查、协作与恢复记录和限制。新增访客卡可先登记规则与断言，再分别实现核心、界面和测试，评审确认兼容性；若需回移旧版，另查接口依赖与维护范围。

报告至少包含需求清单、确切版本、构建入口、实际测试、依赖、已知限制和恢复记录。新需求应拆成可评审任务并说明兼容性，特别考虑已有维护线是否接收修复，以及界面与领域模型如何保持一致。

应用17.13针对金额小数位、重复请求、跨日重试、挂失状态和学生或教工限额设计测试。要求成功结果符合规则，拒绝以后余额与流水均保持原状，并说明内存幂等记录与持久化服务的区别。＋

考查知识点 · 金额解析 / 幂等 / 限额 / 失败不变

金额直接解析为整数分，测试正常小数、过多小数、负数和上限；同一请求标识及相同业务参数返回原回执，参数冲突拒绝。跨日语义按项目约定核对，不能简单把当前余额与原回执余额等同。

分别构造两类持卡人、当日累计限额及挂失拒绝，记录拒绝前后余额和流水数量。内存保存的回执在退出后不自动存在，生产持久化与并发事务需要进一步设计。本题验收既检查正确返回，也检查失败路径未留下部分更新。

应用17.14从实际源码指出封装、继承、多态、移动语义和unique_ptr的使用；再说明Qt界面怎样复用业务服务。设计界面显示与模型一致性测试，并解释为何重复检出后应重新构建、候选验证应使用独立目录。＋

考查知识点 · 领域与界面 / 所有权 / 构建隔离

CardService将账户与流水留在受控入口内，持卡人基类提供类别和限额接口，派生类通过override表达差异；独占智能指针和移动表达生命周期与所有权。Qt按钮调用同一服务，再从视图刷新，不能另建一套不受校验的余额。

测试应覆盖成功与拒绝交互后表格同服务内容一致。核心和GUI分别核对语言标准与依赖；连续快速编辑、检出后清理旧生成产物，防止测试旧二进制。候选验证从索引物化内容，避免工作区未暂存修正混入待交付版本的结论。

综合17.15为校园卡系统增加“访客卡”并规定独立限额与有效期，小组同时修改领域、Qt界面和文档。请完成需求分解、接口与测试设计、并行分支及PR、至少一次真实冲突处理、回归定位、旧维护线修复与新版本发布；交付独立恢复报告，明确持久化、时区和真实支付等未实现范围。＋

考查知识点 · 新类别迭代 / 协作 / 维护 / 交付 / 企业迭代规划 / 模块接口与任务追踪 / 日期策略与回归测试

先把访客卡类别、限额、有效期和失败不变条件写成验收断言，再决定哪些差异适合通过现有多态接口扩展、哪些需要新增明确校验。领域与GUI按依赖拆成可评审变化，文档记录构建和数据范围；并行整合要保留来源、冲突决定及内容和父关系检查。

构造回归并以稳定测试定位，维护线只移植需要的独立修复及测试。发布固定确切提交和标签，从新目录取得源码、依赖与备份后构建验证，另列平台材料和未提交草稿。交接如实说明内存状态、日期规则、并发持久化与真实支付集成的限制，不把教学原型扩展任务写成已具备生产保障。

先定义访客身份、限额与有效期的边界，明确时间由何处提供，以及过期、余额不足和重复请求的预期结果。领域、界面和文档分别建立主题任务，并约定抽象接口；每条分支包含对应测试。整合时保留冲突来源及解决理由，用稳定判定定位一次回归，再把适用修复移植到维护线。发布前从确定标签独立构建核心与Qt目标，验证拒绝路径不改变余额或流水，并在新目录恢复交付。持久化、时区政策和支付网络接入若未实现，必须列入明确的范围说明。

实施前先用任务卡明确访客卡限额、有效期边界和拒绝条件，登记接口及数据变化。将策略放入持卡人或明确的新规则模块，日期检查通过可控制依赖测试；Qt仅增加输入和展示，不复制过期判断。分开提交契约、实现与测试、界面及文档，PR连接需求与证据。发布后从旧标签建立维护线，只回移适用修复，并由独立目录核对标签、构建、行为和未被源码备份覆盖的数据。
