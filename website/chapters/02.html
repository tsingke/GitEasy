CHAPTER 02 · 基础篇

环境配置与仓库初始化

张庆科 编著约 36 分钟11 道分层习题

假设你准备整理一份课程学习笔记。今天写下两段内容，明天修正其中一句，周末再请同学补充。你希望每次重要修改都有记录，也希望能够确认某次修改究竟保存了什么。本章从这个需求出发，完成安装、配置、建仓和两次提交。实验不需要 GitHub 账号，也不需要连接远程仓库。

学习目标：能够检查 Git 是否可用；区分提交身份与平台登录；在指定目录初始化仓库；完成“编辑、暂存、提交、检查”的循环；判断文件是否已经进入历史；识别初次操作中的常见失败原因。

检查程序 →\rightarrow 建立学习目录 →\rightarrow 配置实验身份 →\rightarrow 创建文件 →\rightarrow 第一次提交 →\rightarrow 第二次修改 →\rightarrow 检查历史与忽略规则。

安装之前先检查

安装软件的目的，是让操作系统能够找到并运行 Git 程序。打开“阅读准备”介绍的终端，输入：

检查 Git 程序
git --version

若显示以 git version 开头的版本号，说明当前终端能够调用 Git。实际版本号不必与书中示例相同；后文如使用仅在较新版本提供的功能，会单独说明。若出现“找不到命令”一类错误，先安装或修复程序路径，不要继续执行后面的仓库操作。

选择适合操作系统的安装方式

Windows 可从 Git 官方下载入口选择 Git for Windows。它同时提供 Git 程序与 Git Bash。首次学习请保留 Git Bash，以便运行本书的基础 shell 示例。安装界面的选项会随版本变化，不必逐屏照搬旧截图；重要的是安装后能在 Git Bash 中通过版本检查，并能使用自己熟悉的文本编辑器。

macOS 可以安装 Apple 命令行开发工具，也可以在已有 Homebrew 的情况下安装 Git。两者可能提供不同版本。如果计算机已经有可用 Git，先完成本章实验，不必为追求相同版本号重复安装。Linux 通常通过发行版包管理器安装，命令与权限依发行版而定。表2.1给出本节所用的比较项目。使用时应同时核对前述适用条件。

表 2.1 常见系统的安装入口与检查方法
环境安装入口与说明
Windows官方 Git for Windows 安装包；安装后重新打开 Git Bash
macOS命令行开发工具，或已有 Homebrew 环境下的 brew install git
Debian/Ubuntu系统包管理器，例如 sudo apt install git
Fedora系统包管理器，例如 sudo dnf install git
共同检查在实际使用的终端运行 git --version

软件安装可能需要管理员权限，但日常学习不应为 Git 操作随意添加 sudo。如果一个普通学习目录中的文件突然无法写入，应先检查目录所有者和路径，而非不断提升权限。

同一台计算机可能有多个 Git

版本检查只反映当前终端找到的程序。图形客户端、集成开发环境和终端可能各自使用不同的 Git。macOS/Linux 或 Git Bash 中可以用 command -v git 查看当前调用位置。后续遇到“同一条命令在不同工具中行为不同”时，程序版本、配置与当前目录都值得核对。官方安装入口为 https://git-scm.com/downloads。下载页面和包管理器版本属于可变化信息，使用时以实际页面及安装后的版本检查为准。

创建一个独立的学习仓库

安装程序只使计算机能够调用Git，项目本身还需要明确的工作目录和仓库。下面在新目录完成初始化，再观察普通文件与隐藏管理信息的位置；这个位置关系会成为判断后续命令作用范围的起点。

（图 2.2 ）

初始化后，项目目录中同时存在供人编辑的工作文件和供Git管理历史的信息。图 2.1 用文件夹形态区分这两部分：日常编辑发生在工作目录，Git通过管理目录组织对象、引用和索引；读者应通过命令查询这些信息，避免手工改动内部文件。

先明确目录，再初始化

请在个人学习目录中执行以下命令。如果名为 git-lab-02 的目录已存在，换一个新名称，并相应调整 cd 后的参数。不要在存有作业或个人项目的目录中试验覆盖操作。

创建本章专用仓库
mkdir git-lab-02
cd git-lab-02
git init -b main
git status

git init 将当前目录初始化为 Git 仓库；-b main 指定初始分支名为 main。这里的“分支”暂时理解为组织一条工作历史的名称，第 5 章会解释其结构。显式指定名称可以避免不同计算机的默认设置影响实验。

运行 status 后，应能看到当前位于 main、尚无提交，以及尚无可提交文件的含义。本书不固定每一个英文或中文句子的拼写，因为输出可能经过本地化。判断要点是：仓库已建立，但还没有历史版本。

git init 通常会创建隐藏的 .git 目录，用来保存该仓库的对象、引用和配置等信息。用 ls -a 可以查看。不要把“能看见的项目文件”与“Git 保存的历史数据”混为一谈，也不要手工删除或编辑其中的文件。后续会遇到裸仓库和多工作树等不同布局，此处先认识普通仓库的常见形式。图2.3给出本节所用的结构与关系示意。阅读时请结合前述对象与操作区分各元素的含义。

为练习配置提交身份

一次提交除了文件状态，还包含作者、时间与说明等信息。先在本仓库设置教学身份：

仅为当前仓库配置示例身份
git config --local user.name "Git Learner"
git config --local user.email "learner@example.invalid"
git config --local user.name
git config --local user.email

最后两条命令读取配置，应该分别显示刚才输入的姓名和邮箱。--local 表示只作用于当前仓库。示例邮箱用于离线练习；准备向公开仓库提交时，应改成自己选择的真实或隐私邮箱，因为这些信息会随提交进入历史。

提交身份不等于登录凭据。你可以在完全没有网络和平台账号的情况下创建提交。配置姓名和邮箱，并没有证明操作者拥有某个账号，也没有完成服务器认证。以后通过 HTTPS 或 SSH 连接服务器时，还需要另行处理访问权限。第 7 章将把这两件事分开解释。

理解配置的覆盖关系

常用配置有系统级、用户全局级和仓库级。对于常见的单值设置，可以先理解为：越具体的设置优先。仓库级可以覆盖用户全局级，同一用户下不同项目便可使用不同邮箱。命令行临时配置、条件包含和部分多值设置另有规则，不能把三层关系当作全部配置机制。

查看配置值来自哪里
git config --show-origin --get user.email

这个命令不仅给出值，还标明来源。若你为个人项目和课程项目使用不同身份，先查来源比不断重设全局配置更容易定位问题。

熟悉本章以后，可以按自己的需要使用 git config --global 建立个人默认值。本章不要求修改全局编辑器或行尾配置，以免影响其他项目。

跨平台换行使用 LF/CRLF 的差别，以及仓库内 .gitattributes 的作用，将在后续实验中单独说明。

从一个文件走到第一次提交

仓库初始化以后尚未形成项目历史。第一次提交需要先创建内容、选择候选，再建立记录；下面把这三个动作分别观察，重点理解每一步新增了什么事实，以及哪些事实还没有成立（图 2.5 ）。

第一次提交前，HEAD已经可以指向预定的分支名，但这个名字尚未解析到一个提交。图 2.4 把提交前后的状态并列展示。提交建立后，分支名才有具体目标，提交再通过树与文件内容对象描述快照；A、T、B仅为对象的示意名称。

创建文件，观察未跟踪状态

在刚才的仓库内执行：

创建课程笔记的说明文件
printf '# Git learning notes\n' > README.md
cat README.md
git status

README.md 是普通文本文件。.md 表示常用 Markdown 格式，本章无需掌握 Markdown 语法；开头的 # 仅文件中的一个字符。由于文件尚未纳入 Git 的跟踪范围，status 应把它列为未跟踪文件。

未跟踪不表示文件丢失，也不表示 Git 无法读取它；含义是 Git 尚未把这个路径加入后续版本管理。此时文件只存在于工作目录中。关掉终端不会删除它，但也没有任何提交可以替它保存历史。

暂存：明确下一次要提交什么

把 README.md 加入本次提交候选内容
git add README.md
git status

add 后，status 应将 README.md 列入待提交的变化。这里引入一个术语：索引，也称暂存区，它记录下一次提交的候选内容。现在只需把动作理解为“选择这一版 README.md 作为待提交内容”。第 3 章将通过三份内容对照解释其精确含义。add 通常不输出成功提示。应通过 status 检查结果，而非重复执行直到出现文字。此时还没有提交：暂存只准备候选内容，尚未产生一条新的历史记录。

第一次实验明确写出文件名，不立刻使用 git add .。后者可以一次暂存目录范围内的多种变化，但学生需要先学会判断究竟哪些路径被纳入。提交范围应由意图决定，不能只图输入方便。

提交：保存选定状态并写下理由

创建并查看第一次提交
git commit -m "docs: create learning notes"
git log -1 --oneline
git status

commit 根据索引创建提交；-m 后面的字符串提供提交说明。本例说明采用英文，是为了保持跨终端显示一致；中文说明也可以使用。docs: 是一种可选的说明约定，不是 Git 强制语法。

提交输出通常包含当前分支、提交标识的缩写、说明，以及涉及的文件与行数。第一次提交还可能带有 root-commit 标记，表示它没有父提交。git log -1 --oneline 只显示最近一次提交，并把输出压缩成一行。最前面的一串十六进制字符是提交标识的缩写，不要求与你的同学相同。

最后的 status 应显示没有待提交变化，工作区干净。这个结果表明当前比较范围没有Git需要报告的待提交变化；目录仍可以包含已跟踪文件和其他资料。被忽略文件等特殊情况仍可能存在，不能把“干净”理解为文件系统中任何内容都已备份。图2.6给出本节所用的结构与关系示意。阅读时请结合前述对象与操作区分各元素的含义。

第二次修改：历史开始形成

一个提交只能说明“曾经保存过一次”。再做一次修改，才能看到版本之间的联系。

增加一行学习计划，先不暂存
printf 'Goal: understand each change.\n' >> README.md
git status
git diff

>> 在末尾追加一行。status 此时应报告 README.md 已修改，但未暂存。diff 展示内容差异，其中以加号开头的新增行是本次追加的文字；输出头部的路径和行号将在第 3 章细读。

请先回答：如果现在不执行 add 就直接提交，这条新增内容会进入下一次提交吗？在本例中不会。文件曾经被跟踪，不代表所有未来编辑都会自动成为候选内容。需要再次暂存这一版文件。

保存第二次修改
git add README.md
git diff --cached
git commit -m "docs: add a learning goal"
git log --oneline
git status

git diff --cached 查看索引相对当前提交的差异，也就是本次准备提交的变化。每次提交前查看这一份差异，是确认提交范围的直接方法。

现在 log 应显示两条提交，较新的通常位于前面。Git在内部保存了两个项目状态及其联系，历史版本可通过提交访问，无须为工作文件增加“最终版”等后缀。工作目录仍只有一个当前的 README.md，历史查询则可以找到先前状态。

在工作区与索引已经一致的前提下，普通提交把所选快照记录到新的提交中（图 2.7 ）。图示比较记录前后的内容，提醒读者区分文件没有继续改变与历史新增了一条记录。

只读查看上一次提交中的文件
git show HEAD:README.md
git show HEAD~1:README.md

这两条命令不会替换工作文件。HEAD 在此表示当前提交，HEAD~1 表示沿第一父链向前一代。冒号后接提交中的文件路径。第一条应显示两行，第二条只显示最初的标题。修订名称的完整规则在第 4 章介绍，此处用它验证“旧内容确实仍可查询”。

把无关文件排除在提交之外

项目目录里可能有编辑器临时文件、缓存和个人配置。这些文件不一定适合共享。.gitignore 用来定义忽略规则，主要影响未跟踪文件的发现与添加（图 2.8 ）。

忽略学习过程中的临时文件
printf 'scratch.tmp\n' > .gitignore
printf 'temporary notes\n' > scratch.tmp
git status --short
git check-ignore -v scratch.tmp

此时，普通状态会列出规则文件 .gitignore，但不列出已经被忽略的临时文件。check-ignore -v 显示哪一条规则生效，帮助区分“文件真的不存在”和“文件被规则隐藏”。.gitignore 本身是要共享的规则文件，可以像 README.md 一样提交。

把忽略规则保存到历史
git add .gitignore
git commit -m "chore: ignore scratch notes"
git status --ignored --short

最后的状态检查会把忽略项也列出来，scratch.tmp 前可能出现 !!。它仍在磁盘上，仅没有纳入本实验的提交。不要把密钥写进文件后再期待忽略规则自动清除历史；已经跟踪的文件不会因为后来匹配忽略规则就自动停止跟踪，历史中的内容也不会消失。第 3 章会通过反例说明已跟踪文件与忽略规则的关系。此处的原则是：先决定哪些内容应该进入仓库，再执行暂存与提交。

另一种起点：克隆已有仓库

init 是从本地空历史开始；clone 是从已有仓库取得一份本地仓库。为避免依赖网络，我们使用本章刚完成的仓库作来源。以下命令从其上一级目录执行：（图 2.9 ）

用本地仓库练习克隆
cd ..
git clone git-lab-02 git-lab-02-copy
cd git-lab-02-copy
git log --oneline
git remote -v

clone 的第一个参数是来源路径，第二个参数是新目录名。此操作创建另一份本地仓库，通常自动配置来源别名 origin，并检出默认分支。未跟踪和被忽略的 scratch.tmp 不会因为位于来源目录就自动进入克隆。

普通克隆通常取得服务器或来源仓库向本次操作提供的历史，但不能把它等同于完整备份：未提交文件、其他人的本地记录、reflog、平台议题和某些外部文件存储并不会自动包含。浅克隆和部分克隆还会主动限制历史或对象范围。第 7、14、15 章将分别解释传输、规模化和备份。完成观察后，可以保留两个目录。下一章使用自己的新实验目录，不依赖本章是否做过克隆或忽略练习。

初次操作失败时，先检查什么

表2.2给出本节所用的比较项目。使用时应同时核对前述适用条件（图 2.10 ）。

表 2.2 首次提交中的常见现象与排查起点
现象应先检查的事实
提示不是 Git 仓库用 pwd 确认目录，再检查是否已经初始化；不要在错误位置盲目再 init
提交提示身份未知查询当前仓库 user.name 与 user.email，确认配置成功
提交提示没有变化用 status 检查文件是否已保存、是否暂存、是否被忽略

排查时只改变与问题有关的一项条件。若同时重装程序、删除仓库、修改全局配置，可能让问题暂时消失，却失去理解原因的机会。Git 的报错首先是状态信息，读懂它有助于选择下一步，而非看到错误就重新开始。

实验拓展：辨认目录、仓库与生效配置

命令可能在不符合预期的位置执行，也可能读取更高层配置。拓展实验先辨认目录与管理边界，再核对生效来源，为多项目并行工作建立清晰起点。

为什么先查位置，再查设置

同一终端窗口可以先后进入多个目录，而 Git 会根据当前位置寻找仓库。编辑器中打开的项目与终端的当前目录也可能不同。因此，看到“不是 Git 仓库”的提示时，首先应确认目录；看到身份设置不符合预期时，则应进一步确认配置来源。把两类问题混在一起，容易在错误目录初始化一个并不需要的仓库。

以下是独立实验，使用新建的 inspect02 目录，不接续前面的学习仓库。姓名和邮箱是教学占位信息，仅写入本仓库配置。实验关注配置如何覆盖和如何查询，不涉及平台认证。

建立可定位的实验仓库
mkdir inspect02
cd inspect02
git init -b main
git config --local user.name "Git Learner"
git config --local user.email "learner@example.invalid"
pwd
git rev-parse --show-toplevel
git rev-parse --is-inside-work-tree
git config --show-origin --get user.name
git -c user.name="Temporary Learner" config --get user.name
git config --get user.name

pwd 由终端解释器提供，显示当前工作目录；--show-toplevel 由 Git 给出工作区顶层目录，两者在仓库子目录中可能不同。--is-inside-work-tree 用来判断当前位置是否属于工作区，不能据其结果推断仓库是否已经有提交。最后三项查询分别观察本地配置来源、单次命令覆盖和覆盖结束后的值。

-c 设置只影响本次 Git 调用及其传递的相关上下文，不会把新值写回本地配置文件。最后一次查询应重新得到 Git Learner。若读者只看中间输出，可能误以为身份已被永久修改；通过前后对照才能证明设置的作用范围。

没有提交时，分支名为何仍然存在于提示中

初始化仓库后，Git 可以记录 HEAD 将指向的分支名称，但对应分支引用尚未指向任何提交。此时不能把初始化理解为已经产生一个空白版本。可以创建第一份内容，再观察提交前后的区别。

从尚无提交到具有历史入口
if git rev-parse --verify HEAD; then
  echo "Unexpected initial commit" >&2
  exit 1
fi
printf '# Environment notes\n' > README.md
git add README.md
git diff --cached --stat
git commit -m "docs: record the environment entry"
git rev-parse --verify HEAD
git log -1 --format='%h %s'
test -z "$(git status --porcelain)"

这里将第一次查询放在条件语句中，是为了明确表示预期失败，而非忽略错误。提交前查询 HEAD 失败，提交后查询成功，说明历史入口已经从计划中的名称转变为可解析的提交。test 是终端命令，用退出状态检查工作区是否干净；没有输出且退出成功才符合预期。

环境问题的分层诊断

程序、编辑器、提交身份与远程认证分别承担不同职责。出现失败时，先确定停止的阶段，再检查对应条件，通常比重新安装全部工具更有针对性。

程序找不到与仓库找不到

终端提示找不到 git，通常意味着当前命令搜索路径中没有对应可执行程序。此时检查安装位置和终端启动方式，比重复初始化更有意义。若 Git 可以输出版本，却提示当前位置不是仓库，则说明程序启动正常，应检查目录和仓库边界。这两个层次应按先后顺序排查。

图形客户端内置的 Git 与终端 Git 可能来自不同安装路径，版本和凭据组件也可能不同。报告问题时至少记录操作系统、终端类型、Git 版本、当前目录和原始错误。截图可辅助说明，但可复制的错误文字更便于搜索和核对。

编辑器没有退出与提交没有完成

某些命令会启动文本编辑器并等待其退出。终端暂时没有出现新的提示符，并不意味着程序失去响应。初学者应先辨认是否进入编辑器，再按编辑器的保存退出方式完成操作。使用图形编辑器时，还要确认命令行启动器是否等待窗口关闭；否则 Git 可能在说明文件尚未编辑时继续执行。

环境排查应对准失败的对象（图 2.11 ）。配置提交姓名不会自动授予远端写权限，重新安装程序也不能解释错误的当前目录。

本书在可复现实验中经常使用 -m 提供简短说明，以减少环境差异。但正式项目中的复杂说明仍可使用编辑器撰写。应理解两种方式服务于相同的提交信息输入过程，而非认为 -m 是提交的必要条件。

认证失败与提交身份错误

user.name 和 user.email 影响提交元数据，不提供服务器访问凭据。访问私有仓库时，服务器还会根据连接方式检查令牌、SSH 密钥或其他凭据。把邮箱改成平台账号邮箱，可能有助于平台关联展示，但不能据此获得读取或推送权限。

排查时先判断失败发生在哪个阶段：本地提交尚未创建，还是远程访问被拒绝。前者检查身份与编辑器，后者检查地址、连接协议、账号和授权范围。错误发生层次不同，修复措施也应不同。

迁移任务：为另一台计算机准备环境说明

请编写一份不依赖截图的安装与验证记录，包含安装来源、版本查询、学习目录、编辑器设置、身份作用域和一次成功提交的证据。不要在记录中写入令牌或私钥。若某一步必须由使用者自行选择，说明选择依据而非只给一个结果。

评价重点是另一位读者能否据此判断自己处于哪个步骤。例如，“安装完成”缺乏验证依据；“在新终端中运行版本查询，并记录可执行程序位置”则同时覆盖安装结果和环境来源。配置文件内容可作为证据之一，但最终仍应以 Git 实际读取到的生效值为准。

图形界面与命令行的对应阅读

界面可以降低观察成本，但按钮名称不能替代状态模型。下面把文件列表、候选差异和历史图分别对应到Git查询，使学生更换工具后仍能解释结果。

两种界面面对同一套状态关系

图形客户端可以用文件列表、差异面板和提交图展示仓库，帮助初学者观察变化；命令行则便于精确记录参数和复现步骤。两种入口可以相互验证。学习时应先理解界面展示的对象，再把按钮动作对应到实际状态变化。高见龙的公开教材也强调以概念理解支持界面操作(高見龍 2026)。

不同工具的界面名称和默认操作可能不同。例如名为“同步”的按钮可能组合获取、整合和推送，名为“提交所有”的按钮也可能自动暂存某些内容。因此，不能只依据按钮文字判断影响范围。应查看工具说明、操作预览及执行后的文件和引用状态。

一次提交应观察哪些区域

打开新建学习仓库以后，先确认客户端显示的路径与终端所处仓库一致；再创建一份文本文件，观察未跟踪列表；选择暂存后，观察候选列表与差异；创建提交以后，查看历史与工作区状态。每一步只完成一个目的，避免使用批量自动操作掩盖中间状态。

如果工具支持部分暂存，可以在文件中制造两处相距较远的修改，只选择其中一处，然后用 git diff 与 git diff --cached 分别核对。界面中的勾选结果应与索引实际内容一致。若工作文件后来继续编辑，界面也应能展示已暂存和未暂存两个比较范围。

提交图需要读懂连线含义

图形历史通常把提交排列在若干视觉轨道上，以便展示父关系。轨道颜色不是 Git 对象固有属性，也不必一一对应永久分支。一个分支名称可以随新提交移动，分支被删除以后，相关提交仍可能由其他入口访问。不能把图上的某条彩线当作独立复制的文件集合。

读图时先定位当前分支、HEAD 和目标提交，再看父关系。对于合并提交，注意它连接了哪些父提交；对于快进，注意名称移动而没有新建双亲整合点。必要时使用命令查询父标识进行核对。图形展示提供认知辅助，父关系才是历史判断依据。

从界面错误返回可复制证据

遇到失败时，应记录完整错误文字、操作目标、当前版本和目录。若工具提供执行日志，可据此辨认它实际调用了哪些操作。不要只写“按钮不能用”，也不要在不清楚原因时连续点击重试。重复操作可能改变现场，使原有问题更难解释。

本节练习不要求安装某个特定商业客户端。读者可以使用自己已有的工具，填写一份界面与状态对照记录：界面区域显示什么，操作改变什么，终端查询如何证明。若某个按钮包含组合动作，应逐项拆开解释。评价关注模型理解，而非对某一版本界面位置的记忆。

本章小结

本章完成了一个不依赖远程平台的版本记录过程：先确认程序可用，再在明确目录初始化仓库；配置提交身份，创建文件；用 add 选择候选内容，用 commit 保存版本，用 status、diff 和 log 检查结果。

理解操作时，应分别确认以下事实：文件存在不表示已跟踪，已跟踪不表示最新编辑已暂存，已暂存不表示已有提交，已有提交也不表示已经共享或完成备份。下一章将把这些区别放到工作区、索引和 HEAD 三份状态中解释。

应用2.1在一个全新目录中完成两次提交。第一次只写标题，第二次增加计划。提交最近两条历史和最终 status 的结果，并说明为何不要求哈希与教材相同。＋

考查知识点 · 初始化 / 根提交 / 第二次提交

在新目录init，创建标题并add、commit；追加计划后再次add、commit。提交log最近两条与status结果。哈希受内容、父项、身份和时间等字段影响，不要求逐字相同；要核对两次意图、父关系和最终候选状态。

验收时读取第二个提交的父字段，确认它连接第一个提交，再分别查看两棵树中的文件。最终工作区干净说明本次选定变化已记录；它不能代替对两次提交是否具有正确目的和内容的检查。

应用2.2同学已经配置了 GitHub 登录，提交时仍提示作者身份未知。这两种配置有什么不同？应查询哪两项设置？＋

考查知识点 · 配置作用域 / 提交身份 / 平台认证

GitHub登录验证平台访问身份，提交作者字段由本地Git配置写入。查询user.name与user.email，并使用show-origin确认生效来源；按需要修正仓库级配置。登录浏览器不会自动为所有本地仓库补齐作者配置。

可使用git config --show-origin --get user.email判断值来自哪个文件，再决定采用仓库级还是用户级配置。实验仓库中的合成身份用于演示；正式项目应由本人确认邮箱及公开范围，避免把浏览器登录当作本地配置来源。

应用2.3新建文件后直接运行 commit，提示没有待提交内容。列出至少三种应检查的事实，并按检查成本排列顺序。＋

考查知识点 · 当前目录 / 跟踪状态 / 候选内容

先用pwd或仓库根查询确认位置，再用status确认文件名、保存状态和跟踪状态，接着查看候选差异；必要时检查是否被忽略、是否存在其他仓库边界。新文件未add时，普通commit不会自动选择它。

诊断应从低成本事实开始，先确认命令在正确仓库执行，再确认编辑器已保存，最后检查文件是否进入索引。若路径命中忽略规则，使用check-ignore说明命中的文件和行号，比反复运行commit更容易定位原因。

应用2.4在 add 后、commit 前查看 log，新增的版本为什么还不存在？应使用什么命令检查本次候选变化？＋

考查知识点 · 暂存 / 历史查询 / 未诞生分支

add更新候选而未建立提交，log只读取已有历史。使用git diff --cached检查候选与HEAD的差异，使用git show :路径直接读取索引内容；尚无HEAD时按初始化情境解释命令结果。

尚无首次提交时，日志查询可能因没有可遍历入口而失败，这是该初始化状态的正常结果。git diff --cached仍可检查准备记录的新文件。报告应把命令失败原因与“Git未安装”“目录无权限”等环境问题分开。

应用2.5把一个临时文件加入忽略规则，验证文件仍在磁盘上、不会出现在普通 status 中。写出证据，不要只给规则文本。＋

考查知识点 · 忽略规则 / 未跟踪文件 / 规则来源

创建未跟踪临时文件，增加匹配忽略规则，然后用文件读取或存在性检查证明文件仍在；普通status不列出它，再用git check-ignore -v确认命中规则。不要对已经跟踪的文件套用同一结论。

完整验证包含三项事实：磁盘文件仍存在，普通状态输出省略该路径，规则查询指出命中来源。若文件此前已经跟踪，应另行说明其候选和历史变化；忽略模式的匹配结果不能抹去已有跟踪关系。

应用2.6完成本地 clone，比较两个仓库的历史与文件。说明为什么原仓库的临时文件没有出现在新目录中。＋

考查知识点 · 克隆 / 受跟踪快照 / 未提交现场

克隆后比较可达提交、提交树和受跟踪文件。原仓库的忽略临时文件没有进入所选提交，因此普通clone不会传送它；克隆不是复制整个工作目录，也不会复制所有本地未提交现场。

可在原仓库故意保留一份未跟踪草稿，随后从新克隆查询同一提交树。两边相同的是指定版本中的受跟踪内容；本地配置、临时文件和未共享入口可能不同。比较时应明确对象范围，避免机械比较整个目录字节。

应用2.7你准备在线提交课程作业。哪些身份信息会进入提交历史？为什么示例邮箱不应原样用于需要关联个人贡献的正式仓库？＋

考查知识点 · 作者与提交者 / 邮箱 / 隐私

提交一般记录作者与提交者姓名、邮箱及时间等元数据，平台可以据邮箱等条件关联账户。示例邮箱仅用于合成实验，不能代表实际贡献者；正式使用应选择自己确认的身份或隐私邮箱。

作者字段与提交者字段可能不同，平台归属还受到邮箱关联等规则影响。课程报告应使用实际产生的提交元数据核对；需要隐私保护时选择平台提供并经本人确认的隐私邮箱，不应借用教材作者的姓名或地址。

基础2.8解释“工作区干净”为什么不能推出“目录中所有文件都已备份”。至少给出一个本章实际观察到的反例。＋

考查知识点 · 干净状态 / 忽略内容 / 备份范围

干净状态主要说明相应比较范围没有需要报告的受跟踪变化；被忽略文件可能仍在磁盘且未进入历史。例如临时文件被规则忽略后status仍干净，它却没有出现在新克隆中。备份还要列出这些资料。

可以用忽略的临时文件作为反例：文件依然可读取，status却保持干净。进一步说明，备份清单应包含需要保存的未跟踪资料，仓库历史与工作草稿可采用不同方式保全，恢复时分别验证。

应用2.9两台计算机显示不同Git版本，同一台计算机在两个终端中又得到不同邮箱。请设计检查顺序，区分可执行程序路径、配置作用域、配置来源与当前仓库位置，并说明应保留哪些输出。＋

考查知识点 · 安装环境 / 可执行程序 / 配置来源

先记录系统、终端及git --version，再查询shell实际选择的Git程序，排除不同安装入口。随后确认当前项目根目录，读取user.name、user.email及其show-origin结果，判断仓库级、用户级和其他配置是否覆盖。不同终端还可能继承不同环境条件。

修正应针对实际来源，不宜先删除所有配置。验收至少包含程序路径、版本、当前目录与生效配置来源，且在同一实验仓库重查结果。邮箱差异属于提交元数据配置，不能单凭浏览器账号状态推断其成因。

应用2.10初始化后能看到.git却无法显示最近提交；另一个项目的.git是文本文件。分别解释这两种现象可能成立的条件，说明如何用Git提供的查询确定管理目录，哪些信息不能仅凭文件夹外观判断。＋

考查知识点 · .git入口 / 初始化状态 / 路径查询

初始化可以先建立HEAD和管理结构，首次提交尚未产生时，没有可供日志遍历的当前提交，这是未诞生分支的正常情形。HEAD的符号名称与其目标提交是否存在，应分别查询。

.git文本文件可能指向关联工作树或子模块的实际管理目录。可使用rev-parse的管理路径查询核对，进一步观察公共目录。是否拥有完整历史、是否存在有效候选和当前分支指向什么，都需要相应查询；仅看图标不能确定这些事实。

综合2.11实验室需要让三位同学在不同系统上取得同一课程资料。现有目录混有源码、构建结果和临时草稿，其中一台机器作者配置缺失。请制定接入步骤并完成两次有明确意图的提交；从新目录克隆验收，说明哪些文件应交付、哪些应另行保全及如何证明。＋

考查知识点 · 环境接入 / 首次提交 / 忽略 / 克隆验收

先确认Git程序和仓库根目录，按实验需要设置本人确认的提交身份，再列出源码、构建结果、草稿三类内容。对尚未跟踪的生成产物设置忽略规则，草稿按需要另存；第一次提交建立可阅读基线，第二次记录一项独立课程修订。每次提交前检查候选，提交后读取历史和文件。

从新目录克隆，核对两次记录、最终受跟踪内容和必要资源；被忽略的生成结果不应被误当作缺失源码。报告列出实际系统、版本、配置来源、提交意图和未入历史资料的保存位置。若克隆后不能按说明阅读或构建，应定位依赖缺口并修订交付清单。

建议先复制保全原目录，列出源码、生成物和草稿三类路径，再在专用练习仓库配置身份与忽略规则。第一项提交建立可构建的源码基线，第二项提交补充规范说明及必要资料；分别检查候选，避免把目录清理和业务修改混为一次提交。在全新目录克隆后，核对两个提交的树、身份字段和说明，重新构建并比对交付清单。跨系统差异应记录为环境条件，草稿另行归档，不能依赖忽略规则保存。
