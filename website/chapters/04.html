CHAPTER 04 · 基础篇

历史查询与版本溯源

张庆科 编著约 42 分钟13 道分层习题

资料保存下来之后，新的问题随之出现：一条要求何时加入？某行文字为什么改变？哪个版本开始出现错误？本章从这些具体问题出发，建立“提出问题、选择范围、阅读差异、验证判断”的历史查询方法。

学习目标：能组合 log 的范围、筛选与输出；能区分提交集合与两个端点的文件比较；能用修订记号和 show 读取历史；能结合 blame、差异和背景解释一次变更；能准备稳定判定并通过 bisect 定位首次出现问题的提交。

查询问题 →\rightarrow 提交与父关系 →\rightarrow log 范围和筛选 →\rightarrow show 与文件演化 →\rightarrow blame 线索 →\rightarrow bisect 验证 →\rightarrow 证据整理。

先把问题改写成可查询的条件

查询命令的入口取决于要回答的问题。图 4.1 把提交历史、指定版本内容与文本差异放在不同观察位置：先确定对象和范围，再选择输出形式，才能使查询结果与问题对应。

“看看历史”没有明确结束条件。“找出哪次提交把答疑时间从周一改到周二”则包含路径、内容和变化方向，能够用查询逐步缩小范围。查询前先写一句自己需要回答的问题，再选择工具，通常比试完所有选项更有效。

历史查询有三个层次。第一层选择从哪些提交出发沿父关系遍历；第二层按作者、说明、时间、路径或补丁条件筛选；第三层决定显示一行摘要、元数据、统计还是完整差异。选项属于哪一层，决定它如何影响结果。

例如 log 的默认入口是当前 HEAD，并不自动遍历仓库里每一项不可达对象。--all 把所有引用加入入口，包括本地分支、远程跟踪引用和标签等。它也不等于恢复所有已经失去引用的旧对象；救援需要第 8 章讨论的 reflog 等线索。

提交顺序与时间顺序

提交有父关系，也有记录的时间。两位协作者可能在不同机器上工作，时钟也可能不一致；作者时间与提交者时间还可能因拣选、变基而不同。因而“日志上一行较新”不总能推出“它是下一行的直接子提交”。判断祖先关系，应读取父标识或图中的连线。

log 的显示顺序可以调整。--date-order 尽量结合时间与拓扑约束，--topo-order 保持适合阅读分支的拓扑顺序。它们改变呈现，不修改对象父关系。调查故障时，记录完整提交标识比只记某个日期更可靠。

说明搜索与内容搜索

--grep 回答“哪些提交的说明提到了 schedule”；它能否找到真正修改安排的提交，取决于提交说明是否写了这个词。-S 和 -G 改为检查补丁，适合说明不充分的仓库（图 4.2 ）。

-S 关注字符串计数变化。如果同一次改动把一处字符串移走、又在另一处加入相同字符串，计数不变，查询可能不匹配。-G 关注差异增删行是否匹配正则；即使计数不变，只要匹配行被改动，也可能列出该提交。使用哪项，应由问题是“何时引入或移除”还是“哪些匹配行发生变化”决定。

Git 的正则选项不是任意编程语言的正则语法。例如使用可移植的数字范围 [0-9] 往往比假定所有模式都接受反斜线 d 更稳妥。shell 引号又先于 Git 解析，包含空格或特殊字符的模式应正确引用。

摘要是目录，补丁才是内容证据

表4.2给出输出粒度的选择。一行摘要适合定位，统计适合判断规模，完整补丁适合解释实际变化。不要从“修复问题”的说明直接推断修复正确。

自定义格式中的 %h 是缩写标识，%H 是完整标识，%an 与 %cn 分别是作者和提交者名称，%aI 与 %cI 是严格 ISO 8601 风格的对应时间。报告可以保存完整标识与说明，屏幕浏览则使用短格式。元数据是记录，不是密码学身份保证。

修订记号与范围的两种语义

修订范围首先是一种提交集合运算。图 4.3 中，两个圆分别表示从A、B可达的提交集合；双点号选择仅从B可达的部分，三点号选择两端各自独有的部分。这里说明的是git log的提交选择，不能把同一图示直接套用于git diff的文件比较。

HEAD 表示当前位置；普通分支上通常通过分支引用解析到提交，分离状态下直接表示当前提交。HEAD~2 沿第一父链走两步；HEAD^2 选择第二个父提交。线性提交只有一个父提交，不能因为要看“两代以前”就使用第二父记号（图 4.4 ）。

图4.5使用“子提交指向父提交”的箭头。E 的第一父是 M，M 的第一父是 B、第二父是 C。因此 E 的两代第一父是 B，而先走一代再选第二父会到 C。图中的左右排列只为阅读服务，真正决定关系的是箭头与父编号。

log 中的两点范围是集合差

对 log 而言，A..B 表示“从 B 可达、从 A 不可达的提交”。A、B 并不一定在线性历史上，也不要求 A 是 B 的祖先。比较本地与远端时，这个集合定义能清楚表达哪一侧有对方尚未包含的历史。

A...B 表示两个可达集合的对称差，即只被一侧包含的提交。配合 --left-right 可以标记提交属于哪一侧。共同祖先不在这个结果中。范围选择首先是图上的可达性运算，然后才叠加时间或路径筛选。

diff 中的两点与三点是文件比较

对 diff 而言，A..B 通常与 A B 一样，比较 A、B 两端的树；并不是“把 log 列出的每个提交补丁相加”。diff A...B 则从 A、B 的合并基线比较到 B，带有方向性。将 A 与 B 对换，三点比较的终点也变了。

因此，log A...B 和 diff A...B 虽然长得相同，问题却不同。前者问两侧独有的提交有哪些，后者问 B 相对共同基线改了什么。在 PR 中常用的分支变化视角，应先确认平台实际比较方式，再解释页面上的差异。

show、文件历史与逐行线索

show COMMIT 可以显示提交信息和差异；show COMMIT:path 则直接读取该版本中路径的文件内容。后者不会切换当前分支，也不会改写工作区，是查看历史文件的轻量方法。路径以仓库内部路径理解，重命名后旧版本仍需要使用当时的路径（图 4.6 ）。

对于普通提交，补丁通常相对其父提交；合并提交具有多个父，显示模式会影响你看见的差异。调查某次合并引入了什么，可以显式比较第一父与合并结果，也可以分别查看相对各父的变化。默认输出不展示某些行，不代表没有文件变化。

blame 找到最后一次相关行变更

blame 把文件当前行关联到历史提交，帮助回答“这行最后经由哪个相关变化形成”。它不直接回答需求是谁提出，也不保证列出的作者对整个功能负责。格式调整、代码移动和历史重写都会影响线索的呈现。

看到一行归属后，正确下一步是 show 对应提交，阅读上下文及说明，再追查需求或评审。若该提交仅统一缩进，可继续追溯前一版本，或在团队约定下使用忽略特定格式提交的选项。忽略清单也应记录理由，避免把真正的逻辑改动一并隐藏。

blame 的学习目的在于理解，不是追责。把输出当成责任清单，会促使人回避合理重构，也容易把最后修改者与最初设计者混淆。专业的调查报告区分“可证实的变化”和“需要补充背景的解释”。

完整实验：从资料变更到故障提交

本实验需要 Git、Bash 和文本编辑工具。将创建六次连续提交，第三次故意把答疑安排写错，后续提交修改其他内容。这样可以区分“最近一次提交”与“首次引入问题的提交”。所有命令在新目录按顺序执行。

准备具有明确故事的历史

建立资料查询实验的初始状态
mkdir lab04-history
cd lab04-history
git init -b main
git config user.name "Git Learner"
git config user.email "learner@example.invalid"
mkdir docs
printf '# Course\n\nOffice hours: Tuesday.\n' > docs/course.md
printf '# Notes\n\nRead the course first.\n' > README.md
git add .
git commit -m "docs: establish course and office hours"
git tag history-good

起始版本的已知正确条件是答疑在周二。标签 history-good 是本实验保存的边界，不等于工具自动知道它正确。现实中这个判断可能来自上一次验证通过的版本、用户反馈或可重复测试。

增加独立修改并引入一个受控错误
printf '\nInspect each staged change.\n' >> docs/course.md
git add docs/course.md
git commit -m "docs: explain inspection before commit"
printf '# Course\n\nOffice hours: Thursday.\n\nInspect each staged change.\n' > docs/course.md
git add docs/course.md
git commit -m "docs: revise course arrangement"
git tag history-introduced
printf '\nThe notes follow the course.\n' >> README.md
git add README.md
git commit -m "docs: add reading order"
printf '\nKeep one purpose per commit.\n' >> docs/course.md
git add docs/course.md
git commit -m "docs: add commit guideline"
printf '\nRecord questions before practice.\n' >> README.md
git add README.md
git commit -m "docs: describe question collection"
git tag history-bad

现在主线共有六次提交，末尾版本存在错误。为了核验，我们在教学环境中额外保存 history-introduced；正式定位时不要把它作为输入。这相当于教师知道答案，但学生仍须通过稳定判定寻找答案。

用说明、路径与内容逐步缩小范围

对同一个问题使用不同筛选
git log --oneline --all
git log --oneline --grep="arrangement"
git log --oneline -- docs/course.md
git log --oneline -S "Thursday" -- docs/course.md
git log --oneline -G 'Office hours: (Tuesday|Thursday)' -- docs/course.md

第一条建立全貌，第二条依赖说明文字，第三条排除只修改 README 的提交。-S Thursday 应命中首次出现周四的那次变化。-G 的结果还可能包含根提交加入周二安排，因为新增行同样匹配正则；查询结果需要按问题进一步解释。如果以为 -G 只搜索“从周二改成周四”，就把正则的含义扩大了。它只判断增删行是否匹配模式，并不理解课程安排的业务规则。

阅读候选变化和变更前后的文件
git show --format=fuller history-introduced -- docs/course.md
git show history-introduced^:docs/course.md
git show history-introduced:docs/course.md
git blame -L 1,5 -- docs/course.md
git log --format='%h | %aI | %an | %s' -- docs/course.md

对照 show 的补丁和两个完整文件，可以证明周二被改成周四。blame 则指出当前答疑行关联到引入错误的提交。作者身份、日期与说明可以帮助继续调查，却不能仅凭这些字段推断现实身份已被认证。

让比较回答确切的问题

区分提交集合和树的比较
git log --oneline history-good..history-bad
git diff --stat history-good history-bad
git diff history-introduced^ history-introduced -- docs/course.md
git rev-parse history-bad~2
git rev-parse history-introduced

第一条列出起点之后到坏版本的五次提交；第二条比较两个端点的最终文件树；第三条只显示引入错误那次提交对课程文件的影响。最后两条输出并不相同：在六次提交中，末尾上溯两代是第四次，而错误位于第三次。用实际父链检查，能够避免靠视觉数错行。

bisect：把可重复判断放入历史搜索

人工查看适合小范围解释。当数百次提交之间出现回归时，可以让 Git 按父图选择候选，再由人或程序判断当前版本是好是坏。bisect 只负责安排搜索，不理解“坏”的业务含义（图 4.7 ）。

在简单线性历史且每次判定有效的条件下，每次测试大致减半候选范围，因此测试次数随候选数量按对数增长。真实历史有合并和无法测试的提交，不能机械保证每个项目都恰好测试某个固定次数。更重要的是判定必须可靠，否则更快地缩小范围也可能得到错误答案。

自动判定程序的退出状态

bisect run 将退出 0 视为好，1 到 127 中除 125 之外的状态视为坏，125 视为当前版本无法测试。其他退出状态可能中止运行。命令不存在、环境依赖缺失等执行错误也可能落入“坏”的范围，因此必须先在已知边界验证脚本，不能把任何非零都当作发现业务缺陷。

本实验只检查一个稳定文本条件，不需要网络、编译器或外部服务。程序放在仓库之外，以免 bisect 切换旧提交时把检查器本身换掉。现实项目也可在测试脚本中显式处理无法构建的历史版本。

二分查找依赖同一个可重复判定（图 4.8 ）。编译器缺失、测试环境不完整和业务行为不符是不同结果，应在自动脚本中分开处理，防止环境问题污染定位结论。

准备一个不随检出变化的判定脚本
printf '%s\n' '#!/bin/sh' 'grep -q "Office hours: Tuesday[.]" docs/course.md' > ../check-hours04.sh
sh ../check-hours04.sh

最后一条在当前坏版本上应返回非零；终端通常不输出文字。不要把“没有文字”理解为通过。交互操作可紧接着查看 shell 的退出状态；自动验证会检查它确实失败。

记录原位置并开始定位

从已知好坏边界运行二分定位
git status --short
git bisect start history-bad history-good
git bisect run sh ../check-hours04.sh
git bisect log

start 的参数顺序是坏版本在前、好版本在后。运行时 Git 会检出中间候选，可能进入分离 HEAD。它改变的是当前观察位置；不要误以为正在主线上创建新版本。输出结束后应报告 history-introduced 对应提交为首次坏提交。

bisect 的结论是“按这个测试和这些边界，首次从通过转为失败的位置”。如果测试有随机性，或历史上问题多次引入又修复，解释范围需要更谨慎。搜索结果应再用补丁和复现实验确认。

保存搜索过程并回到原位置
git bisect log > ../bisect04.log
git bisect reset
git branch --show-current
git status --short

reset 结束搜索并回到开始前位置。它在这里是 bisect 子命令，不是第 8 章调整提交、索引与工作区的普通 reset。命令长得相似时，应先识别它属于哪个子命令。

验证测试的两个边界

为了证明脚本确实能够区分正确与错误，在独立的后续观察中分别运行一次，再回到 main。检出标签是观察历史，会进入分离状态；本次不编辑、不提交。

核验正确边界与错误边界
git switch --detach history-good
sh ../check-hours04.sh
git switch --detach history-bad
sh ../check-hours04.sh
git switch main

在 history-good 上应通过，在 history-bad 上应失败。严格操作顺序可以将这项边界自检移到 start 之前；本节把它单列出来，是为了让读者看清判定依据。若边界表现与预期不符，应先修正检查程序或业务假设，再重新进行二分。

有分叉时怎样检索

本章主实验使用线性历史，目的是先排除分支干扰。进入后续章节后，需要区分“某提交是否位于当前分支名下”和“某提交是否是某个位置的祖先”。分支名称可以移动，共同祖先与父链则记录在对象中（图 4.10 ）。

有分叉时，提交集合和树差异可能回答完全不同的问题（图 4.9 ）。明确本次调查究竟寻找哪些记录，还是比较哪两份内容，能够减少对双点号、三点号的误用。

假设主线 main 与 topic 都从 B 出发，main 新增 M，topic 新增 T。log main..topic 只会列出 T；交换方向只会列出 M。合并之后，如果 main 指向包含两侧的新提交，topic..main 将包含主线独有的提交和整合点，但 main..topic 会为空。集合为空表示指定方向没有独有提交，不表示两个名称必定相同。图4.11把查询任务串成一条证据路径。每一步减少一种不确定性：先找候选，再读具体差异，再用行为判断，最后补足背景解释。任何一步都不应被单张日志截图代替。

常见误判与报告写法

没有查询结果可能来自入口选错、路径在历史上变名、筛选过严或当前克隆历史不完整。浅克隆尤其可能缺少需要的祖先；应先确认历史范围，不能据“本地没查到”断言项目从未发生过某变化。

缩写哈希只要求在当前对象集合中能被唯一解析；仓库增长后，原先足够的前缀未必永久足够。交互操作可以使用 Git 自动生成的缩写，长期报告和外部交接建议保存完整标识。标识也不是访问地址：仅知道哈希而拿不到对象所在仓库，仍无法读取内容。

报告建议写成“问题—范围—证据—结论—限制”。例如：“调查答疑时间为何变为周四；范围为 history-good 至 history-bad；内容搜索与二分均指向同一提交，补丁显示周二改为周四；该结论只证明变更位置，是否源于需求调整仍需核对课程记录。”这样的表述比“某人把代码写坏了”更准确，也更利于修复。

案例研读：从错误页面追溯到变更原因

调查不能停在发现某个差异，还需要证明它与观察到的现象有关。本节按复现、范围筛选和上下文阅读组织证据，逐步形成有条件的解释。

把“查历史”改写为三个问题

课程网站中的提交期限显示错误。读者首先应区分：当前文件是哪一版；哪一次变更引入了这段内容；当时为何作出修改。第一个问题可由当前引用与文件状态回答，第二个问题需要历史补丁，第三个问题则可能要结合提交说明、需求单和评审记录。没有任何一条查询命令能够自动回答全部问题。

一次规范的调查可以先固定出错版本，再限定文件路径，最后搜索相关文本。固定版本很重要，因为调查过程中主分支可能继续前进。若报告只写“当前 main”，后来的读者可能无法取得当时观察到的内容。应记录实际提交标识，并说明工作区是否另有未提交修改。

逐行批注为调查提供入口，提交说明与讨论补足变化背景（图 4.12 ）。多项资料应共同支持结论，不能把最后修改者直接等同于现实责任人。

从候选提交走向因果判断

搜索到包含“截止时间”的提交，只能说明该提交的说明或补丁与关键词有关。它未必就是故障来源：可能仅修正文句，也可能是对先前错误的修复。应比较父版本与候选版本，在同一测试条件下确认行为是否改变。

即使自动二分定位得到首个失败提交，也仍需分析原因。该提交可能改变了数据格式，使原有读取程序的隐含假设不再成立；也可能引入了真正的拼写错误。定位回答历史边界，原因分析回答机制。两者结合，才能形成有解释力的故障报告。

实验拓展：验证查询范围的含义

以下独立实验建立一个包含主线和主题分支的历史。两条分支各增加一个文件，因此可以清晰区分提交集合与文件比较。实验只查询历史，不执行合并。

构造两条具有共同起点的历史
mkdir ranges04
cd ranges04
git init -b main
git config user.name "Git Learner"
git config user.email "learner@example.invalid"
printf 'Course baseline\n' > README.md
git add README.md
git commit -m "docs: establish the baseline"
git branch topic
printf 'Main schedule\n' > schedule.txt
git add schedule.txt
git commit -m "docs: add the main schedule"
git switch topic
printf 'Topic exercise\n' > exercise.txt
git add exercise.txt
git commit -m "docs: add a topic exercise"
git log --oneline main..topic
git log --oneline topic..main
git log --left-right --oneline main...topic

main..topic 选择从 topic 可达而从 main 不可达的提交，因而本例只列出增加练习的提交。反向范围列出增加主线安排的提交。三点范围在 log 中表示对称差，左右标记帮助辨认各项提交属于哪一侧。

比较端点与比较主题相对共同起点的变化
git diff --name-status main topic
git diff --name-status main...topic
git merge-base main topic
test "$(git rev-list --count main..topic)" = 1
test "$(git rev-list --count topic..main)" = 1
test "$(git diff --name-only main...topic)" = exercise.txt

直接比较两个端点时，主线独有的安排与主题独有的练习都会造成差异；以共同祖先比较到主题端点时，则只出现主题新增的练习。同样的三点符号在不同命令中服务于不同问题，不能把 log 的提交集合含义直接套到 diff。

历史调查的可复核报告

调查过程应能被另一位读者继续执行。报告把事实、假设、方法和限制分别写清，使提交标识和测试结果能够支持具体判断，并用必要截图补充界面位置。

最小证据应包含什么

报告至少记录观察版本、预期结果、实际结果、复现条件、查询范围和候选变更。若使用自动判定，还应说明退出状态的含义，特别是无法测试某一历史版本时怎样处理。把依赖安装失败直接标为业务失败，可能让二分搜索定位到环境边界而非缺陷边界。

逐行归属信息同样需要语境。blame 通常给出相关行最后一次修改的线索，而非对错误责任作裁决。格式整理、文件移动或历史重写都可能影响线索。适当结合忽略空白、移动检测与旧路径查询，可以帮助调查，但最终仍需阅读上下文和补丁。

何时停止继续缩小范围

若已经获得可重复的失败用例，并能解释候选提交如何改变行为，就具备进入修复阶段的基础。继续追求更短的命令或更漂亮的日志，并不会自动增加结论可信度。应把精力用于验证修复是否覆盖原问题，以及是否引入新的边界错误。

一个合格的学习报告可以用四段完成：现象、定位、原因、验证。每段都应关联实际版本和证据。避免仅粘贴整页日志，让读者自行寻找结论；也避免只给结论而缺少重现入口。

内容检索与附加说明

grep检索内容，log检索变化

如果问题是“当前版本哪些文件含有某个术语”，应从内容搜索开始；如果问题是“这个术语何时加入或删除”，则要检索历史变化。两类任务虽然都可能包含关键词，却具有不同输入和输出。git grep 可以在指定内容范围中搜索文本，历史查询则沿提交关系筛选变化。

在大项目中，先限定目录或文件类型通常更有效。需要引用结果时，应同时记录版本与路径，避免只给当前行号。行号会随编辑变化，而提交与路径组合能够为读者提供更稳定的重现入口。

独立实验：同一关键词在两个版本中的位置

以下实验先创建一份说明，再把相同概念转移到另一文件。它用于说明当前搜索结果与历史变更线索之间的区别。

建立可搜索的两个版本
mkdir search04
cd search04
git init -b main
git config user.name "Git Learner"
git config user.email "learner@example.invalid"
mkdir docs
printf 'Index: candidate content for the next commit.\n' > README.md
git add README.md
git commit -m "docs: define the index briefly"
printf '# Course guide\n' > README.md
printf 'Index: candidate content for the next commit.\n' > docs/index.txt
git add README.md docs/index.txt
git commit -m "docs: move the index definition into the guide"
git grep -n -F 'candidate content' HEAD -- README.md docs
git grep -n -F 'candidate content' HEAD^ -- README.md docs
git log --oneline -S 'candidate content' -- README.md

两个版本都包含相同句子，但路径发生变化。搜索指定树中的内容，可以得到该版本的实际位置；沿 README.md 查询相关文本数量变化，则能看到定义的加入和移出。两类证据互补，不应把一次搜索结果当作完整历史。

notes为已有对象附加说明

有时需要为一个已发布提交补充教学批注，又不希望重写原提交信息。Git notes 可以在独立的 notes 引用下记录附加说明。原提交对象保持不变，附加内容则需要作为另一类数据管理和交换(Git Project 2026)。

notes可以为已有对象补充说明，不必原地改写提交正文（图 4.13 ）。共享时应确认相应引用是否传送，避免把本地可见的注释误认为所有副本都已取得。

附加一条复核说明，并验证原提交未改写
ORIGINAL04=$(git rev-parse HEAD)
git notes add -m "Teaching review: definition moved without changing its wording."
git notes show HEAD
test "$(git rev-parse HEAD)" = "$ORIGINAL04"
git log -1 --show-notes
git show-ref refs/notes/commits

附加说明不会自动进入普通文件树，也不能假定所有克隆默认交换全部 notes。若团队依赖它，应明确获取与推送范围，以及不同成员同时修改时怎样整合。对于必须随普通资料分发的说明，直接写入版本化文档可能更容易被读者发现。

检索结果的引用规范

教材、实验报告和问题单引用仓库内容时，至少给出提交标识、路径和所观察的范围。平台的分支链接方便浏览，但随着分支移动，其内容可能变化；固定提交链接更适合说明一次已经完成的调查。敏感仓库中还应考虑接收者是否具有访问权限。

本节练习：为“术语定义在哪一版发生变化”设计调查过程。参考分析应先搜索当前和目标版本，再查看相关补丁，最后记录变化理由。若文字仅从一个文件移动到另一个文件，报告不应错误地声称概念已被删除。

本章小结

历史查询以可达关系选择范围，以筛选减少候选，以差异和测试建立证据。log、show、blame 与 bisect 分别服务于不同阶段；它们共同帮助解释变化，却不会自动替人理解需求。

先把一个具体问题完整查清，再扩展选项组合。只要能够说明从哪里开始查、比较哪两份内容、依据什么判定以及结论有哪些边界，就已经掌握了历史溯源的基本方法。

本章习题与解析

先独立作答，再展开解析核对思路。答案与教材同源，知识点随题列出。

应用4.1给“看看最近历史”补充可观察的目标，分别设计按说明、路径和内容的查询。＋

考查知识点 · 查询目标 / 日志过滤 / 内容搜索

先给出目标，例如查最近五次提交、查说明含room的提交、查某路径的历史，分别用log限定数量、--grep和路径。内容调查再用-S或-G配合补丁阅读。答案必须明确查询范围与期待找到的事实。

数量、说明、路径和内容回答不同问题，宜逐项加入条件。报告需保留最终命令和命中项的上下文；没有命中时，先撤去最后增加的过滤条件，判断是任务范围不含目标，还是模式、路径或引号写法有误。

应用4.2在主实验中解释 -S Thursday 与 -G 正则结果可能不同的原因，并逐项阅读补丁。＋

考查知识点 · 字符串计数 / 补丁正则 / 差异阅读

-S主要依据匹配字符串出现次数的变化选择提交，-G依据补丁新增或删除行是否匹配正则。文字改写可能保持次数不变而仍有匹配补丁，因此结果不同。逐项读取补丁并说明具体增删，不能只比较提交数量。

可以设计字符串出现次数保持不变、所在行却被重写的修改，观察两个选项的不同结果。正则由Git解释，shell先处理引号；模式中的空格、反斜线和元字符均应按两层解析检查，避免把解析错误解释为历史缺失。

基础4.3说明 log A..B 与 diff A..B 分别操作什么；再解释两个命令中的三点记号为何不能套用同一含义。＋

考查知识点 · 可达提交集合 / 树差异 / 三点范围

log A..B选择B可达而A不可达的提交；diff A..B比较两个端点的树。log三点一般取两侧对称差，diff三点通常比较合并基与右端点。相同标点在不同命令中表达不同范围。

应给出一张实际分叉图并列出集合元素，再独立比较端点文件。提交集合与树差异不能互相推导：两条历史可以得到相同树，同一组补丁在不同上下文中也可能产生不同业务结果。

应用4.4画出一个双亲提交，标记第一父和第二父，并分别求 HEAD~2 与 HEAD^2。＋

考查知识点 · 父次序 / 修订表达式 / 首父链

设HEAD为双亲提交M，第一父为P，第二父为Q；HEAD^2是Q，HEAD~2沿第一父连续走两次，到P的第一父。图上标记父次序，不按屏幕左右位置推断。若相应父链不存在，名称解析会失败。

合并提交中的parent字段顺序提供第一父、第二父的依据。先用rev-list --parents核对，再解释~和^的不同步进方式。若实际历史不足两代，应明确表达式无法解析，不能随意补画不存在的节点。

应用4.5选择 blame 指向的一行，继续读取提交与上下文，列出已知事实和仍需补充的背景。＋

考查知识点 · 逐行归属 / 上下文 / 业务背景

已知事实是当前行与所报告提交的归属关系及该提交中的差异。继续查看提交前后内容、说明和关联讨论；业务要求、作者当时掌握的信息及评审背景可能仍未知。不要把最后修改者自动等同于全部问题责任人。

可将调查材料分为已确认的行变化、待核实的设计原因和关联任务三部分。格式化、文件搬迁或自动生成可能影响归属结果，应进一步比较旧版本；责任判断需要更多组织与需求背景。

应用4.6把主实验的判定改成一个故意永远失败的脚本，说明为何无法据此确认真实故障位置。实验应在独立副本中进行。＋

考查知识点 · 稳定判定 / 好坏边界 / 二分前提

永远失败的脚本无法区分真实好坏，违反稳定判定的前提，得到的位置仅反映错误判定。先在已知正常和失败版本分别验证脚本；本实验在独立副本进行，结束后保留日志并恢复原入口。

先确认脚本在已知好版本返回通过，在已知坏版本返回失败；两者不能区分时不应开始定位。故意错误的脚本可用于说明方法前提，但所得位置必须标为无效演示结果，不能进入真实故障结论。

基础4.7说明 bisect run 如何区分通过、失败、跳过与执行异常。依赖命令缺失时，应该怎样避免误判？＋

考查知识点 · 退出状态 / 跳过 / 执行异常

bisect run把0视为通过，1至127中除125外通常视为失败，125表示无法测试而跳过，其他状态可能中止。依赖缺失应由包装脚本识别，按原因跳过或停止，不让命令未找到的127误判成业务失败。

包装脚本应把依赖不足、构建失败和业务断言失败分类。对于依赖不足，可选择中止调查或明确跳过；无法测试的版本过多时，搜索可能留下多个候选，报告应保留这种不确定性。

应用4.8保存一次二分日志，结束搜索并确认回到原位置，再写出可复现结论。＋

考查知识点 · 二分日志 / 现场恢复 / 复现条件

保存bisect log并记录好坏边界、判定脚本与环境，然后bisect reset，核对当前分支与提交回到预期位置。结论说明在所选边界与判定下定位到何处，遇到跳过或不稳定结果时不能报告唯一确定结论。

除保存bisect log，还应记录判定脚本、依赖版本及运行命令。结束后核对分支和提交，清理生成产物，避免旧二进制影响下一轮测试。同一故障在另一台机器复现时，这些材料提供必要前提。

基础4.9解释为什么长期报告应保存完整标识，以及完整标识仍不能代替仓库和访问条件。＋

考查知识点 · 对象标识 / 仓库来源 / 长期引用

短标识可能随对象增加发生歧义，长期报告应保存完整标识及仓库位置。完整标识仍需实际对象可取得；服务器不提供、权限不足或对象已清除时，摘要不能自行还原内容。

建议记录仓库地址、完整提交标识、目标路径和查询日期。短标识适合屏幕浏览，长期报告则需要足够明确的对象入口；同时要保证仓库或备份确实保存对象，否则标识本身不能提供文件内容。

应用4.10为主实验写一份五段式调查记录，必须将技术变化与业务原因分开。＋

考查知识点 · 调查报告 / 技术原因 / 需求依据

可按现象、边界、方法、证据、结论五段组织。记录具体输入与版本，说明查询和测试如何缩小范围；技术差异是代码变化，业务原因需要需求或讨论证据。最后列出未验证条件与后续动作。

结论应区分“该提交使测试首次失败”与“该改动为何作出”。前者来自测试和历史比较，后者可能需要Issue、评审或设计文档。对无法核实的业务原因保留待查项，避免用推测填补记录。

应用4.11为一个既有提交添加调查说明，同时保持该提交标识不变。说明notes如何保存、普通推送为何未必传递它，以及另一位协作者需要怎样取得和查看同一说明；分析说明被遗漏会怎样影响交接。＋

考查知识点 · notes / 附加说明 / 共享范围

notes通过独立引用组织附加说明，目标提交正文及其标识保持不变。添加后应分别读取目标提交和notes内容，证明正文未被改写。传递说明需要明确相应引用的交换配置或显式范围，不能默认普通分支推送已经覆盖它。

接手者取得notes以后，还需在查询时启用相应显示。交接报告宜记录说明引用、取得方式和目标提交，必要时提供可检索文本副本。只给一个提交标识可能足以定位代码，却不足以保证调查背景同时到达。

应用4.12同一调查在两位同学电脑上得到不同日志结果。请分别检查时间条件、作者字段、正则和shell引号、路径限定与历史简化，并设计逐项撤除条件的诊断过程，避免立即判断历史被删除。＋

考查知识点 · 日志过滤 / 时区 / 正则 / 路径限定

先确认双方从同一仓库和确切入口查询，再逐项记录日期及时区、作者过滤、模式文本和路径。shell对引号的处理先于Git，正则选项也有各自语法；路径限定可能影响显示的历史范围。

以不带附加过滤的查询建立基线，再逐条加入条件，定位首次产生差异的步骤。最终说明是输入、环境还是实际历史不同，并保留可复现命令。过滤结果为空只对当前条件成立，不能独立证明对象或历史已经不存在。

综合4.13校园卡某版本开始错误允许挂失消费，期间还发生接口重构、格式调整和依赖升级。请制定调查路线：定位相关变化，验证好坏版本的判定程序，区分无法构建与业务失败，完成二分及现场恢复，并给出能供他人复核的结论和未决条件。＋

考查知识点 · 故障调查 / 二分定位 / 环境区分 / 报告

先固定已知好坏提交及仓库来源，使用日志、路径和内容搜索了解候选改动，再在两个边界版本运行同一判定程序，确认它识别的确是挂失规则。构建前清理旧产物；依赖不足或历史版本无法测试时明确分类，选择跳过或停止，避免将工具异常归为业务失败。

完成搜索后保留bisect日志、脚本、运行环境和候选提交的前后差异，再结束搜索并核对原现场。结论只对给定边界与判定成立；若存在多个未测试候选，应列出而不强行指定唯一提交。对业务原因继续查阅需求和评审，区分引入缺陷的位置与作出改动的动机。

调查报告应包含已知好坏提交的完整标识、构建环境、判定程序和每类退出结果的含义。先在两端运行同一判定，证明它能稳定区分规则满足与挂失消费错误，再开始二分。遇到无法构建的候选，应按协议跳过或单独处理依赖，不能将它直接标为业务失败。定位后阅读完整补丁，另做回退或修正对照；最后结束二分，核对原分支与草稿。结论应说明候选范围及仍未排除的环境因素。
