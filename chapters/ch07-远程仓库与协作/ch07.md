# 远程仓库与协作：辅导材料

## 远程协作的状态推理
### 把“远程最新”拆成三个位置
协作者需要同时区分自己的本地分支、本地保存的远程跟踪引用，以及服务器当前分支。远程跟踪引用是本地的一项观察记录；它的名称包含远端简称，并不意味着每次读取时都访问服务器。若另一位成员刚推送，而本地尚未获取，本地记录就可能落后。

这也是为什么比较之前经常需要获取：不是获取操作替用户选择最终内容，而是先更新可用于判断的信息。取得信息以后，再依据前后关系决定快进、合并、变基或暂缓。把这些步骤分开，能使协作决策具有明确依据。

### 跟踪关系提供默认值，不提供持续同步
上游设置帮助某些命令在缺少显式参数时确定比较或交换对象。它不建立持续运行的同步通道，也不会在后台自动完成冲突处理。没有设置上游时，显式写出远端和分支仍可以完成许多操作；设置了上游，也仍须判断目标是否正确。

团队中可能同时存在作者仓库、个人 fork 和课程小组仓库。远端简称只是本地名称，`origin` 并不天然属于某个角色。报告协作问题时，应记录简称对应的地址以及获取、推送方向，必要时遮去地址中的敏感参数。

## 实验拓展：用观察记录证明获取与整合的区别
本独立实验使用本地裸仓库模拟服务器，不要求联网或账号。两个克隆代表两位操作者，每个克隆的身份配置都仅写在本地。


### 建立服务器和两位协作者

```bash
git init --bare --initial-branch=main center07.git
git clone center07.git alice07
cd alice07
git config user.name "Alice Learner"
git config user.email "alice@example.invalid"
printf 'Course baseline\n' > README.md
git add README.md
git commit -m "docs: establish the course"
git push -u origin main
cd ..
git clone center07.git bob07
cd bob07
git config user.name "Bob Learner"
git config user.email "bob@example.invalid"
printf 'Exercise: compare local and remote state.\n' > task.txt
git add task.txt
git commit -m "docs: add the comparison task"
git push origin main
cd ../alice07
BEFORE07=$(git rev-parse main)
OBSERVED07=$(git rev-parse origin/main)
test "$BEFORE07" = "$OBSERVED07"
```


此时 Alice 的本地分支和本地远程跟踪引用仍相同，但服务器已因 Bob 的推送而前进。不能仅凭本地两个名称相同，就认定自己已经取得服务器最新内容。


### 获取后先比较，再明确整合

```bash
git fetch origin
test "$(git rev-parse main)" = "$BEFORE07"
test "$(git rev-parse origin/main)" != "$OBSERVED07"
test ! -e task.txt
git log --oneline main..origin/main
git merge --ff-only origin/main
test -f task.txt
test "$(git rev-parse main)" = "$(git rev-parse origin/main)"
```


获取更新了观察记录，却没有自动将 task.txt 写入当前工作区。随后快进整合才使 main 到达取得的提交，并更新工作文件。这个先后关系为理解 `pull` 提供基础：组合操作仍然包含信息获取与后续整合两个概念阶段。

## 推送拒绝的判断顺序
### 先看目标，再看关系与权限
推送失败可能来自地址错误、权限不足、网络不可用、服务器规则或历史关系不满足要求。若输出说明是非快进拒绝，应先获取并比较双方独有提交；若是认证失败，则应检查凭据和授权。不同错误不能统一用强制推送处理。

即使使用租约保护的强制更新，也需要明确期待的旧值与协作规则。租约只能保护其所表达的并发条件，不能判断被替换历史是否仍被其他成员依赖。共同使用的分支上，追加修正通常更便于保留协作记录。

### 同步完成应由哪些证据支持
一次协作交接应确认：目标分支上的提交是否符合预期；必要内容是否已取得；本地草稿是否另行保留；平台检查与评审是否满足约定。推送退出成功只说明服务器接受了相应更新，不能证明部署已完成，也不能证明其他成员的工作区自动更新。

迁移到 GitHub 时，本章的数据关系仍然适用，新增的是账号、权限、PR、规则和运行记录。第 13 章将把这些机制纳入工作流。读者应始终先解释仓库之间交换了什么，再解释平台怎样组织合作。
