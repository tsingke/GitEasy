# 合并原理与冲突处理：辅导材料

## 案例研读：没有文本冲突，结果仍可能错误
### 自动整合依据什么
一位成员把课程时长由两小时改为三小时，另一位成员把练习安排从三个单元扩展到五个单元。如果修改位于不同位置，Git 可能顺利生成结果，且不会报告文本冲突。但五个单元是否适合三小时，需要课程设计知识来判断。文本整合成功不能证明语义协调完成。

Git 主要依据版本中的文本变化和相关合并机制处理文件，无法自动掌握每项业务约束。合并后的验收应包括文件检查、测试运行和需求核对。对于资料项目，可以检查时间总和、引用编号、目录链接和术语一致性；对于软件项目，还要覆盖接口、数据格式与运行行为。

### 冲突只是需要明确决定的位置
冲突并不等于其中一位成员做错了。两人可能都基于正确但不同的需求修改同一处内容。解决时先恢复共同语境：共同起点是什么，双方分别试图解决什么，最终版本必须满足什么约束。删除标记只是编辑动作，解释选择依据才是整合工作。

对无法独自判断的冲突，应保留双方证据并向相应作者确认。若项目明确授权整合者作决定，也应在提交说明或评审记录中写出理由。选择“当前方”或“对方”是一种内容取舍，不能仅因为按钮名称更熟悉就执行。

## 实验拓展：验证合并提交的两个维度
下面的独立实验让两条分支修改不同文件，并强制保留双亲整合点。它用于分别观察最终文件和历史连接，不制造内容冲突。


### 建立互不覆盖的两项变化

```bash
mkdir evidence06
cd evidence06
git init -b main
git config user.name "Git Learner"
git config user.email "learner@example.invalid"
printf 'Course baseline\n' > README.md
git add README.md
git commit -m "docs: establish the baseline"
git switch -c topic
printf 'Exercise: inspect the index.\n' > exercise.txt
git add exercise.txt
git commit -m "docs: add the index exercise"
git switch main
printf 'Lecture: Wednesday.\n' > schedule.txt
git add schedule.txt
git commit -m "docs: record the lecture schedule"
git merge --no-ff topic -m "merge: integrate the index exercise"
```



### 分别核对内容与父关系

```bash
git show HEAD:exercise.txt
git show HEAD:schedule.txt
git rev-list --parents -n 1 HEAD
git diff HEAD^1 HEAD --name-status
git diff HEAD^2 HEAD --name-status
test "$(git rev-list --parents -n 1 HEAD | wc -w | tr -d ' ')" = 3
test -z "$(git status --porcelain)"
```


最后一项提交具有两个父提交，因此父关系查询的一行包含三个标识：当前提交与两个父提交。从第一个父提交比较到合并结果，看到主题练习的加入；从第二个父提交比较到结果，看到主线安排的加入。这两个补丁并不矛盾，而是比较起点不同。

本例还说明：合并提交不是将两份补丁简单拼接成一个文本文件。它记录完整结果树，并以父关系连接被整合的历史。要检查“哪些主题变化进入主线”，通常以主线侧父提交为比较起点；要调查某一整合决定，则还应结合其他父提交与共同起点。

## 整合后的审阅顺序
### 先检查范围，再检查关键约束
完成合并后，先看变化文件列表，确认没有意外的大文件、生成目录或无关重排；再阅读关键文件补丁，检查冲突位置及其邻近内容；最后运行与需求匹配的验证。范围检查能发现误纳入内容，局部检查能发现不完整解决，运行验证能覆盖部分语义后果。

对于存在格式化工具的项目，应尽量区分纯格式调整与功能整合。否则大量空白差异会遮蔽真正需要审阅的变化。若必须同时调整格式，应在说明中解释原因，并提供便于识别业务修改的比较方式。

### 中止、重试与继续的适用时机
当合并目标选错、前置条件不满足或需求仍不清楚时，中止往往比仓促完成更合适。中止不是抹去所有工作现场的通用命令，其能否完整恢复还受起始未提交变化等条件影响，因此开始整合前应先处理好草稿。

若只是暂时无法判断一处冲突，可以保留现场继续调查；若要开始另一个任务，应先明确当前操作状态，不能在未完成整合的索引上随意推进。可靠流程的核心是保持每个阶段的状态可解释，而不是追求每条命令都立即成功。

## 迁移练习：设计一次语义验收
请为课程时间表设计两项分别合理、合并后却相互矛盾的修改，并写出能检测矛盾的验收规则。例如授课总时长与各单元时长之和必须一致，实验前置软件版本应与安装指南一致。规则应基于项目约束，而不是检查“没有冲突标记”。

参考分析：文本冲突检测与项目验收承担不同责任。前者帮助定位不能自动决定的文本位置，后者判断最终成果是否满足约束。真正完成合并，需要对最终结果负责。
