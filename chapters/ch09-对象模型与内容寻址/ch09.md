# 对象模型与内容寻址：辅导材料

## 实验拓展：从同一内容观察对象复用
### 问题背景
两份实验说明恰好具有相同文字，但名称不同。Git 是否必须为它们分别保存两份 blob？回答这个问题，需要把内容对象与目录条目分开。blob 对应内容，tree 条目把路径名称、模式和对象标识联系起来。两个路径可以引用同一 blob，而目录结构仍然清楚区分这两个名称。

以下独立实验不直接操作对象文件，而使用稳定的查询命令观察逻辑关系。对象标识会随内容与对象格式变化，不应照抄书中某个固定哈希作为判断依据。


### 让两个路径具有相同内容

```bash
mkdir reuse09
cd reuse09
git init -b main
git config user.name "Git Learner"
git config user.email "learner@example.invalid"
printf 'Inspect the staged content.\n' > first.txt
cp first.txt second.txt
git add first.txt second.txt
git commit -m "docs: add two identical notes"
FIRST09=$(git rev-parse HEAD:first.txt)
SECOND09=$(git rev-parse HEAD:second.txt)
test "$FIRST09" = "$SECOND09"
git ls-tree HEAD
git cat-file -t "$FIRST09"
git cat-file -p "$FIRST09"
```


`ls-tree` 显示两个路径条目，却可看到它们指向相同内容标识。这不是两个文件名相同，而是两份内容具有相同的 blob 表示。查询 blob 本身时，输出中不会附带路径名；路径属于 tree 的组织信息。


### 只改一个路径，并观察另一份内容继续复用

```bash
printf 'Inspect both staged and unstaged content.\n' > first.txt
git add first.txt
git commit -m "docs: refine the first note"
NEW09=$(git rev-parse HEAD:first.txt)
test "$NEW09" != "$FIRST09"
test "$(git rev-parse HEAD:second.txt)" = "$SECOND09"
test "$(git rev-parse HEAD^:first.txt)" = "$FIRST09"
git diff HEAD^ HEAD --name-only
```


新提交的根树发生变化，first.txt 指向新 blob，second.txt 仍引用旧 blob。旧提交也继续引用原有内容，因此读者仍能查到 first.txt 的旧版本。逻辑上的完整快照不要求每个版本都重新写入所有相同内容。

## 对象模型带来的三项推论
### 提交标识不能只由文件内容解释
提交对象除了树标识，还包含父提交、作者、提交者、时间和说明等信息。因此两个提交可以具有相同树，却具有不同提交标识。例如两种整理路线可能产生相同最终文件，但连接到不同父提交。比较树与比较历史回答不同问题。

这也解释了为什么修改旧提交通常影响相关后继提交的标识：父标识属于提交内容，父关系改变会传递到重新构造的后继。其他没有重写、也不依赖该变化的分支，不会因为“仓库里改过历史”就全部自动改变。

### 可达性是一种关系判断
对象是否仍可由引用和相关对象关系访问，与对象此刻是否还占据磁盘空间，不能简单等同。失去普通分支入口以后，对象可能暂时仍存在；反之，受限克隆也可能使某些所需内容尚未在本地完整取得。恢复时应查询实际对象与入口，而不是根据文件夹大小推断。

对象回收有其保留条件和实现细节。日常学习无需手工删除对象目录；真实故障中更不应为了“整理干净”而先执行激进清理。先建立保护入口与副本，再依据诊断结果决定维护动作。

### 内容校验与来源信任必须分开
对象标识帮助检测内容是否与预期对象一致，但它本身不能证明作者身份、需求正确性或依赖安全性。攻击者也能构造内容自洽的仓库。获取外部项目时，还需要核对来源、签名、发布流程和依赖策略。

学习哈希时应避免“绝不会碰撞”这类绝对表述。有限长度标识存在理论碰撞可能，实际安全还涉及具体算法、实现与攻击模型。本书用对象模型解释内容关系，不把哈希当作所有信任问题的统一答案。
