# 第2章 环境配置与仓库初始化：参考答案

答案用于复核理解；工程题需要同时提交操作、内容和验证依据。

## 2.1 【应用】在一个全新目录中完成两次提交。第一次只写标题，第二次增加计划。提交最近两条历史和最终 status 的结果，并说明为何不要求哈希与教材相同。

**考查知识点：**初始化、根提交、第二次提交。

**参考答案：**在新目录init，创建标题并add、commit；追加计划后再次add、commit。提交log最近两条与status结果。哈希受内容、父项、身份和时间等字段影响，不要求逐字相同；要核对两次意图、父关系和最终候选状态。

验收时读取第二个提交的父字段，确认它连接第一个提交，再分别查看两棵树中的文件。最终工作区干净说明本次选定变化已记录；它不能代替对两次提交是否具有正确目的和内容的检查。

## 2.2 【应用】同学已经配置了 GitHub 登录，提交时仍提示作者身份未知。这两种配置有什么不同？应查询哪两项设置？

**考查知识点：**配置作用域、提交身份、平台认证。

**参考答案：**GitHub登录验证平台访问身份，提交作者字段由本地Git配置写入。查询user.name与user.email，并使用show-origin确认生效来源；按需要修正仓库级配置。登录浏览器不会自动为所有本地仓库补齐作者配置。

可使用git config --show-origin --get user.email判断值来自哪个文件，再决定采用仓库级还是用户级配置。实验仓库中的合成身份用于演示；正式项目应由本人确认邮箱及公开范围，避免把浏览器登录当作本地配置来源。

## 2.3 【应用】新建文件后直接运行 commit，提示没有待提交内容。列出至少三种应检查的事实，并按检查成本排列顺序。

**考查知识点：**当前目录、跟踪状态、候选内容。

**参考答案：**先用pwd或仓库根查询确认位置，再用status确认文件名、保存状态和跟踪状态，接着查看候选差异；必要时检查是否被忽略、是否存在其他仓库边界。新文件未add时，普通commit不会自动选择它。

诊断应从低成本事实开始，先确认命令在正确仓库执行，再确认编辑器已保存，最后检查文件是否进入索引。若路径命中忽略规则，使用check-ignore说明命中的文件和行号，比反复运行commit更容易定位原因。

## 2.4 【应用】在 add 后、commit 前查看 log，新增的版本为什么还不存在？应使用什么命令检查本次候选变化？

**考查知识点：**暂存、历史查询、未诞生分支。

**参考答案：**add更新候选而未建立提交，log只读取已有历史。使用git diff --cached检查候选与HEAD的差异，使用git show :路径直接读取索引内容；尚无HEAD时按初始化情境解释命令结果。

尚无首次提交时，日志查询可能因没有可遍历入口而失败，这是该初始化状态的正常结果。git diff --cached仍可检查准备记录的新文件。报告应把命令失败原因与“Git未安装”“目录无权限”等环境问题分开。

## 2.5 【应用】把一个临时文件加入忽略规则，验证文件仍在磁盘上、不会出现在普通 status 中。写出证据，不要只给规则文本。

**考查知识点：**忽略规则、未跟踪文件、规则来源。

**参考答案：**创建未跟踪临时文件，增加匹配忽略规则，然后用文件读取或存在性检查证明文件仍在；普通status不列出它，再用git check-ignore -v确认命中规则。不要对已经跟踪的文件套用同一结论。

完整验证包含三项事实：磁盘文件仍存在，普通状态输出省略该路径，规则查询指出命中来源。若文件此前已经跟踪，应另行说明其候选和历史变化；忽略模式的匹配结果不能抹去已有跟踪关系。

## 2.6 【应用】完成本地 clone，比较两个仓库的历史与文件。说明为什么原仓库的临时文件没有出现在新目录中。

**考查知识点：**克隆、受跟踪快照、未提交现场。

**参考答案：**克隆后比较可达提交、提交树和受跟踪文件。原仓库的忽略临时文件没有进入所选提交，因此普通clone不会传送它；克隆不是复制整个工作目录，也不会复制所有本地未提交现场。

可在原仓库故意保留一份未跟踪草稿，随后从新克隆查询同一提交树。两边相同的是指定版本中的受跟踪内容；本地配置、临时文件和未共享入口可能不同。比较时应明确对象范围，避免机械比较整个目录字节。

## 2.7 【应用】你准备在线提交课程作业。哪些身份信息会进入提交历史？为什么示例邮箱不应原样用于需要关联个人贡献的正式仓库？

**考查知识点：**作者与提交者、邮箱、隐私。

**参考答案：**提交一般记录作者与提交者姓名、邮箱及时间等元数据，平台可以据邮箱等条件关联账户。示例邮箱仅用于合成实验，不能代表实际贡献者；正式使用应选择自己确认的身份或隐私邮箱。

作者字段与提交者字段可能不同，平台归属还受到邮箱关联等规则影响。课程报告应使用实际产生的提交元数据核对；需要隐私保护时选择平台提供并经本人确认的隐私邮箱，不应借用教材作者的姓名或地址。

## 2.8 【基础】解释“工作区干净”为什么不能推出“目录中所有文件都已备份”。至少给出一个本章实际观察到的反例。

**考查知识点：**干净状态、忽略内容、备份范围。

**参考答案：**干净状态主要说明相应比较范围没有需要报告的受跟踪变化；被忽略文件可能仍在磁盘且未进入历史。例如临时文件被规则忽略后status仍干净，它却没有出现在新克隆中。备份还要列出这些资料。

可以用忽略的临时文件作为反例：文件依然可读取，status却保持干净。进一步说明，备份清单应包含需要保存的未跟踪资料，仓库历史与工作草稿可采用不同方式保全，恢复时分别验证。

## 2.9 【应用】两台计算机显示不同Git版本，同一台计算机在两个终端中又得到不同邮箱。请设计检查顺序，区分可执行程序路径、配置作用域、配置来源与当前仓库位置，并说明应保留哪些输出。

**考查知识点：**安装环境、可执行程序、配置来源。

**参考答案：**先记录系统、终端及git --version，再查询shell实际选择的Git程序，排除不同安装入口。随后确认当前项目根目录，读取user.name、user.email及其show-origin结果，判断仓库级、用户级和其他配置是否覆盖。不同终端还可能继承不同环境条件。

修正应针对实际来源，不宜先删除所有配置。验收至少包含程序路径、版本、当前目录与生效配置来源，且在同一实验仓库重查结果。邮箱差异属于提交元数据配置，不能单凭浏览器账号状态推断其成因。

## 2.10 【应用】初始化后能看到.git却无法显示最近提交；另一个项目的.git是文本文件。分别解释这两种现象可能成立的条件，说明如何用Git提供的查询确定管理目录，哪些信息不能仅凭文件夹外观判断。

**考查知识点：**.git入口、初始化状态、路径查询。

**参考答案：**初始化可以先建立HEAD和管理结构，首次提交尚未产生时，没有可供日志遍历的当前提交，这是未诞生分支的正常情形。HEAD的符号名称与其目标提交是否存在，应分别查询。

.git文本文件可能指向关联工作树或子模块的实际管理目录。可使用rev-parse的管理路径查询核对，进一步观察公共目录。是否拥有完整历史、是否存在有效候选和当前分支指向什么，都需要相应查询；仅看图标不能确定这些事实。

## 2.11 【综合】实验室需要让三位同学在不同系统上取得同一课程资料。现有目录混有源码、构建结果和临时草稿，其中一台机器作者配置缺失。请制定接入步骤并完成两次有明确意图的提交；从新目录克隆验收，说明哪些文件应交付、哪些应另行保全及如何证明。

**考查知识点：**环境接入、首次提交、忽略、克隆验收。

**参考答案：**先确认Git程序和仓库根目录，按实验需要设置本人确认的提交身份，再列出源码、构建结果、草稿三类内容。对尚未跟踪的生成产物设置忽略规则，草稿按需要另存；第一次提交建立可阅读基线，第二次记录一项独立课程修订。每次提交前检查候选，提交后读取历史和文件。

从新目录克隆，核对两次记录、最终受跟踪内容和必要资源；被忽略的生成结果不应被误当作缺失源码。报告列出实际系统、版本、配置来源、提交意图和未入历史资料的保存位置。若克隆后不能按说明阅读或构建，应定位依赖缺口并修订交付清单。

建议先复制保全原目录，列出源码、生成物和草稿三类路径，再在专用练习仓库配置身份与忽略规则。第一项提交建立可构建的源码基线，第二项提交补充规范说明及必要资料；分别检查候选，避免把目录清理和业务修改混为一次提交。在全新目录克隆后，核对两个提交的树、身份字段和说明，重新构建并比对交付清单。跨系统差异应记录为环境条件，草稿另行归档，不能依赖忽略规则保存。
