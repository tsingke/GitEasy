# 环境配置与仓库初始化：辅导材料

## 图形界面与命令行的对应阅读
### 两种界面面对同一套状态关系
图形客户端可以用文件列表、差异面板和提交图展示仓库，帮助初学者观察变化；命令行则便于精确记录参数和复现步骤。两种入口可以相互验证。学习时应先理解界面展示的对象，再把按钮动作对应到实际状态变化。高见龙的公开教材也强调以概念理解支持界面操作（参见仓库根目录的参考资料）。

不同工具的界面名称和默认操作可能不同。例如名为“同步”的按钮可能组合获取、整合和推送，名为“提交所有”的按钮也可能自动暂存某些内容。因此，不能只依据按钮文字判断影响范围。应查看工具说明、操作预览及执行后的文件和引用状态。

### 一次提交应观察哪些区域
打开新建学习仓库以后，先确认客户端显示的路径与终端所处仓库一致；再创建一份文本文件，观察未跟踪列表；选择暂存后，观察候选列表与差异；创建提交以后，查看历史与工作区状态。每一步只完成一个目的，避免使用批量自动操作掩盖中间状态。

如果工具支持部分暂存，可以在文件中制造两处相距较远的修改，只选择其中一处，然后用 `git diff` 与 `git diff --cached` 分别核对。界面中的勾选结果应与索引实际内容一致。若工作文件后来继续编辑，界面也应能展示已暂存和未暂存两个比较范围。

### 提交图需要读懂连线含义
图形历史通常把提交排列在若干视觉轨道上，以便展示父关系。轨道颜色不是 Git 对象固有属性，也不必一一对应永久分支。一个分支名称可以随新提交移动，分支被删除以后，相关提交仍可能由其他入口访问。不能把图上的某条彩线当作独立复制的文件集合。

读图时先定位当前分支、HEAD 和目标提交，再看父关系。对于合并提交，注意它连接了哪些父提交；对于快进，注意名称移动而没有新建双亲整合点。必要时使用命令查询父标识进行核对。图形展示提供认知辅助，父关系才是历史判断依据。

### 从界面错误返回可复制证据
遇到失败时，应记录完整错误文字、操作目标、当前版本和目录。若工具提供执行日志，可据此辨认它实际调用了哪些操作。不要只写“按钮不能用”，也不要在不清楚原因时连续点击重试。重复操作可能改变现场，使原有问题更难解释。

本节练习不要求安装某个特定商业客户端。读者可以使用自己已有的工具，填写一份界面与状态对照记录：界面区域显示什么，操作改变什么，终端查询如何证明。若某个按钮包含组合动作，应逐项拆开解释。评价关注模型理解，而不是对某一版本界面位置的记忆。
