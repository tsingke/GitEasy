# 历史查询与版本溯源：辅导材料

## 案例研读：从错误页面追溯到变更原因
### 把“查历史”改写为三个问题
课程网站中的提交期限显示错误。读者首先应区分：当前文件是哪一版；哪一次变更引入了这段内容；当时为何作出修改。第一个问题可由当前引用与文件状态回答，第二个问题需要历史补丁，第三个问题则可能要结合提交说明、需求单和评审记录。没有任何一条查询命令能够自动回答全部问题。

一次规范的调查可以先固定出错版本，再限定文件路径，最后搜索相关文本。固定版本很重要，因为调查过程中主分支可能继续前进。若报告只写“当前 main”，后来的读者可能无法取得当时观察到的内容。应记录实际提交标识，并说明工作区是否另有未提交修改。

### 从候选提交走向因果判断
搜索到包含“截止时间”的提交，只能说明该提交的说明或补丁与关键词有关。它未必就是故障来源：可能只是修正文句，也可能是对先前错误的修复。应比较父版本与候选版本，在同一测试条件下确认行为是否改变。

即使自动二分定位得到首个失败提交，也仍需分析原因。该提交可能改变了数据格式，使原有读取程序的隐含假设不再成立；也可能引入了真正的拼写错误。定位回答历史边界，原因分析回答机制。两者结合，才能形成有解释力的故障报告。

## 实验拓展：验证查询范围的含义
以下独立实验建立一个包含主线和主题分支的历史。两条分支各增加一个文件，因此可以清晰区分提交集合与文件比较。实验只查询历史，不执行合并。


### 构造两条具有共同起点的历史

```bash
mkdir ranges04
cd ranges04
git init -b main
git config user.name "Git Learner"
git config user.email "learner@example.invalid"
printf 'Course baseline\n' > README.md
git add README.md
git commit -m "docs: establish the baseline"
git branch topic
printf 'Main schedule\n' > schedule.txt
git add schedule.txt
git commit -m "docs: add the main schedule"
git switch topic
printf 'Topic exercise\n' > exercise.txt
git add exercise.txt
git commit -m "docs: add a topic exercise"
git log --oneline main..topic
git log --oneline topic..main
git log --left-right --oneline main...topic
```


`main..topic` 选择从 topic 可达而从 main 不可达的提交，因而本例只列出增加练习的提交。反向范围列出增加主线安排的提交。三点范围在 `log` 中表示对称差，左右标记帮助辨认各项提交属于哪一侧。


### 比较端点与比较主题相对共同起点的变化

```bash
git diff --name-status main topic
git diff --name-status main...topic
git merge-base main topic
test "$(git rev-list --count main..topic)" = 1
test "$(git rev-list --count topic..main)" = 1
test "$(git diff --name-only main...topic)" = exercise.txt
```


直接比较两个端点时，主线独有的安排与主题独有的练习都会造成差异；以共同祖先比较到主题端点时，则只出现主题新增的练习。同样的三点符号在不同命令中服务于不同问题，不能把 `log` 的提交集合含义直接套到 `diff`。

## 历史调查的可复核报告
### 最小证据应包含什么
报告至少记录观察版本、预期结果、实际结果、复现条件、查询范围和候选变更。若使用自动判定，还应说明退出状态的含义，特别是无法测试某一历史版本时怎样处理。把依赖安装失败直接标为业务失败，可能让二分搜索定位到环境边界而非缺陷边界。

逐行归属信息同样需要语境。`blame` 通常给出相关行最后一次修改的线索，而不是对错误责任作裁决。格式整理、文件移动或历史重写都可能影响线索。适当结合忽略空白、移动检测与旧路径查询，可以帮助调查，但最终仍需阅读上下文和补丁。

### 何时停止继续缩小范围
若已经获得可重复的失败用例，并能解释候选提交如何改变行为，就具备进入修复阶段的基础。继续追求更短的命令或更漂亮的日志，并不会自动增加结论可信度。应把精力用于验证修复是否覆盖原问题，以及是否引入新的边界错误。

一个合格的学习报告可以用四段完成：现象、定位、原因、验证。每段都应关联实际版本和证据。避免仅粘贴整页日志，让读者自行寻找结论；也避免只给结论而缺少重现入口。
