# 团队工作流与代码评审：辅导材料

## 案例研读：让评审形成可执行的决定
### 从需求到验收条件
某小组准备把实验报告提交方式由邮件改为仓库提交。如果需求只有“优化提交流程”，作者可能只修改一处说明，而评审者却期待同时更新命名规则、截止时间和评分依据。冲突并非来自 Git，而是来自任务边界不明确。

需求应写成读者可以验证的行为：学生能找到提交入口；报告命名具有示例；截止时间含时区；教师能按固定位置取得材料；旧方式停用时间明确。每一项都应能在补丁或验证结果中找到依据。这样评审讨论便围绕任务是否满足，而不是围绕个人偏好反复修改。

### 评审意见需要包含理由与影响
“这里不好”难以执行，“请将截止时间写明时区，否则异地读者可能产生不同理解”则说明了问题、后果和修改方向。对可以接受但尚有取舍的设计，应区分建议与阻断项，避免作者把所有偏好都当作必须满足的要求。

作者回应时应说明已修改的位置、验证方式，或保留原设计的依据。简单回复“已改”无法帮助评审者判断新版本解决了什么。若补丁发生较大变化，应重新核对范围，不能沿用旧版本的通过结论。

## 协作练习：建立一份可审阅的变更说明
下面的独立实验用本地分支模拟提交评审前的材料准备。它不创建线上 PR，但将作者必须解释的内容组织成实际文件，后续可直接迁移到 GitHub。


### 准备具有明确验收范围的主题变化

```bash
mkdir review13
cd review13
git init -b main
git config user.name "Git Learner"
git config user.email "learner@example.invalid"
printf '# Course guide\n' > README.md
git add README.md
git commit -m "docs: establish the course guide"
git switch -c docs/submission
mkdir docs
cat > docs/submission.md <<'EOF'
# Report submission

- Location: reports/student-id/
- File name: lab-number.md
- Deadline: Friday 18:00, Asia/Shanghai.
- Required sections: method, evidence, and explanation.
EOF
git add docs/submission.md
git commit -m "docs: define the report submission contract"
git diff --check main...HEAD
git diff --stat main...HEAD
git log --oneline main..HEAD
```



### 按问题、变化与验证组织交接说明

```bash
cat > ../review13-summary.md <<'EOF'
# Submission contract

Problem: students need one unambiguous report location.
Change: define location, file naming, deadline, and report sections.
Validation: inspect the new guide and run git diff --check.
Follow-up: the instructor confirms the deadline before merging.
EOF
test "$(git diff --name-only main...HEAD)" = docs/submission.md
grep -q 'Asia/Shanghai' docs/submission.md
test -z "$(git status --porcelain)"
```


交接说明保存在仓库外，是为了在本实验中区分待评审的产品内容与评审描述。真实平台上的 PR 正文承担类似沟通职责，但其本身不是普通提交对象的一部分。需要长期保存的设计理由，可以进一步写入项目文档，而不能只依赖某个临时讨论入口。

## 合入策略与长期维护
### 一项策略同时影响哪些工作
保留合并提交有助于识别整合点，压缩合入有助于把主题作为一项主线变化，重放合入则可能形成线性序列。选择时要考虑回退、逐提交测试、来源追踪和团队习惯，而不能只依据日志是否简短。

无论选择哪种策略，都应检查最终主线内容，并确认评审所依据的版本与实际合入结果相匹配。自动化合入还可能在新的主线基线上执行，因此需要理解平台检查绑定的是哪个提交或合并候选。

### 完成任务还包括关闭反馈循环
合入以后，应说明目标版本、相关文档和后续事项。若需求只是部分完成，不能因 PR 已合入就关闭全部讨论。教学小组可以将任务分为已完成、需另行处理和明确不采用三类结论，并为每项结论保留理由。

迁移练习：评审通过以后，主线发生了相关修改。作者应怎样处理？参考分析是先取得新信息，判断主题是否仍满足需求，必要时整合并重新验证。过去的通过说明适用于当时审阅的内容，不能自动延伸到所有后续版本。
