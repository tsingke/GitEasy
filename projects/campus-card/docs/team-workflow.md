# 团队协作与发布约定

需求先登记背景、可观察结果和拒绝条件，再从最新main建立短期分支，例如`feature/cc-03-payment`。一次提交表达一项可解释的变化；实现与必要测试通常一起提交，大范围格式调整另行处理。

贡献者在推送前检查候选差异，运行核心测试；界面变化另跑Qt构建与交互冒烟测试。PR说明包含关联需求、实现范围、验证环境、失败用例、界面变化和未完成事项。评审者核对业务规则、所有权、异常后的状态与构建前提，不能只依据终端绿色结果确认业务正确。

合入策略由团队明确选择。保留合并提交有利于观察主题分支整合，压缩合入适合把多次工作提交组织为一个交付意图；采用任一方式都必须按结果检查测试和目标差异。已共享分支的历史整理需协调，不用强推掩盖未处理的分歧。

发布前记录确切提交、测试证据和依赖，建立附注标签；GitHub Release补充说明与构建产物。源码归档不包括Git历史，bundle不自动覆盖平台Issue/PR或外部数据。维护分支从已发布标签建立，只移植与该版本相关的修复和测试。

教材中的本地双人演练不创建真实Issue或PR。线上任务在学习者自己的仓库或获得权限的教学仓库进行；把实际URL写入报告，不填写虚构审批或不存在的评审人。

连续快速修改与检出后，教学路线使用 `cmake --build build --clean-first --parallel 2` 清理旧对象再验证；二分检查也重新编译当前版本，避免旧生成产物影响好坏判断。源码、索引和历史不会因此被清理。
