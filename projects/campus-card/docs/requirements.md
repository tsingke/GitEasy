# 需求、业务规则与验收

## 使用者与目标

校园服务台为学生和教工办理演示卡业务。维护者统筹需求、评审和发布，领域开发者实现规则，界面开发者连接事件与模型，测试者验证成功与拒绝路径。小组可轮换角色，记录每一阶段的责任。

## 需求清单

| 编号 | 需求 | 验收 |
|---|---|---|
| CC-01 | 学生卡、教工卡开卡 | 卡号不重复，标识和姓名有非空白内容，余额为零 |
| CC-02 | 充值 | 金额严格为正且在演示上限内，更新余额并追加流水 |
| CC-03 | 消费 | 检查挂失、余额与当日累计限额，通过后扣款 |
| CC-04 | 挂失与解挂 | 挂失期间拒绝新的资金业务，解挂后恢复 |
| CC-05 | 同一请求重试 | 参数相同返回原回执，不重复记账；参数冲突拒绝 |
| CC-06 | 账户与流水显示 | 界面从业务服务读取，不复制另一套计算逻辑 |
| CC-07 | CSV导出 | 输出本次流水，保留引用字段与整数分格式化结果 |
| CC-08 | 可重复构建 | 核心独立构建，Qt目标按显式开关启用 |
| CC-09 | 可追溯交付 | 需求、分支、提交、PR、测试、标签和交接相互对应 |

演示规则：学生单日500.00元，教工单日1000.00元；最大账户余额1000000.00元。这些值是课程设定，不代表任何学校现行规定。日期按业务请求解释，格式为真实的YYYY-MM-DD日历日期。

## 拒绝与一致性

业务拒绝后余额与流水数量都应不变。测试既检查“发生异常”，也检查原状态保留。挂失不删除账户和旧流水；重复请求返回的是原来记账时的余额，不保证等于账户当前余额。

## 后续迭代

持久化、并发事务、统一身份认证、审计权限、设备通信和真实清结算列为后续系统设计任务。新增功能前先说明改变了哪条业务不变量，并建立对应的成功与失败测试。
