# 校园一卡通项目实施方案

本方案先确定需求、模块边界、开发顺序与证据要求，再实施代码调整。项目采用企业研发中的需求追踪、接口评审、短期任务分支、持续检查、发布基线和维护回移方法；交付物为可运行的多文件教学工程。学生先完成个人闭环，再以团队角色复现同一过程。

## 1. 业务范围与交付目标

服务台为学生卡、教工卡办理开卡、查询、充值、消费、挂失、解挂与流水导出。金额以整数分表示，消费受余额、卡状态和类别限额约束；同一请求的重试应返回既有回执，不得重复记账。输入不合法或业务被拒绝时，既有余额与流水保持一致。

第一版采用进程内存储和CSV报告，明确不包含真实支付、身份认证、生产数据库、跨进程事务和并发控制。持久化、权限与服务端接入作为后续架构演进任务，必须先提出接口、迁移方案和测试，再进入实现。课堂工程不因采用企业研发方法便被宣称为真实资金系统。

## 2. 角色与协作规则

| 角色 | 主要责任 | 交付依据 |
|---|---|---|
| 需求负责人 | 描述业务条件、拒绝条件与迭代范围 | 带验收标准的Issue与需求编号 |
| 领域开发者 | 实现金额、日期、持卡人策略与业务服务 | 接口、实现、单元测试与PR |
| 界面开发者 | 完成Qt输入、调用、反馈与视图更新 | 交互说明、截图与冒烟测试 |
| 测试与评审者 | 独立重现边界、评审变更及依赖 | 测试输出、具体评审意见 |
| 发布维护者 | 固定版本、维护分支、验证恢复与交接 | 标签、发布记录、修复回移与恢复报告 |

个人实践时轮换承担角色，并在自检记录中注明身份；团队实践时对主要业务变更安排另一名成员评审。自检不能写成第三方批准。

## 3. 多文件模块与依赖

| 模块 | 头文件与实现文件 | 负责内容 | 不承担的职责 |
|---|---|---|---|
| 基本类型 | `include/campus/types.hpp` | 金额单位、枚举、查询视图与交易回执 | 输入界面、全局状态 |
| 金额 | `money.hpp`、`src/money.cpp` | 十进制文本解析、整数分、格式化与上限 | 账户余额修改 |
| 日期 | `business_date.hpp`、`src/business_date.cpp` | 日历合法性、系统日期和可注入日期提供器 | 界面时钟展示 |
| 持卡人 | `card_holder.hpp`、`src/card_holder.cpp` | 封装身份、虚接口、学生与教工限额策略 | 账户容器与流水 |
| 流水报告 | `ledger_export.hpp`、`src/ledger_export.cpp` | CSV转义、列格式与金额展示 | 数据恢复和数据库事务 |
| 业务服务 | `card_service.hpp`、`src/card_service.cpp` | 开卡、状态、余额、限额、幂等及一致性 | Qt组件、文件对话框 |
| 命令行 | `src/main.cpp` | 最小可运行调用示例 | 复制业务规则 |
| Qt界面 | `gui/campus_window.hpp`、`gui/campus_window.cpp`、`gui/main.cpp` | 输入转换、事件连接和视图刷新 | 直接修改余额与状态 |
| 交互检查 | `gui/smoke_scenario.cpp` | 真实按钮动作与业务、表格一致性检查 | 生产环境认证 |
| 分层测试 | `tests/test_*.cpp` | 值对象边界、日历、导出、服务与日期注入 | 以截图替代行为检查 |

依赖方向为“CLI或Qt → 业务服务 → 基础模块”。基础模块不依赖Qt。头文件表达可使用的接口，`.cpp`保存实现；CMake按目标独立编译并链接，禁止通过包含`.cpp`拼接程序。

## 4. C++能力目标

使用类封装和访问控制保护状态；通过抽象基类、虚析构、继承与`override`解释运行时多态；以`std::unique_ptr`和移动语义表达所有权；以`enum class`区分业务状态和操作；以容器、范围for、lambda、`std::function`、异常及聚合初始化组织规则与可测依赖。业务核心严格使用C++11；Qt6界面采用其要求的C++17。每个特性都对应具体职责，避免为展示语法而增加无关结构。

## 6. 任务进入与完成标准

进入开发前，任务需说明用户、触发条件、业务结果、拒绝条件、涉及模块、验收方法及与既有任务的关系。接口或数据结构调整先提交设计说明，待依赖方确认后实施；团队同时修改同一接口时先协调边界。

完成时，候选差异只包含本任务；代码、测试及必要文档同时更新；核心构建和相关测试通过；界面变化另有Qt交互检查；PR列出验证环境与未完成事项；合入后检查目标分支的实际结果。CI通过是必要证据，业务验收仍需逐项核对需求。

## 7. 版本与证据管理

需求编号连接设计、任务分支、提交、PR、测试和发布标签。实现分支从当前基线建立，短期合入；共享主线优先追加修复，私有历史整理前先确认是否已被他人使用。维护分支仅接收适用于该发布线的修复与测试。

每次交付保存确切提交、环境、构建命令、测试结果、依赖来源、已知限制及恢复方法。代码用Git跟踪，构建目录和真实账户数据排除；凭据不入库。Git历史、源码归档、平台元数据和运行数据分别列出保全方法。

## 8. 实施顺序与验收

本轮先拆分基础模块与界面，再补充分层测试和注释，随后修订连续演练的种子生成器、补丁工具、教材命令与文件路径。现有业务行为作为回归基线；重构不更改已有金额、限额与幂等约定。完成后执行核心与Qt测试、连续双人演练、38条离线路线、候选构建、章节材料检查及跨平台CI，并记录实际通过范围。
