# 综合项目实训：辅导材料

## 项目六：课程资料库的独立交接与复核
### 情境、角色与交付边界
课程小组完成一个学期的资料编写后，需要将维护工作交给下一届学生。接收者没有参与原开发过程，也不了解个人计算机上的目录习惯。项目目标是让接收者仅凭交付材料，能够取得正确版本、运行检查、理解历史、完成一项修复，并验证恢复路线。

本项目设作者、接收者和复核者三种角色。作者整理交付材料；接收者从干净目录执行；复核者检查证据是否足以支持结论。人数不足时可由同一学生分阶段扮演，但必须使用独立目录，并记录各阶段的输入和结果，避免凭借旧环境掩盖缺失步骤。

### 任务一：固定可交接的版本
作者选择一个已完成检查的提交，创建符合团队约定的发布入口，记录实际提交标识、版本说明和适用环境。若当前分支仍有草稿，应明确这些草稿不属于本次发布，并按需要另行保全。不能用“工作目录当前看起来正确”替代提交级交付。

复核者检查发布入口是否确实指向记录的提交，说明是否与实际内容一致，依赖和外部数据是否可取得。若使用签名，分别记录签名验证结果和公钥信任来源。不得仅因平台显示某个状态图标就省略验证对象说明。

### 任务二：从空目录重建并发现缺口
接收者按 README 获取材料，并依照环境说明运行检查。对每个失败，先判断属于资料缺失、路径错误、权限问题、版本差异还是业务规则不满足。应保留原始提示，并给出最小复现步骤；不要未经分析就在原项目中反复试改。

作者根据这些反馈完善文档和工具。一次真正的交接验收，往往能够发现作者长期使用环境中被忽略的前提：自动生成但未说明的文件、个人配置、绝对路径、未固定的依赖或只能从私人地址取得的数据。这些都应形成明确修订。

### 任务三：完成一项跨章节修复
复核者给出一项受控问题，例如课程安排与实验说明中的地点不一致。接收者创建任务分支，先用历史查询定位相关修改，再形成独立修复，检查候选范围并提交评审材料。若主线同时前进，应先比较变化，再选择符合约定的整合方式。

验收同时检查结果与过程：两份说明是否一致，提交是否仅包含相关变化，评审说明是否解释原因，整合后是否重新验证。若采用历史整理，还要保留整理前后的对应证据。此项任务将基础操作、历史检索、分支、协作与评审连接为一条完整工作链。

### 任务四：实施可恢复性演练
作者提供按范围说明的备份材料，接收者在另一新目录恢复。检查目标包括发布提交、关键文件、必要依赖和运行能力。若使用增量 bundle，必须先满足其基线前提，再应用增量，不能把增量文件当作独立完整副本。

演练报告应列出恢复成功的内容、未覆盖内容和实际耗时。若平台需求单、评审讨论或外部对象不在备份范围，应写明其另行保存方式。恢复过程中不应访问真实生产凭据；所有教学身份和密钥均按实验边界使用。

## 综合能力的分层评价
### 结果正确性
这一层评价交付内容是否满足明确需求，是否能从指定版本重建，是否存在无关文件或遗漏。结果正确是基础，但不能只依据文件数量或提交数量评分。相同数量可以对应完全不同的工作质量。

### 过程可解释性
学生应能解释索引为什么包含这些内容，某次整合为什么采用该策略，某项恢复依据来自哪里。答辩可要求学生在一个新情境中预测状态变化，再执行查询验证。背诵命令选项而不能解释比较边界，不应视为已经掌握模型。

### 协作可接续性
评审者应能从变更说明理解问题，接收者应能从 README 找到运行入口，维护者应能从历史与发布记录定位版本。若这些工作仍依赖作者口头补充，应把缺失内容反馈到项目文档，而不是把沟通困难归咎于接收者不熟悉工具。

### 风险与范围判断
面对历史改写、强制更新、凭据事故和恢复操作，学生需要先判断影响范围，再决定执行路线。评价不要求所有任务都采用最复杂工具，而要求选择与前提一致、解释充分。能说明某种方法为什么不适用于当前条件，同样体现专业能力。

## 结课反思与后续学习
完成项目以后，请写一份简短反思，回答三个问题：哪个实验改变了自己对 Git 的原有理解；哪个错误最能暴露模型上的混淆；今后怎样在真实项目中保持可验证的记录习惯。反思应关联具体提交或实验结果，避免只写“学会了很多命令”。

进一步学习可沿三个方向展开：阅读官方手册理解边界条件；参与真实项目练习评审与维护；研究对象存储、传输协议和自动化工具。Git 的命令会继续发展，但对状态、关系、证据和协作约定的清晰区分，将持续帮助读者判断新工具的实际作用。
